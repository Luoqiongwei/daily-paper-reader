## 摘要
自动程序修复（APR）近期受益于大语言模型（LLMs），但其有效性高度依赖于修复上下文。现有的基于LLM的APR方法存在因果差距：测试上下文可能嘈杂或不完整，而静态分析得到的源代码上下文往往包含不相关且未执行的代码，从而误导LLM无法识别真正的根本原因。为解决此问题，我们提出了CausalRepair，一种基于最小因果上下文的对话驱动APR框架，即解释失败所需的基本依赖。CausalRepair采用双切片策略：上下文感知的静态切片净化测试语义，而基于执行轨迹的动态切片捕获源代码中的精确运行时依赖。两者结合，构建紧凑且因果相关的上下文以指导迭代修复。我们在Defects4J V1.2、V2.0和Defects4J-Trans上使用DeepSeek-V3评估了CausalRepair。CausalRepair在Defects4J上正确修复了313个缺陷，优于ReinFix和TSAPR等最先进方法，同时将平均修复成本降至每个缺陷0.029美元。

## Abstract
Automated Program Repair (APR) has recently benefited from Large Language Models (LLMs), yet their effectiveness heavily depends on repair context. Existing LLM-based APR methods suffer from a causality gap: test contexts can be noisy or incomplete, while source contexts derived from static analysis often contain irrelevant and unexecuted code, misleading LLMs from identifying the true root cause. To address this issue, we propose CausalRepair, a conversation-driven APR framework based on minimal causal context, i.e., the essential dependencies required to explain a failure. CausalRepair employs a dual-slicing strategy: context-aware static slicing purifies test semantics, while execution-trace-based dynamic slicing captures precise runtime dependencies in source code. Together, they construct compact, causally relevant contexts to guide iterative repair. We evaluate CausalRepair on Defects4J V1.2, V2.0, and Defects4J-Trans using DeepSeek-V3. CausalRepair correctly fixes 313 bugs on Defects4J, outperforming state-of-the-art approaches such as ReinFix and TSAPR, while reducing the average repair cost to $0.029 per bug.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：自动化程序修复（APR，Automated Program Repair）旨在自动修复程序缺陷，是提升软件可靠性与开发效率的关键技术。近年来，基于大语言模型（LLM）的APR方法已成为该领域的主流范式。
- **核心问题**：基于LLM的APR方法严重依赖所提供的修复上下文的质量，但现有方法在构建上下文时存在一个关键“因果差距”（Causality Gap），具体表现为两方面：
  - **测试端上下文模糊**：或者提供过于完整的测试代码，引入多个断言和无关场景，干扰模型理解失败意图；或者只给失败断言与错误信息，缺少必要的执行上下文和状态依赖。
  - **源码端上下文过度近似**：基于静态分析的检索会包含所有可能执行路径（即静态过度近似），引入大量实际未执行的死代码和噪声，使LLM无法区分真正导致失败的语句。
- **研究含义**：论文指出有效的APR不依赖“更多的上下文”，而依赖“因果相关的上下文”。若不能向LLM提供精确对应失败因果链的上下文，模型就会被误导，产生过拟合或幻觉式修补。

## 2. 方法论（核心思想与技术细节）

### 2.1 核心概念：最小因果上下文
- 定义为“解释特定失败所需的基本依赖集合”，即过滤所有噪声后，保留直接导致失败断言的根本原因链路。

### 2.2 双切片策略（Dual-Slicing）
- **测试端：上下文感知静态切片**
  - 以小失败行及其变量集为切片标准，基于程序依赖图（SDG，System Dependence Graph）计算数据依赖和控制依赖的后向闭包，删除与失败无关的测试语句。
  - 进一步开展过程间依赖提取（Inter-procedural Context Extraction），递归解析相关外部方法定义和字段，避免依赖缺失。
  - 最终获得语义纯净、依赖完整的测试上下文（\(C_{test}\)）。
- **源码端：基于执行轨迹的动态切片**
  - 使用Slicer4J在净化后的测试驱动下执行缺陷程序，记录实际运行时事件序列。
  - 以失败语句对应的最后一个运行实例作为动态切片标准，构建动态依赖图（DDG，Dynamic Dependence Graph），只保留动态数据依赖和动态控制依赖的传递闭包。
  - 将片段映射回源码，得到精确的最小运行时依赖语句集（\(S_{dyn}\)），排除未执行的死代码。

### 2.3 结构化重构与提示工程
- **AST重构**：将碎片化的切片语句按其所属文件、类和方法进行层级封装，重建代码骨架，避免“lost in the middle”现象。
- **语义锚点注入**：加入文件路径头、保留Javadoc与注释、标注相对行号，增强LLM的空间感知和意图理解。
- 最终将测试上下文与源码上下文合并为“最小因果上下文”，构造修复提示。

### 2.4 对话驱动的迭代修复与补丁扩充
- **Phase 2（对话驱动迭代修复）**：采用“生成—验证—反馈”闭环，LLM基于候选补丁和测试执行反馈（错误信息、编译错误）逐轮修正。算法层面：最多m次修复尝试，每次尝试内最多n次迭代交互，直至补丁通过全部测试。
- **Phase 3（补丁扩充）**：将已验证的可行补丁作为参考基准，引导LLM生成语义相似的替代实现，以缓解测试套件不完整导致的过拟合问题，增强补丁多样性。
