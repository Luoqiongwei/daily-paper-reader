## 摘要
大语言模型在代码生成和自动化程序修复方面展现出强大的能力，但迁移整个仓库很少能生成可运行的应用程序，因为长时程翻译挑战了基于LLM的智能体维护仓库级迁移目标的能力。在这项工作中，我们提出了基于熵的代码对抗翻译（ECAT），一种用于自动化Android到HarmonyOS仓库迁移的多智能体框架。ECAT将仓库迁移表述为通过生成器-判别器架构进行的对抗熵最小化。判别器使用称为代码熵的统一指标来衡量迁移质量，并产生文本梯度，这些梯度指定了文件级生成指令以及执行这些指令所需的技能。在这些优化信号的指导下，生成器迭代更新仓库，并且仅当更新降低代码熵时才被接受。重复的生成器-判别器交互逐步推动迁移从初始模板朝向功能完整的HarmonyOS仓库。成功的低熵轨迹进一步被提炼为自进化的记忆树，使迁移知识能够在仓库间迁移。我们还引入了A2H-RepoBench，这是首个用于Android到HarmonyOS仓库迁移的真实世界基准，涵盖从数万行到数十万行代码的应用程序。通过节点对齐和基于智能体的功能评判者进行评估，ECAT实现了74.7%的整体迁移质量，并在不同规模的仓库中持续优于现有的基于智能体的方法。

## Abstract
LLMs have demonstrated strong capabilities in code generation and automated program repair, but migrating an entire repository rarely produces a runnable application because long-horizon translation challenges LLM-based agents' ability to maintain repository-level migration objectives. In this work, we propose Entropy-based Code Adversarial Translation (ECAT), a multi-agent framework for automated Android-to-HarmonyOS repository migration. ECAT formulates repository migration as adversarial entropy minimization through a generator-discriminator architecture. The discriminator measures migration quality using a unified metric called Code Entropy and produces text gradients that specify both file-level generation directives and the skills needed to execute them. Guided by these optimization signals, the generator iteratively updates the repository, and each update is accepted only if it reduces Code Entropy. Repeated generator--discriminator interactions progressively drive the migration from an initial template toward a functionally complete HarmonyOS repository. Successful low-entropy trajectories are further distilled into a self-evolving memory tree, enabling transferable migration knowledge across repositories. We also introduce A2H-RepoBench, the first real-world benchmark for Android-to-HarmonyOS repository migration, covering applications from tens of thousands to hundreds of thousands of lines of code. Evaluated by node alignment and an agent-based functional judge, ECAT achieves 74.7% overall migration quality and consistently outperforms existing agent-based methods across repositories of different scales.

## 1. 核心问题与研究动机

论文聚焦**仓库级代码迁移**（repository-level code migration），具体场景是 Android → HarmonyOS 的整仓迁移。相比单文件级翻译或代码生成，整仓迁移需要同时转换编程语言（Java/Kotlin → ArkTS）、UI 框架、项目配置、平台 API，并保持跨文件依赖、资源和运行时行为的一致性。由于仓库规模达数万至数十万行代码，LLM 的长上下文推理能力会下降，导致生成错误累积和长程依赖断裂。

现有基于 LLM 智能体的方法主要存在两个问题：

- **自我评估偏差**：大多数系统是同一代理负责生成与自我修正，容易高估自身输出质量，出现“过早收敛”，导致编译错误或功能缺失。
- **经验不可积累**：不同仓库的迁移过程彼此孤立，类似优化轨迹会被重复探索。

作者借鉴生成对抗网络的思想，将仓库迁移转化为**对抗熵最小化**问题，核心思路是引入独立的判别器来评估迁移质量、提供优化信号，并由生成器逐步修复仓库，从而使迁移过程可监控、可迭代、可持续优化。

## 2. 方法论

### 2.1 总体框架：ECAT

ECAT 是一个多智能体框架，包含：

- **生成器（Generator, G）**：根据当前仓库状态和文本梯度，生成或修复 HarmonyOS 仓库。
- **判别器（Discriminator, D）**：独立评估迁移质量，输出代码熵估计值和结构化文本梯度。
- **自进化记忆树（Self-Evolving Memory Tree, M）**：共享给生成器和判别器，存储可迁移的迁移知识与修复经验。

核心流程为：判别器 → 文本梯度 → 生成器更新 → 判别器评估 → 仅接受熵减更新 → 持续迭代至满足停止条件。

### 2.2 代码熵（Code Entropy）

引入统一目标函数——**代码熵** \( H(R_t) \)，衡量仓库的整体“无序度”，数值越大表示迁移错误、不一致和未解决问题越多。

形式化地，代码熵由 \( K=14 \) 个评估维度组成：

\[
H(R_t) = \frac{W^\top E}{\mathbf{1}^\top W}
\]

其中 \( E = [e_1, ..., e_K]^\top \) 为各维度归一化熵向量，\( W \) 为权重向量。各维度分为：

- **静态熵**：编译是否通过、代码风格、占位符、包名与权限一致性、导航可达性、功能完备性等，通过规则检测或 LLM 判定。
- **动态熵**：运行时的 UI 对齐、冷启动存活率、崩溃情况等，依赖模拟器截图与多模态 LLM 评估。

### 2.3 对抗优化过程

- 每次迭代中，判别器生成结构化文本梯度 \( g_t \)，包含摘要、工作列表（具体错误文件、问题描述）、建议技能；
- 生成器依据梯度更新仓库得到候选仓库 \( \hat{R}_{t+1} \)；
- 仅当候选仓库的代码熵低于当前熵时，才被接受，保证单调优化；
- 使用滑动窗口停止准则，当连续 \( l \) 次迭代熵值低于阈值 \( \epsilon \) 时终止。

该过程类似 GAN 的对抗训练：判别器不断“攻击”缺陷区域，生成器不断“修补”，使系统逐步靠近高质量迁移目标。

### 2.4 自进化记忆树

成功降低熵的轨迹会被蒸馏为记忆树中的经验节点。树结构由根节点、类别节点（如导航与路由、跨平台移植、占位符检测）和叶子节点（具体模式、根因、验证准则）构成。记忆树支持跨仓库知识迁移，并在检索时按层级筛选，避免平铺记忆带来的上下文膨胀。

## 3. 实验设计

### 3.1 数据集 / 基准

作者构建了 **A2H-RepoBench**，首个真实世界 Android-to-HarmonyOS 仓库迁移基准，包含三个应用：

| 仓库 | 规模 | 特点 |
|---|---|---|
| Gallery | 50K LOC | 多媒体应用，侧重 UI 迁移与媒体管理 |
| AntennaPod | 120K LOC | 播客管理，涉及播放与异步任务调度 |
| Meshtastic | 300K LOC | 网状通信应用，蓝牙与硬件交互，长程依赖复杂 |

### 3.2 评估指标

- **Node Alignment**：基于 CodeGraph 抽取语义图，计算 Android 与 HarmonyOS 节点的匹配比例；
- **Agent-as-Judge**：基于特征清单，由评判智能体对每个功能给出 Full/Partial/Missing 评分。

### 3.3 对比方法

- **OpenHands**：通用 ReAct 式软件工程代理；
- **RepoTransAgent**：ReAct 式仓库翻译代理；
- **ReCodeAgent**：多角色协作的原仓库翻译框架。

### 3.4 主要实验结果

| 方法 | 平均迁移质量 |
|---|---|
| OpenHands | 14.0% |
| RepoTransAgent | 13.3% |
| ReCodeAgent | 46.4% |
| **ECAT (Ours)** | **74.7%** |

- 去除动态熵后平均分降至 72.7%，说明动态评估对运行时密集型仓库有影响。
- 去除独立判别器后平均分暴跌至 28.4%，验证了“独立判别器”对避免自我偏差的关键作用。
- 使用记忆树时收敛更快（38 vs 66 迭代），累计 token 消耗约减半（~65M vs ~125M）。

## 6. 主要结论

1. **对抗熵最小化对于长时程仓库迁移是有效的**：将生成与评估解耦，可以显著避免自我评估偏差；
2. **代码熵提供了可优化的统一目标**：静态与动态熵的结合可更全面地反映迁移质量；
3. **自进化记忆树能实现跨仓库知识迁移**，减少迭代次数和 token 开销；
4. ECAT 在真实场景从 50K 到 300K LOC 的仓库上均优于现有基于代理的系统，整体迁移质量提升至 74.7%。

## 7. 方法优点

- **将对抗学习思想引入仓库级代码迁移**，突破了单一智能体自我修正的限制，框架概念新颖且清晰；
- **代码熵作为统一优化目标**，将多维度质量度量归一化，便于控制器和评估器协作；
