## 摘要
近似最近邻搜索（ANNS）在十亿级向量数据集上已经成为现代检索系统的基础算子，支撑大规模推荐、语义搜索和LLM/RAG工作负载。尽管GPU为批量向量搜索提供了大规模并行性和高带宽内存，但其有限的显存容量使得完全驻留在GPU上的十亿级索引难以部署。在CPU-GPU异构设计中，将基础向量保留在主机内存中可以避免这一容量限制，但天真地将精细搜索卸载到GPU会引入新的瓶颈：大量基础向量数据必须通过PCIe流式传输。我们提出了InSituANN，一种基于IVF的ANNS引擎，能够在单个商用GPU上实现十亿级向量搜索。InSituANN将原始基础向量保留在主机内存中，就地执行精细搜索，并使用GPU进行紧凑路由和可选剪枝。因此，查询处理避免了高维基础向量的PCIe传输，同时保留了IVF的简单性。除了查询性能之外，我们还为InSituANN设计了一条超快的IVF构建路径。在SIFT-1B上，InSituANN在5.2分钟内构建IVF索引，比测量的30.4小时HNSW构建快约350倍。在十亿级数据集上达到匹配召回率时，与受PCIe限制的Rummy基线相比，InSituANN将端到端吞吐量提高了104.9倍到4298.2倍，在SIFT-1B和DEEP-1B上比DiskANN提高了2.4倍到4.6倍。结合强大的召回-吞吐量权衡和比基于图的方法更低的索引空间，这些改进使得十亿级检索在成本高效的硬件上变得实用。我们在https://github.com/mindtravel/InSituANN-OpenSource开源了InSituANN。

## Abstract
Approximate nearest neighbor search (ANNS) over billion-scale vector datasets has become a foundational operator for modern retrieval systems, powering large-scale recommendation, semantic search, and LLM/RAG workloads. Although GPUs offer massive parallelism and high-bandwidth memory for batched vector search, their limited VRAM capacity makes fully GPU-resident billion-scale indexes difficult to deploy. In CPU-GPU heterogeneous designs, keeping the base vectors in host memory avoids this capacity limit, but naively offloading fine search to the GPU introduces a new bottleneck: large volumes of base-vector data must be streamed over PCIe.   We present InSituANN, an IVF-based ANNS engine that enables billion-scale vector search on a single commodity GPU. InSituANN keeps original base vectors in host memory, performs fine search in situ, and uses the GPU for compact routing and optional pruning. As a result, query processing avoids PCIe transfers of high-dimensional base vectors while retaining the simplicity of IVF. Beyond query performance, we further design an ultra-fast IVF construction path for InSituANN. On SIFT-1B, InSituANN builds the IVF index in 5.2 minutes, about 350x faster than the measured 30.4-hour HNSW build. At matched recall on billion-scale datasets, InSituANN improves end-to-end throughput by 104.9x-4298.2x over the PCIe-bound Rummy baseline and by 2.4x-4.6x over DiskANN on SIFT-1B and DEEP-1B. Together with strong recall-throughput trade-offs and lower index space than graph-based alternatives, these gains make billion-scale retrieval practical on cost-efficient hardware.   We open-source InSituANN at https://github.com/mindtravel/InSituANN-OpenSource.

# InSituANN：重新审视IVF以实现PCIe高效十亿级向量搜索——论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **痛点背景**：近似最近邻搜索（ANNS）是推荐系统、语义搜索、RAG等现代检索系统的关键算子。十亿级数据集上，基于图的索引（如HNSW、DiskANN）虽然召回率高，但存在指针追逐导致的内存访问不规则、索引存储开销大、构建/更新成本高等问题。
- **GPU的局限**：GPU虽有强大并行计算能力和高带宽显存，但显存容量有限（单卡通常几十GB），十亿级全精度向量无法完全驻留GPU（如SIFT-1B需512GB float32）。
- **PCIe成为新瓶颈**：在CPU-GPU异构设计中，若将基向量保存在主机内存、把精细搜索卸载到GPU，则需要将候选向量通过PCIe传输到GPU。PCIe带宽（PCIe 5.0 x16约64GB/s）远低于主机DDR5内存带宽（数百GB/s）和GPU显存带宽（TB/s级），导致大量基向量跨PCIe传输成为主导瓶颈。例如取SIFT-1B仅2%的向量（2.56GB）即需至少40–80ms。
- **核心研究问题**：如何在单块商用GPU上实现十亿级向量搜索，避免PCIe基向量传输瓶颈，同时保留IVF索引的简单性和可更新性？

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想：硬件匹配的分阶段放置

- 将IVF搜索按硬件特性拆分：
  - **GPU粗搜索（路由）**：查询-质心距离计算是密集、规则、算力密集型的批量矩阵运算，适合GPU（Tensor Core加速）。
  - **CPU原位精细搜索**：精细搜索是带宽密集型的大规模内存扫描，应在基向量所在的主机DRAM上就地执行（in situ），避免PCIe传输。
- 流水线调度：GPU处理第i+1批路由时，CPU同时处理第i批的精细搜索，隐藏跨设备空闲时间。

### 2.2 InSituANN-Flat路径

- **索引布局**：离线构建IVF索引，基向量按聚类簇主序（list-major）连续存储，每个列表记录偏移、长度和向量ID。
- **查询流程**：
  1. 查询批量上传GPU；
  2. GPU计算查询与质心矩阵的距离（利用公式∥q−c∥²=∥q∥²+∥c∥²−2qᵀc），在设备端完成逐行top-P选择，仅返回选中的列表ID（O(BP)大小的紧凑元数据）；
  3. CPU根据列表ID映射到主机内存连续范围，使用SIMD（AVX-512/FMA）内核扫描并计算精确距离；
  4. 多线程各自维护局部top-K堆，最后合并输出。
- **触达列表调度与查询分块**：多个查询若选中同一列表，该列表只从内存流式读取一次；默认核函数在一次加载中同时与最多4个查询计算距离。

### 2.3 InSituANN-PQ路径（残余PQ候选剪枝）

- **动机**：精确验证在候选量巨大时可能成为延迟瓶颈。
- **残余编码**：对每个基向量x，编码其残余x−c(x)（减去所属质心），残余PQ的动态范围更小、估计更准。
- **GPU侧PQ扫描**：将紧凑的残余PQ码放入GPU空闲显存，GPU按chunk扫描PQ码，用ADC（非对称距离计算）查表累加近似距离，每个chunk保留局部top-K，经chunk→group→查询级层级合并，最终返回有界的手交候选集（budget N_rerank）。
- **精确排序**：最终排名仍基于原始向量的精确距离计算；PQ仅用于候选缩减。
- **PCIe传输量**：从O(被探测向量总数)降为O(B·N_rerank)——仅传输候选ID而非向量数据。
- **Fused-first合并**：将chunk扫描和首层group合并融合，减少中间结果全局内存读写。

### 2.4 索引快速构建

- **子集训练**：在5M样本子集上训练N_list=524,288个IVF质心，而非全量数据。
- **图辅助分配**：仅在质心上构建CAGRA图，加速训练和全量分配阶段的质心搜索；构建后丢弃该图，不保留十亿节点图。
- **超快模式**：进一步减少Lloyd迭代次数和CAGRA搜索预算，同时增大批大小，SIFT-1B仅需5.2分钟完成构建。

## 6. 主要结论与发现

1. **PCIe传输是GPU-centric异构IVF的核心瓶颈**：Rummy需将候选向量传输至GPU计算，而InSituANN原位扫描主机内存向量，将端到端吞吐量提升104.9×–4298.2×（批大小8/32时最为显著）。
2. **PQ作为GPU侧候选缩减层大幅提升吞吐**：InSituANN-PQ在大多数实际召回目标下均优于Flat模式；对Faiss-CPU-IVFPQ提升4.1×–47.8×；对Faiss-CPU-IVFFlat的Flat模式提升1.7×–39.9×。
3. **超越图索引**：在Recall@10≥0.95时，InSituANN-PQ比DiskANN快2.6×–4.6×（SIFT-1B）和3.2×–4.6×（DEEP-1B）；最高比HNSW快14.9×–16.2×。
4. **构建速度极快**：SIFT-1B索引5.2分钟完成，比HNSW约快350×，比DiskANN约快300×；且最终索引不含十亿节点图，存储开销更小。
5. **延迟可预测**：PQ路径通过有界精确重排实现紧凑的延迟分布（毫秒级），而Rummy延迟达秒级（10³ms）。
6. **两种模式互补**：PQ模式在剪枝可靠时最大化吞吐；Flat模式在高召回或稳健性优先时更优（尤其SPACEV-1B上高召回区域）。

## 7. 优点与亮点

- **问题识别精准**：清晰指出PCIe带宽与DRAM/VRAM带宽的数量级差距是异构IVF搜索的根本瓶颈，并有量化数据支撑。
- **设计简洁而优雅**：仅用"GPU做路由+CPU做扫描"这一简单分工就规避了复杂的图结构和数据搬移优化，保留IVF的规则内存访问和更新友好性。
- **层级剪枝体系完整**：粗路由（GPU质心搜索）→ 中剪枝（GPU PQ扫描）→ 精验证（CPU精确距离），每级输出有界，PCIe流量可控。
- **工程优化扎实**：SIMD核函数、列表触达调度、fused-first合并、流水线重叠、前缀扫描分配输出偏移等细节完备，且每项优化都有对应消融验证。
- **实验严谨**：GPU缓存方案的对照实验证明缓存虽有效但无法弥合放置差距；对无法复现的基线如实说明；提供H100可移植性验证。
- **开源**：代码在GitHub公开，利于复现和社区应用。

## 8. 不足与局限

- **PQ适用性有限**：SPACEV-1B上PQ剪枝候选质量下降较早，高召回区Flat更优，说明残余PQ的有效性依赖数据几何特性，非普适最优。
- **高资源环境假设**：1032GB DRAM的两路服务器并非真正的"低成本"环境；虽然基向量驻留内存避免了SSD I/O，但DRAM容量仍是隐含前提（SPACEV-1B需140GB）。
- **HNSW对比配置存在降级**：SPACEV-1B上HNSW仅用M=10、ef=32的降级配置，不能完全代表HNSW在该数据集上的最优水平。
- **部分强基线缺失或未复现**：FusionANNS未纳入（代码不可用），BANG结果无法复现；这两个系统若可比较，可能改变性能排序的某些细节。
- **小批量延迟未充分优化**：Flat路径在批大小8时，CPU核数（64线程）利用率有限，延迟分布在小批量下存在明显上尾（如DEEP-1B、SPACEV-1B批大小32）。
- **更新机制验证范围有限**：更新实验仅覆盖SIFT-1B，未验证其他数据类型或更大更新比例下的行为。
- **未讨论多查询并发/服务级SLA**：评测以批吞吐为主，未覆盖真实服务场景中的延迟SLA、并发查询隔离等指标。
