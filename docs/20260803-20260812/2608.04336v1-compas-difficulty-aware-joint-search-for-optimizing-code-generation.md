## 摘要
代码生成系统在进行每次大语言模型调用时，都会使用一个模型、一个提示和解码设置。然而，现有的优化方法通常只调整这些选择中的一部分，或者对所有任务使用一种固定配置：全局优化器为所有任务搜索一种配置，路由器只选择模型，而提示优化器则保持模型和解码设置固定。这使得它们之间联合的、针对特定分组的交互方式尚不明确。因此，我们考察了这些选择如何交互，并观察到提示与解码设置相互影响，调优效果因模型而异，且最佳配置随任务难度而变化。基于这些观察，我们提出了COMPAS（模型、提示和解码设置上的代码生成优化），这是一种难度感知方法，通过低成本模型选择和联合提示-解码搜索来学习特定分组的质量-成本前沿，然后在线将每个测试任务路由到其匹配的前沿，而无需进一步搜索。在LiveCodeBench上匹配的搜索预算下，COMPAS将pass@1从最佳基线的45.9%提升到52.8%，同时将成本从36.57美元降低到4.92美元。这同样适用于SWE-bench上的仓库级代码生成，解决了76.0%的任务，而最佳基线为70.0%。代码和可复现性工件可在https://github.com/gjz78910/COMPAS获取。

## Abstract
Code generation systems make each LLM call with a model, a prompt, and decoding settings. However, existing optimization methods usually tune only part of these choices or use one fixed configuration for all tasks: global optimizers search one configuration for all tasks, routers choose only a model, and prompt optimizers keep the model and decoding settings fixed. This leaves their joint, group-specific interactions unclear. We therefore examine how these choices interact and observe that prompts and decoding settings interact, tuning effects vary by model, and the best configuration varies by task difficulty. Guided by these observations, we introduce COMPAS (Code-generation Optimization over Models, Prompts, And Decoding Settings), a difficulty-aware method that learns group-specific quality-cost fronts through low-cost model selection and joint prompt-decoding search, then routes each test task to its matching front online without further search. Under a matched search budget on LiveCodeBench, COMPAS improves pass@1 from 45.9% for the best baseline to 52.8% while reducing cost from $36.57 to $4.92. This also transfers to repository-level code generation on SWE-bench, resolving 76.0% of tasks versus 70.0% for the best baseline. Code and the reproducibility artifact are available at https://github.com/gjz78910/COMPAS.

## 1. 论文的核心问题与整体含义（研究动机和背景）

* **背景**：每次 LLM 代码生成调用都涉及三个核心选择——模型（model）、提示（prompt）和解码设置（decoding settings，如温度、top-p、频率惩罚等）。这些选择共同决定了生成代码的质量与成本。
* **现有方法的结构性缺陷**——已有优化方法往往只覆盖了决策空间的一部分：
  * **全局优化器**（如 EcoTune、EcoOptiGen）：为所有任务搜索单一全局配置，忽略了任务之间的难度差异。
  * **路由器**（如 RouteLLM）：只选择模型，固定提示和解码设置。
  * **提示优化器**（如 GEPA）：固定模型和解码设置，只优化提示。
  * 因此，模型、提示、解码设置三者之间的**联合交互**以及**分组特异性的交互模式**尚未被系统研究。
* **核心观察**：通过大规模实证研究，论文识别出三个关键现象：
  * **观察 1**：提示与解码设置之间存在显著交互——单独优化提示或解码分别只能达到 64.3% 和 64.9% 的 Pass@1，而联合优化可达 72.2%。
  * **观察 2**：联合调优的效果是**模型特异性的**——同一调优更新对 DeepSeek-V3 有正效果（76.3%→77.2%），但对 DeepSeek-V3.2 却是负效果（74.0%→72.1%）。
  * **观察 3**：最佳配置随任务难度分组而变化——全局最优配置（53.4%）甚至不如默认配置（54.1%），而按难度分组的最优配置可达 62.4%。
* **整体含义**：代码生成优化问题本质上是一个**按难度分组的联合搜索问题**，而非单一维度的全局调优问题。正确的做法是在有限预算下，为每个难度组寻找模型-提示-解码设置的最优组合，并按需路由。

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

### 核心思想
COMPAS（Code-generation Optimization over Models, Prompts, And Decoding Settings）采用**离线搜索 + 在线路由**的范式，通过轻量级的两阶段搜索构建每个难度组的**质量-成本帕累托前沿**（quality-cost front），在线部署时仅做查找，不进行任何搜索。

### 总体架构（两个阶段）

**第一阶段：离线搜索（Offline Search）**

1. **难度感知分组（Difficulty-Aware Grouping）**
   * 使用 benchmark 自带的官方难度标签将任务分为 Easy、Medium、Hard 三组。
   * LiveCodeBench 使用 Codeforces 风格 Elo 评分（Easy ≤2000，Medium 2000–3000，Hard >3000）；SWE-bench 使用工程师预估修复时间（Easy <15min，Medium 15min–1hr，Hard >1hr）。
   * 在 LiveCodeBench 上额外按任务接口（functional vs stdin）细分，形成难度-类型对。
   * 各组搜索预算按 **1:2:3** 权重分配给 Easy、Medium、Hard，困难组获得更多搜索预算。

2. **阶段 1：快速模型选择（Fast Model Selection）**
   * 在每个分组内，用固定种子配置 (t₀, d₀) 在随机子集 S_g（每组最多 8 个问题）上探测所有候选模型。
   * 通过成本感知规则选择胜出模型：
     * **m\*_g = arg max_{m∈M} [ α_g · d_quality(m) + (1−α_g) · d_cost⁻¹(m) ]**
     * 其中 d_quality 和 d_cost⁻¹ 为在 S_g 上平均通过率和逆成本，经 min-max 归一化。
   * α_g 设置为：Easy=0.2（偏成本）、Medium=0.5（均衡）、Hard=0.8（偏质量）。

3. **阶段 2：联合提示-解码调优（Joint Prompt-Decoding Tuning）**
   * 在选定模型 m\*_g 上，通过 **LLM-based 反射循环**联合变异提示和解码设置。
   * 每个组的任务按 80/20 切分为搜索池和 held-out 池。
   * 每轮：从搜索池随机采样小批量 M_g，评估当前候选 c；LLM 读取**压缩反射上下文**（最多 10 个失败/成功示例、搜索历史、当前前沿、质量-成本指标），提出新候选 c′。
   * **接受准则**：c′ 必须在小批量 M_g 和随机 held-out 批量 H_g 上都通过规则 A_g——不降低分数，且要么修复此前失败的任务、要么在成本上限内降低成本。
   * 接受的 c′ 替换当前候选，若不被前沿支配则加入该组的帕累托前沿 F_g。
   * 搜索空间包括：温度 {0, 0.1, …, 1.0}、top-p {0.05, …, 0.95}、频率惩罚 {−0.5, …, 0.5}（共 8×6×5=240 种解码组合 × 提示候选）。

**第二阶段：在线路由（Online Testing）**

* 每个测试任务 x 先由难度分配器匹配到分组 g(x)，然后从前沿 F_g 中选择使 α_g·quality + (1−α_g)·cost⁻¹ 最大化的配置。
* 纯查找操作，不进行在线搜索；前沿为空时回退到更粗粒度前沿或默认配置。

## 6. 论文的主要结论与发现

* **核心发现**：按任务难度分组、联合优化模型-提示-解码设置，能显著优于全局单配置优化、纯模型路由和纯提示优化方法。
* **LiveCodeBench 主实验（v6-only）**：COMPAS 达到最高 Pass@1 **52.8%**（最佳基线 EcoTune 45.9%），同时成本最低 **$4.92**（对比 EcoTune 的 $36.57，降低 7.4 倍）；统计显著（p=0.0167，A12=0.544）。
* **随机划分**：COMPAS 以 62.2% Pass@1 领先（第二名 PromiseTune 59.6%），成本 $1.09（比第二名低 91.5%）。
* **五种子聚合**：COMPAS 是唯一在 Pass@1 和成本两个维度上均排名第一的方法（Pass@1 51.6%，成本 $11.84）。
* **Per-group 分析**：COMPAS 在 Easy/functional 上高达 97.6% Pass@1，大幅领先所有基线（最高 30.6%）；但 RouteLLM 在 Medium/stdin 和 Hard/stdin 上更好。
* **SWE-bench 泛化**：COMPAS 解决 76.0%（38/50）任务，高于最佳基线 RouteLLM/PromiseTune 的 70.0%；优势主要来自 Medium 组（19/23 vs 17/23）。
* **跨模型族**：Qwen3.5 上 COMPAS 全面领先（40.6% Pass@1、$1.01 成本）；Devstral 上提升有限（27.1% vs EcoTune 的 29.3%），原因是该模型族内两个模型在廉价探针上得分过近导致模型选择失效。
* **消融结论**：每个组件都有贡献；任务分组贡献最大（移除后 Pass@1 降至 39.4%，甚至低于 Default）。
* **敏感性结论**：默认超参数设置整体最优；学习型难度预测器（XGBoost）可逼近官方标签效果，说明方法不严格依赖人工标签。

## 7. 优点

* **维度完整性**：首次系统联合优化模型、提示和解码设置三个维度，弥补了现有方法只优化部分维度的空白。
* **难度感知的细粒度优化**：按任务难度（以及任务类型）分组构建各自的质量-成本前沿，而非全局单配置，更符合实际任务异构性。
* **搜索效率设计巧妙**：
  * 两阶段搜索（先探针选模型、再联合调优）大幅降低搜索空间；
  * 压缩反思上下文控制输入长度；
  * 小批量轮流评估配合随机 held-out 批量，兼顾预算效率和过拟合防护；
  * 引用 Dwork et al. (2015) 的可复用 holdout 理论，避免自适应轮次带来的统计有效性损失。
* **在线零搜索**：部署时仅做前沿查找，无额外推理开销。
* **实验严谨性高**：多基准、多模型族、多种子、消融和敏感性分析全覆盖，统计检验规范。
* **泛化验证扎实**：从函数级（LiveCodeBench）到仓库级（SWE-bench）、从单一模型族到三个模型族的系统验证。
* **开源可复现**：提供代码和可复现性工件。

## 8. 不足与局限

* **模型池规模有限**：每族仅两个模型（一弱一强），未测试跨家族模型选择；作者也承认这是主要局限。
* **对官方难度标签的依赖**：主实验使用 benchmark 自带的难度标签，实际部署中未必可得；虽然 XGBoost-Router 实验显示可学习近似（49.7% vs 52.8%），但仍存在 3.1 个百分点的差距（统计不显著但绝对值存在）。
* **特定 benchmark 限制**：SWE-bench 使用 Verified-mini 子集（50 任务），结果不可与完整 leaderboard 直接比较。
* **成本并非总是最低**：SWE-bench 上 COMPAS 成本（$37.37）高于 RouteLLM（$8.82），原因是路由到更贵的强模型；成本优势在仓库级任务上不如函数级任务显著。
* **Devstral 上的局限暴露了探针风险**：当族内模型能力差距过小时，廉价模型探针无法可靠区分，导致次优模型选择。
* **部分组别效果不佳**：在 Medium/stdin 和 Hard/stdin 上不如 RouteLLM 的按难度模型路由；Hard 任务在所有方法上解决率都很低（SWE-bench 上最多 2/8），说明 Hard 组的优化空间仍然巨大。
* **超参敏感性**：预算加倍到 2M tokens 反而导致性能下降（46.6%），表明存在过拟合风险，默认预算的选取依赖经验校准。
* **未报告推断延迟**：成本以美元计，但未讨论在线路由的延迟开销（虽然查找本身是 O(1) 的）。
