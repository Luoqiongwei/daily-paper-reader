## 摘要
大型语言模型（LLM）在代码生成方面取得了显著进展，但在需要复杂算法或复杂实现的任务上仍然存在困难。近期方法越来越多地使用代码执行作为反馈，尤其是在从生成的代码构建验证信号的自修正流程中。然而，这些流程通常依赖于可靠性未知的监督信号，这可能会引入误导性反馈、不必要的修订以及错误的最终答案。为解决此问题，我们提出了ExeCRE，一种执行一致性引导的代码可靠性估计框架。ExeCRE不通过测试或LLM反馈来评判候选代码，而是通过在大量随机生成的输入上对执行输出的一致性模式进行统计分析来估计代码可靠性。它收集生成输入上的执行输出，将其投影为一致性信号，并应用Dawid-Skene模型推断潜在代码可靠性。我们将ExeCRE集成到代码生成的自修正中。实验表明，ExeCRE持续提升了有效性和稳定性，同时大幅减少了误导性修正信号。在LiveCodeBench上使用GPT-5.2时，原本正确的代码上平均误导性反馈案例数从代表性自修正基线的113.2降至ExeCRE的14.0。作为额外研究，我们将相同的可靠性估计策略应用于基于代码的数学推理，并观察到类似的好处。这些结果表明，ExeCRE能够在基于执行的流程中更可靠地使用生成的代码。

## Abstract
Large language models (LLMs) have made notable progress in code generation, but they still struggle on challenging tasks that require sophisticated algorithms or complex implementations. Recent methods increasingly use code execution as feedback, especially in self-correction pipelines that construct verification signals from generated code. However, these pipelines often depend on supervision signals whose reliability is unknown, which can introduce misleading feedback, unnecessary revisions, and incorrect final answers. To address this issue, we propose ExeCRE, an Execution-Consistency guided code Reliability Estimation framework. Instead of judging candidate code by tests or LLM feedback, ExeCRE estimates code reliability by statistically analyzing consistency patterns in execution outputs over a large number of randomly generated inputs. It collects execution outputs over generated inputs, projects them into consistency signals, and applies the Dawid-Skene model to infer latent code reliability. We integrate ExeCRE into self-correction for code generation. Experiments show that ExeCRE consistently improves both effectiveness and stability, while substantially reducing misleading correction signals. Under GPT-5.2 on LiveCodeBench, the average number of misleading feedback cases on already correct code drops from 113.2 with a representative self-correction baseline to 14.0 with ExeCRE. As an additional study, we apply the same reliability estimation strategy to code-based mathematical reasoning and observe similar benefits. These results suggest that ExeCRE enables more reliable use of generated code in execution-based pipelines.

- **背景**：大语言模型（LLM）在基础代码生成任务上表现优异，但在需要复杂算法或精细实现的竞赛级编程问题上仍力有不逮。近年主流解决方案是"自修正"（self-correction）范式：模型迭代生成代码，并利用基于执行（execution）的反馈信号（如测试用例）来判断是否需要修订及如何修订。
- **核心痛点**：自修正流程高度依赖验证信号（verification signals），但现有信号质量未经验证、可靠性未知——
  - 参考代码（reference code）本身可能含有隐蔽 bug、只覆盖部分情况，或在复杂输入上相互冲突；
  - 用 LLM 作为"裁判"来判断代码正确性，判断本身不可靠；
  - 不可靠的监督信号会误导自修正过程：正确的代码被无谓修改（misleading feedback），错误的代码反而被强化，最终形成级联错误。
- **核心问题**：如何在将参考代码用作验证信号之前，量化其可靠性，从而过滤掉不可靠的监督？
- **整体含义**：论文提出 ExeCRE（Execution-Consistency guided code **R**eliability **E**stimation），不依赖测试或 LLM 主观评判，而是通过在大规模随机输入上统计代码执行输出的一致性模式，利用经典的 Dawid–Skene 模型推断参考代码的潜在可靠性，以此做"可靠性感知的代码选择"。该框架旨在让基于执行的代码生成管道（自修正、数学推理）更可信、更稳定。

## 2. 论文提出的方法论

### 2.1 核心思想

将"代码可靠性估计"类比于众包标注中的"标注者质量估计"：
- **输入** = 待标注的样本（item）；
- **候选代码** = 标注者（annotator）；
- **执行输出** = 标注结果；
- 利用多个代码在同一批输入上的执行一致性，推断每个代码的潜在错误率与每条输入的真实一致性状态，进而得到每个代码的可靠性分数 α_j ∈ [0,1]。

### 2.2 三大阶段

1. **Schema 驱动的测试输入生成（Input Construction）**
   - 用一个 LLM prompt 从问题描述中抽取结构化输入 schema（JSON 格式），包含输入格式、变量类型、取值范围、变量间依赖关系。
   - 从 schema 构建变量依赖图，按拓扑序依次实例化变量（如 l_i 生成后再生成 r_i，因 r_i ∈ [l_i, 10^9]）。
   - 对 List/Group/Matrix 尺寸上限设为 20，以控制执行开销；若 schema 解析失败或 >10% 执行失败则丢弃并重试（最多 3 次）。
   - 相比先前依赖 LLM 重复生成测试或用少量参数解析的方法，本方案只用一次 LLM 调用、覆盖 stdin 与函数式两种输入形式、可生成约 300 × 5 = 1500 规模的多样有效输入。

2. **执行一致性投影 + Dawid–Skene 可靠性估计**
   - 构建执行输出矩阵 O = [O_ij]（第 i 个输入、第 j 个代码的执行输出；执行失败记为 NaN）。
   - 由于原始输出空间可能超过输入数量，直接套用 DS 不可行，论文将原始输出**投影为二元一致性信号** U_ij：
     U_ij = 1[O_ij 等于该输入下多数代码的输出]（NaN 保留缺失）。
   - 引入潜在一致性状态 T_iq（该输入更可能属于哪一侧）、类先验 p_q、以及每个代码的错误率矩阵 π^(j)_qa（潜在真实状态为 q 时观察到 a 的概率）。
   - 使用 EM 算法迭代优化观测数据的似然：
     - **E-step**：计算后验 T̂_iq；
     - **M-step**：闭式更新 p_q 和 π^(j)_qa；
   - 最终可靠性分数：**α_j = p̂₁·π̂^(j)₁₁ + p̂₀·π̂^(j)₀₀**，即代码输出与潜在一致性状态相符的期望概率。

3. **阈值筛选与自修正集成**
   - 仅当最高分 α* ≥ τ（默认 0.95）时，才选出最可靠参考代码（brute-force 实现），在其上生成小型测试对（约 2000 个用例，单线程 1 分钟内执行完），用于引导基于测试的自修正（参照 TextGrad 流水线，但避免直接使用 LLM 文本判断）。
   - 若没有候选达到阈值，则**回退（fallback）**到仅用公开测试，防止不可靠参考代码污染修正过程。

## 6. 论文的主要结论与发现

1. **主性能**：ExeCRE 在四个模型上均取得最佳 Pass@1（GPT-5.2：72.8 vs TextGrad 69.9；DeepSeek-V3.2：55.4 vs 52.6；Qwen-32B：32.5 vs 31.5；LLaMA-8B：21.0 vs 19.4），提升集中在 Medium/Hard 难题。
2. **误导反馈大幅减少**：对"本已正确"代码产生的误导信号数，GPT-5.2 上从 TextGrad 的 113.2 降至 14.0，DeepSeek-V3.2 从 81.2 降至 11.6，Qwen 从 50.4 降至 7.4，LLaMA

从 8.3 降至约 4.1，且修正后正确代码被改错的比率显著下降。这直接验证了“可靠性估计→过滤不可靠监督”的核心机制有效性。

3. **可靠性识别能力**：在识别“哪个候选代码最可靠”的任务上，ExeCRE（DS 版）的 F1 分数显著高于 Random、LLM Judge、LLM Analyze、CodeJudge、SLM Judge 及简单投票版本；尤其在 Hard 题目上优势更大。即便在候选代码全部含错的极端情况下，ExeCRE 也能通过一致性状态推断出相对更可信的候选，而非盲目信任多数。
4. **阈值与回退机制**：τ = 0.95 时性能最优；提高阈值会更多触发回退（仅用公开测试），但不会显著损害性能；降低阈值则会引入不可靠参考代码，导致 Pass@1 下降。回退机制有效防止了低可靠性监督对自修正过程的污染。
5. **输入构造消融**：Schema 驱动的输入生成在覆盖率和有效性上优于 Oracle-Guided Fuzzing 和 CodeT 的 LLM 生成输入，且仅需一次 LLM 调用，成本更低；在函数式接口问题上，Schema 方法也能直接适用。
6. **跨任务迁移**：在 GSM8K PoT 设置下，用 ExeCRE 选出的“可靠参考代码”作为 few-shot 示例，能显著提升数学推理准确率（如 Qwen2.5-Coder-32B 从 83.5% 提升至 86.2%），说明可靠性估计不限于代码生成竞赛题，对代码型数学推理同样有效。
7. **效率与可扩展性**：ExeCRE 的额外开销主要体现在代码执行（证据收集），而 Dawid–Skene 推断本身 <3 秒；多线程 + batch API 下每次运行约 26 秒，远低于 LLM 自修正的迭代成本，适合作为自修正流水线的前置筛选模块。

## 7. 论文的学术贡献与局限性

### 7.1 学术贡献

- **问题视角新颖**：将“参考代码可靠性”从传统的“测试通过率”或“LLM 主观评判”中解放出来，建模为众包标注中的标注者质量估计问题，给出了无需测试 oracle 的通用可靠性度量。
- **方法简洁、理论可解释**：基于 Dawid–Skene 模型的 EM 推断，既有概率论支撑，又避免了训练额外判别模型（如 SLM Judge）所需的数据标注成本。
- **工程可落地**：Schema 驱动的输入生成 + 执行一致性投影 + 阈值回退，三者组合成一个完整的“先评估参考代码、再决定是否用其引导自修正”的流水线，对现有执行型自修正框架（TextGrad、CodeT 等）可即插即用。
- **实验严谨性较好**：覆盖多模型、多难度、多 baseline，并专门做了 cutoff-clean 模型验证；对“误导反馈”的量化分析直接支撑了核心动机。

### 7.2 局限性

- **依赖输入分布的合理性**：执行一致性假设“真实一致性状态存在且可被多数代码揭示”。若多数候选代码共享同一系统性偏差（如都用了相同错误算法），则一致性状态本身可能是“一致地错”，DS 模型无法识别；论文通过 10 个多样候选和随机输入缓解，但无法根除。
- **二元投影的信息损失**：将执行输出压缩为“是否等于多数输出”，丢弃了输出间更细粒度的相似性（如数值接近、结构相同但顺序不同），可能降低可靠性估计的分辨率。
- **阈值选择依赖经验**：默认 0.95 虽经敏感性分析验证，但不同任务/数据集上最优阈值可能变化，论文未给出自适应阈值方法。
- **评估范围仍有限**：主实验仅覆盖编程竞赛题（LiveCodeBench）和数学应用题（GSM8K），未涉及代码补全、代码翻译、仓库级代码生成等更实际场景；GSM8K 上仅用 2 个小模型，外推需谨慎。
- **未公开硬件与训练细节**：由于方法零训练，GPU 资源可忽略，但论文未报告运行环境的 CPU/内存/并行度，复现时需自行摸索。

## 8. 个人评价与后续研究方向

### 8.1 总体评价

ExeCRE 是一篇思路清晰、实验扎实的可靠代码生成方法论论文。它的核心亮点在于**用统计推断替代主观判断**，以极低额外成本为自修正流水线提供了可量化的信任锚点。相比同期的 LLM-as-a-Judge、微调判别器等方法，ExeCRE 在数据效率、可解释性和无需人工标注三方面有明显优势。论文在“误导反馈减少”这一维度上的定量分析尤其有价值——它把自修正失败的根源从“模型笨”转译为“监督噪声大”，并给出了系统性的过滤方案。

### 8.2 可能的改进方向

1. **多值投影**：将二元一致性扩展为多簇（如按输出类型/数值区间聚类），保留更多执行信息，提高可靠性估计精度。
2. **自适应阈值**：根据候选代码间的分歧度、输入规模、题目难度动态调整 τ，避免固定阈值在不同分布上的失效。
3. **与测试生成联合优化**：将 Schema 输入生成与候选代码生成交替迭代，用前一轮执行结果引导下一轮输入更偏向难例（类似主动学习），提升样本效率。
4. **扩展到更广代码场景**：在代码补全、缺陷修复、单元测试生成等任务上验证 ExeCRE 的通用性，并考虑与静态分析工具结合。
5. **理论分析**：给出 DS 模型在“多数一致但全体错误”场景下的失败界，以及输入数量 N 与候选数 M 对可靠性估计误差的影响，使方法有更强理论保证。
