## 摘要
从自然语言Bug报告中复现Web GUI Bug对于软件维护至关重要，但由于报告通常缺少依赖和输入文件等前提条件，这仍然很困难。现有的Bug复现技术主要针对代码单元或移动应用，缺乏对Web GUI的端到端可视化执行和验证。我们提出了ReBug，一种上下文感知的智能体系统，通过驱动真实浏览器，从Web GUI Bug报告中重构、执行和验证浏览器级别的复现过程。ReBug将复现分为两个阶段。在准备阶段，ReBug从报告和可用工件中重构缺失的前提条件，并生成高层复现计划。在执行阶段，它在浏览器中执行工具介导的交互，维护页面状态和动作历史的结构化摘要，并根据报告得出的期望验证最终状态。我们在来自四个开源Web应用的667个真实Bug报告上评估了ReBug。在受控的当前部署中，ReBug优于两个基线，实现了平均RSR为49.96%，平均任务完成率为74.96%，平均动作执行成功率为86.54%。我们的结果表明，显式的上下文重构和状态感知的浏览器执行有效地支持了源自报告的浏览器复现，而历史回放显示，成功的复现过程通常会在恢复的缺陷版本上暴露原始含Bug的行为。

## Abstract
Reproducing web GUI bugs from natural-language bug reports is critical for software maintenance, but remains difficult because reports often lack prerequisites such as dependencies and input files. Existing bug reproduction techniques mainly target code units or mobile applications and lack end-to-end visual execution and validation for web GUIs. We present ReBug, a context-aware agent system that reconstructs, executes, and validates browser-level reproduction procedures from web GUI bug reports by driving a real browser. ReBug separates reproduction into two stages. In the preparation stage, ReBug reconstructs missing prerequisites from the report and available artifacts, and it produces a high-level reproduction plan. In the execution stage, it performs tool-mediated interactions in the browser, maintains structured summaries of page state and action history, and validates the final state against expectations derived from the report. We evaluate ReBug on 667 real-world bug reports from four open-source web applications. On controlled current deployments, ReBug outperforms both baselines, achieving an average RSR of 49.96%, a mean task completion rate of 74.96%, and a mean action execution success rate of 86.54%. Our results show that explicit context reconstruction and state-aware browser execution effectively support report-derived browser reproduction, while historical replay shows that successful procedures often expose the original bug-present behavior on restored buggy versions.

## 2. 论文提出的方法论

**核心思想**：将 Web GUI Bug 复现拆分为“准备”和“执行”两个阶段，显式处理上下文重建、状态感知浏览器交互和基于报告的最终状态验证。

**两阶段架构：**

### （1）准备阶段

**Context Builder（上下文构建器）**：

- **Phase 1 评估**：判断报告是否需要可物化的本地前提条件（文件、图片、文档、配置片段、表格数据等），排除部署级条件（安装应用、切换版本、重建数据库等）。输出前提摘要，记录工件类型、来源、可行性、本地路径或失败原因。
- **Phase 2 迭代物化**：以“构建-检查-精化”循环增量式准备所需上下文。由 Context Building Agent 基于 Bug 报告、前提摘要和已备工件推理具体操作，通过 System Executor 在沙箱工作区内执行白名单内的本地工件操作（创建/编辑文件、复用白名单文件、下载报告关联资源、验证文件、暂存上传文件等）。维护工件清单和动作历史以保证可追溯性和复用性。

**Plan Generator（计划生成器）**：从 Bug 报告和已备上下文中生成高层意图步骤的有序序列，作为执行过程的进度脚手架而非固定脚本。

**Browser Initialization（浏览器初始化）**：启动全新浏览器会话，编码运行时信号（URL、标题、标签页状态、导航状态、对话框、错误、超时等），如有指定入口 URL 则导航至该页面，否则默认从应用主页开始。

### （2）执行阶段

**执行循环**：

- **信息更新模块**：捕获当前页面截图和结构化 DOM 表示；
- **Browser-Info Update**：将原始观察转换为紧凑的浏览器可观察记录，写入 Information Center（结构化执行时记忆，存储智能体状态、上下文摘要、消息历史、动作结果、浏览器状态历史、复现统计）；
- **Historical Filtering**：仅暴露最新浏览器状态作为决策依据，防止过期页面观察被误用；
- **Action Generator**：基于最新页面信息、剩余计划和高层计划步骤索引，生成结构化 JSON 动作（导航、点击、文本输入、键盘输入、滚动、悬停、下拉选择、文件上传、等待、任务终止），动作通过类型化模式校验，仅能引用当前浏览器状态中暴露的可交互元素索引；
- **Plan List Update**：跟踪计划进度。
- **失败控制与预算**：设置最大执行步数（20）、连续失败上限（3）、单动作超时（120秒），超过阈值后强制进入仅允许终止的最终步骤。
- **轨迹与统计收集**：记录截图、URL、动作、结果、步骤元数据为结构化 Reproduction Report，并在线更新复现统计。

**评估阶段**：

- 汇总最终浏览器可观察状态（当前 URL、可见元素结构化视图、截图、累积证据）；
- 从报告中推导结果预言（捕获失败症状或预期可观察行为）；
- 基于 LLM 的评估器对照预期/非预期描述检查最终证据，输出二元复现决策及理由；
- 成功条件：到达计划终止状态 + 满足预期描述 + 不满足非预期描述。

## 6. 论文的主要结论与发现

1. **有效性（RQ1）**：ReBug 在 667 份真实 Bug 报告上平均 **RSR 达 49.96%**，TCR 均值 74.96%，AESR 均值 86.54%。项目间 RSR 范围 45.79%（Ghost）至 52.60%（n8n）。
2. **基线对比**：ReBug 比 Browser-use 高出 10.21%-17.31 个百分点；直接脚本生成基线表现极差（1.34%-4.82%），表明单次自然语言转脚本远不足以处理真实 Bug 报告。不同 LLM 骨干间性能差距较小（RSR 范围 45.79%-54.55%），说明系统设计比模型选择更具决定性影响。
3. **历史回放**：40 个成功案例中 **39 个（97.5%）** 在恢复的 Buggy 版本上触发了报告描述的 Bug 行为（唯一失败案例因缺失特定主题而无法观察症状），证明当前部署上验证成功的流程具有真实复现意义。
4. **消融（RQ2）**：移除 Context Builder 使 RSR 下降 6.63%-11.29%；移除 Plan Generator 仅导致 0.45%-2.31% 的轻微下降——说明初始高层计划主要起进度跟踪稳定作用，真正核心能力来自状态感知的在线执行与前提重建。但“需要额外上下文的报告比例”（29.30%-51.03%）远高于移除后的性能跌幅，原因是部分前提可通过在线交互（如注册账号、应用内准备数据）弥补。
5. **失败分析（RQ3）**：**元素定位/交互阻塞是首要瓶颈**，占所有失败标签的 60.47%-73.91%。次要失败包括文件/数据/配置前提缺失、预算超限和报告歧义，反映了前提恢复和环境感知执行的重要性。

## 7. 优点

- **针对真实痛点的系统设计**：明确识别 Web GUI Bug 复现的三大特有挑战（上下文补全、状态感知执行、结果验证），将移动端和代码级方法无法覆盖的浏览器可观察证据（DOM 状态、URL、截图、异步更新）系统化集成到复现流程中。
- **两阶段分离的清晰架构**：准备阶段和执行阶段职责分明，准备阶段重现场景前提，执行阶段专注于动态浏览器交互，模块间通过 Information Center 结构化共享记忆。
- **上下文重建机制**：白名单机制、迭代“构建-检查-精化”循环、工件清单和动作历史的设计具有工程实用性，可追溯、可调试、可复用。
- **严格且可解释的评估框架**：RSR 采用“到达完成状态 + 满足预期 + 不满足非预期”的严格条件，支持自动化批量评估；历史回放设计为成功流程提供真实失败触发的语义验证。
- **全面的多维度实验**：方法对比、骨干模型敏感性、组件消融、失败分类分析构成了较完整的证据链，失败标签分类法细粒度高且有人工双编码保障。
- **高可复现性**：提供了包含实现、提示模板、结构化输出模式、评估者规则、工具规范和代表性轨迹的匿名工件仓库。

## 8. 不足与局限

- **复现成功率仍有较大提升空间**：平均 RSR 仅约 50%，意味着约半数真实 Bug 报告无法在此框架下被成功复现，尚不足以支撑大规模工业应用。
- **元素定位仍是核心瓶颈**：动态 UI 更新、遮挡层、隐藏或过期元素导致 60%-74% 的失败，表明当前基于 DOM 快照+截图的元素索引策略对复杂 Web 组件的适应性不足。
- **评估部署局限**：主实验在受控的“当前部署”上进行，由于没有为每份报告重建历史 Buggy 版本，RSR 衡量的是“程序性完成+状态一致性”而非真实 Bug 触发；评估部署与原始报告环境的差异可能引入不确定因素。
- **数据集选择偏差**：Stage 2 过滤排除了安装/构建缺陷、专用基础设施、版本锁定和非 GUI 故障等类别，导致 benchmark 偏向可复现案例；仅选择四个高星级项目，可能无法推广到高度动态、领域特定或快速演进的 Web 应用。
- **历史回放的选择偏差**：仅从成功的当前部署运行中采样，未对失败案例进行历史版本验证，无法排除部分失败运行实际上也可能触发真实 Bug 的可能性。
- **消融实验粒度不足**：Plan Generator 消融仅报告 RSR，缺少对 TCR 和成本的影响分析；“某些前提可通过在线交互弥补”的解释缺乏定量验证。
- **未见多智能体协作与可扩展性讨论**：上下文构建代理与动作生成代理之间的协调复杂度、面对大规模项目时的扩展性以及对非英语报告的处理能力未进行深入研究。
- **LLM 概率性本质**：ReBug 依赖 LLM 的非确定性输出，虽然通过多次尝试和批量评估缓解，但单次运行的稳定性仍受提示词设计和模型版本影响。
