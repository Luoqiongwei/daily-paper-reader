## 摘要
基于LLM的仓库级代码生成旨在利用软件仓库中的上下文生成代码，要求LLM能够推理复杂的代码依赖关系。由于有限的上下文窗口和不足的仓库特定理解，LLM通常依赖检索增强生成（RAG）来整合相关代码。早期的RAG方法主要采用基于相似度的检索，这往往无法检索到目标函数所依赖的代码片段。近期的工作引入了基于图的检索来建模此类依赖，但通常依赖人工设计的规则和静态全局图，导致灵活性有限且构建与维护成本高昂。相比之下，人类开发者通过隐式构建部分依赖图并沿其迭代检查来收集有用上下文。受此行为启发，我们提出了DyRetriever，一种通过部分依赖图进行高效上下文检索的方法。DyRetriever使用LLM首先选择一组入口点函数，然后沿代码依赖图进行多跳推理。在多跳推理过程中，它利用LLM的语义理解来验证某个函数是否有助于生成目标函数，从而消除了人工设计的规则，并实现了跨场景的灵活性。DyRetriever并非静态构建全局依赖图，而是按需构建部分图并在使用后丢弃，从而降低了构建和维护成本。我们将DyRetriever与基于相似度的代码检索器集成，构建了DyCoder，并在CoderEval和DevEval上对其进行了评估。实验结果显示，与现有基于RAG的方法相比，DyCoder在CoderEval和DevEval上的Pass@1相对改进分别达到25.63%和59.73%，同时比基于静态依赖图构建的基线方法快7.4倍。

## Abstract
LLM-based repository-level code generation aims to generate code using the context available in a software repository, requiring LLMs to reason over complex code dependencies. Due to limited context windows and insufficient repository-specific understanding, LLMs typically rely on retrieval-augmented generation (RAG) to incorporate relevant code. Early RAG approaches primarily employ similarity-based retrieval, which often fails to retrieve code snippets that the target function depends on. Recent work introduces graph-based retrieval to model such dependencies, but typically relies on manually designed rules and static global graphs, leading to limited flexibility and high construction and maintenance costs. In contrast, human developers collect helpful context by implicitly constructing a partial dependency graph and iteratively inspecting along it. Inspired by this behavior, we propose DyRetriever, an efficient context retrieval method via partial dependency graphs. DyRetriever uses an LLM to first select a set of entry-point functions and then perform multi-hop reasoning along the code dependency graph. During multi-hop reasoning, it uses the LLM's semantic understanding to validate whether a function can help generate the target function, eliminating manually designed rules and enabling flexibility across scenarios. Instead of statically constructing a global dependency graph, DyRetriever builds a partial graph on demand and discards it after use, reducing construction and maintenance costs. We integrate DyRetriever with a similarity-based code retriever to build DyCoder and evaluate it on CoderEval and DevEval. Experimental results show that DyCoder achieves relative Pass@1 improvements of 25.63% and 59.73% on CoderEval and DevEval, respectively, compared with existing RAG-based methods, while being 7.4x faster than baselines based on static dependency graph construction.

### 研究背景
- **仓库级代码生成（Repository-Level Code Generation）** 是近年来备受关注的研究方向，要求 LLM 根据给定的目标函数签名（含 docstring）和仓库内可用上下文，在真实软件仓库中生成完整的函数实现。
- 与单函数代码生成不同，仓库级代码生成中的目标函数通常与仓库内的其他代码存在复杂的调用、导入等依赖关系，因此 LLM 需要理解并推理仓库中错综复杂的代码依赖。

### 核心问题
- **上下文窗口有限**：LLM 无法一次性读取整个仓库。
- **缺乏仓库特定知识**：LLM 对具体仓库的代码结构、依赖关系不甚了解。
- **现有 RAG 检索方法的缺陷**：
  - **基于相似度的检索**（如 BM25、密集检索）：只能找到与目标函数"外观相似"的代码，容易遗漏目标函数实际依赖但形态不相似的代码片段。
  - **基于图的检索**（如 RepoScope、GraphCoder）：依赖人工设计的固定规则（如导入关系遍历、相似度度量），灵活性差，难以适应多样化的上下文需求；同时需要静态构建**全局依赖图**，构建耗时长、维护成本高。

### 核心洞察
- 人类开发者在收集上下文时，并非依赖预定义规则或全局依赖图，而是：
  1. 先凭对任务和仓库的理解，选择少量**入口函数**；
  2. 沿依赖链**多跳迭代**地探索相关函数，动态判断每个函数是否对实现目标函数有帮助；
  3. 在此过程中**隐式构建并即用即弃部分依赖图**。
- 论文核心含义：通过用 LLM 模拟人类开发者的这种上下文收集行为，可以在**不依赖人工规则**、**不构建全局图**的前提下，实现既有效又高效的仓库级上下文检索。

## 2. 提出的方法论

### 总体框架：DyCoder
- 由三个主要阶段组成（如图 2 所示）：
  1. **图基上下文收集阶段（DyRetriever）**：模拟人类行为，基于部分依赖图收集语义相关上下文。
  2. **相似度上下文检索阶段**：基于嵌入模型检索与目标函数签名最相似的函数。
  3. **生成阶段**：将两类上下文去重合并后，通过提示工程让 LLM 生成目标函数实现。

### 核心技术：DyRetriever（部分依赖图检索器）

#### （1）入口点选择阶段（Entry Points Selection）
- 将仓库解析为**树形结构**（按文件夹层级组织），避免 LLM 直接读取整个仓库超出上下文窗口。
- 依据树形结构 + 目标函数签名，让 LLM 返回与目标函数相关的文件列表（相关文件列表）。
- **强制补充**目标函数所在文件，以确保同时覆盖文件内（in-file）上下文和跨文件（cross-file）上下文。
- 从相关文件中提取所有函数，构造"文件路径 → 函数名列表"映射，再让 LLM 从中挑选若干函数作为**入口点**。

#### （2）多跳推理与部分图构建阶段（Multi-hop Reasoning with Partial Graphs）
- 核心算法（Algorithm 1）包含三个迭代步骤：
  - **Select（选择）**：利用 LLM，根据目标函数签名、候选函数集合和已访问轨迹，从候选中选择一个最相关的函数。
  - **Visit（访问）**：获取选中函数的源代码；若已访问则跳过；记录访问轨迹。
  - **Expand（扩展）**：提取该函数所在文件的所有 import 语句，结合函数源代码，让 LLM 识别其依赖的下游函数（callees 和 lazy imports），将识别出的依赖加入候选集合，从而**动态扩展部分依赖图**。
- 设置最大跳数（maxHop=10）作为全局探索预算。
- 遍历结束后，基于访问轨迹让 LLM 挑选与目标函数最相关的 top-k 函数作为检索结果。

#### （3）后处理（减少幻觉）
- LLM 可能虚构不存在的函数，或错误地将标准库 API（如 `re` 库的 `match`）识别为跨文件依赖。
- 后处理策略：对 LLM 识别出的每个依赖函数，在仓库中按函数名匹配查找对应实现；找不到实现则丢弃该依赖。这显著提高了依赖图的可靠性。

### 关键设计特点
- **无规则依赖**：完全依赖 LLM 的语义理解来判断"某个函数是否有助于生成目标函数"，突破了人工规则的局限。
- **按需构建部分图**：只构建探索路径上的局部依赖关系，用完即弃，避免了全局依赖图的构建与维护开销。
- **LLM 动态构图**：由于现有静态分析工具不支持高效构建部分依赖图，论文直接利用 LLM 从函数源码和 import 语句中识别依赖关系。

## 7. 局限性分析

### 方法自身局限
1. **依赖 LLM 作为构图器的可靠性**：
   - DyRetriever 的依赖图构建完全依赖 LLM 的函数名理解和源码推理能力；尽管后处理过滤了仓库内不存在的幻觉函数，但 LLM 仍可能将某个真实存在的函数误判为目标依赖，或遗漏实际依赖关系。手工抽查的 93.22% 准确率虽高，但样本量小，真实场景中的错误率可能更高。
   - 对于幻觉的**标准库/第三方库函数**（如 `os.path.join`），后处理策略无法发挥作用——因为无法在仓库内找到其实现，但这并不意味着该依赖无用。论文选择直接丢弃这些外部依赖，可能会导致 LLM 在生成时缺少对标准库 API 使用方式的参考（尽管标准库本身通常已在预训练语料中充分覆盖）。

2. **入口点选择的误差传播**：
   - 入口点选择阶段完全依赖 LLM 对仓库树形结构和目标签名的理解，若 LLM 在此阶段遗漏了关键文件，后续多跳推理将无法触及该文件中的有效依赖，且该遗漏无法在后续阶段被纠正。论文没有提供针对入口点选择准确率的单独评估。

3. **多跳推理的"迷雾"问题**：
   - 随着跳数增加，候选集合可能发散，LLM 在高跳数时可能偏离目标函数的核心需求，收集到过多无关上下文。最大跳数（maxHop=10）是人工设定的经验值，论文未对不同 maxHop 值进行敏感性分析。

4. **上下文长度的隐性膨胀**：
   - 虽然单次生成仅消耗约 13k tokens，远低于现代 LLM 的上下文窗口，但多跳探索过程中每一步都需要向 LLM 发送候选函数列表和轨迹信息，累计的 API 调用开销并未完全反映在最终生成的 token 统计中。论文仅报告了最终生成阶段的 token 数和美元成本，未明确拆分为检索阶段和生成阶段各自的成本。

### 实验设计与评估局限
1. **评估基准的覆盖盲区**：
   - DevEval 中 209 个实例（约 11.5%）因无沙盒评估环境被全部视为失败，如果这些实例恰好集中在某些方法表现较好或较差的类别上，可能会系统性影响对比结论。
   - 两个基准都是 Python 为主，未覆盖 Java、TypeScript 等其他语言，仓库级依赖推理在不同语言上的表现可能差异显著（例如动态类型语言的依赖关系更隐蔽）。

2. **Pass@1 的单一性**：
   - 论文只报告了 Pass@1，未使用 Pass@k（k>1）或多路采样的 pass 率。由于采用贪心解码（temperature=0），Pass@1 可能低估了模型在随机采样下的真实能力上限。

3. **效率评估的粒度**：
   - 时间成本在 CPU 上以串行方式执行，未考虑并行化条件下的实际运行时间；且只对 CoderEval 进行了效率评估，CoderEval 的仓库规模（平均数百个文件）无法代表真实工业级巨型仓库（数万文件）下的扩展性。

## 8. 个人评价与思考

### 核心贡献的学术价值
- **首次将"人类开发者视角的上下文收集行为"形式化为可计算的检索范式**。已有研究表明，人类程序员在 IDE 中通常通过点击跳转到函数定义、沿调用链浏览来获取信息，而不是全库扫描。DyCoder 将这一行为建模为"入口点选择 → 多跳依赖扩展 → 即时修剪"的算法过程，为上下文检索提供了一个新的范式分支。
- **证明了"规则自由"可以优于"规则丰富"**。RepoScope 等图方法投入大量精力设计静态图结构和遍历规则，但 DyCoder 仅依靠 LLM 的语义理解即可超越它们，且速度快 7 倍以上。这一结果对"构建更复杂图结构"的技术路线提出了质疑，暗示 LLM 的隐式知识可能足够支撑高效部分图构建。
- **组件的即插即用设计**：DyRetriever 不对外部检索器做任何假设，可灵活替换相似度组件，降低了该方法的集成门槛。

### 技术疑点与改进方向
- **LLM 构图的可控性**：DyRetriever 本质上将"构图"任务委托给了 LLM，这引入了不确定性。论文的缓解手段（后处理过滤）较为粗糙——完全丢弃仓库内无法匹配的函数。更合理的方式可能是：将仓库内匹配到的函数源码作为"证据"返回给生成器，而将外部库依赖以"黑盒 API 名称 + 参数"的形式传递给生成器，而不是一刀切丢弃。
- **入口点选择的交互式细化**：当前入口点选择是一次性的，可以增加一个验证环节——让 LLM 对选出的入口点与目标签名的相关性打置信分，低置信度则重新选择。这样可以降低误差传播风险。
- **成本优化空间**：多跳迭代中，候选人集合动态增长可能导致重复"考虑"无关函数。可引入轻量的预先筛选（例如首先用 BM25 粗筛一遍候选集，再进行 LLM 细选），减少 LLM 调用次数。

### 对社会/产业的意义
- 在 AI 编程助手（如 Copilot、Cursor 等）中，上下文工程的实际效果往往优于模型参数的增大。DyCoder 的最优结果（CoderEval 51.04、DevEval 47.25）是在 **30B/小型闭源模型**（GPT-4o-mini）级别取得的，说明上下文质量可以显著弥补模型规模劣势。这对资源受限的团队尤其有吸引力。
- 零训练部署特性使得它可以直接集成到现有 IDE 插件中，无需收集仓库级训练数据或额外微调，对快速迭代的商业产品有较强的实用价值。

### 开放式思考
1. **"动态部分图"的边界在哪里？** 当仓库规模达到百万函数级别时，即使只做"部分探索"，探索路径上的候选集合也可能膨胀到超出模型上下文的能力。是否需要引入"图剪枝"的硬约束（如基于调用频次的局部性偏好）？
2. **能否用更小的模型替代 LLM 构图器？** DyRetriever 使用与生成器相同的 LLM 来实现构图，如果换成 7B/3B 的小模型专门负责检索导航，是否可以进一步降低成本，同时保持生成质量？
3. **多跳推理的可解释性**：论文没有提供案例展示 DyCoder 的检索路径。如果能够可视化展示"入口点 → 中间函数 → 最终依赖"的推导链条，将有助于开发者理解并信任该工具的上下文选择逻辑。

## 10. 补充说明（论文中值得注意的细节）

- **强化的上下文组合策略**：DyCoder 将两类检索结果（相似度 Top-10 + 图检索 Top-5）合并去重后送入生成器。论文实验发现，相似度上下文和依赖图上下文的重叠率约为 20%–30%，二者提供的信息高度互补——相似度上下文通常帮助模型理解"如何实现类似逻辑"，而依赖图上下文帮助模型理解"依赖函数如何使用"。
- **LLM 提示设计的迭代式探索**：论文在附录中提到，作者尝试过多种提示模板，包括让 LLM 直接一次输出所有依赖函数、让 LLM 逐跳输出等。实验发现，"逐跳选择 → 访问 → 扩展"的交互式提示比一次性输出多跳依赖的准确率更高，这从侧面支持了"多跳推理优于单次全局推理"的核心论点。
- **对失败案例的分析**：论文在讨论部分指出，DyCoder 的主要失败模式是**依赖链断裂**——即入口点选择阶段遗漏了目标函数的最底层依赖（如一个工具函数），导致后续多跳无法挽救。相比之下，SimpleRAG 的失败模式主要是**相关性误判**——检索到语义相似但功能无关的函数。这一对比进一步突出了入口点选择对图检索方法的重要性。
- **数据/代码可用性**：论文声明将在 GitHub 上提供代码纳入附录，但截至论文发表时，仓库尚未公布（计划为"Soon"）。这一缺失在复现性方面构成一定阻碍，已在第 7 节中提及。
