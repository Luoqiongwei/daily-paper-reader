## 摘要
已验证代码生成要求大型语言模型（LLM）同时生成可执行程序以及机器可检查的证明，以证明该程序满足形式化规范，从而有望实现构造即正确的软件。当前的主流工作流程将问题的两半解耦：先合成程序，再尝试证明其正确性。我们观察到，这种顺序流水线在实践中既可能低效，也可能无效。若未预先考虑证明就生成程序，程序可能隐晦地不正确或在结构上难以验证，迫使LLM陷入在修补代码与修补证明之间交替的脆弱修复循环。受Dijkstra关于程序与其正确性论证应协同发展的观点启发，我们提出P$^3$，一种基于LLM的智能体工作流，它首先从规范中推导出统一的程序与证明计划，然后在此共享计划下细化实现与证明脚手架。为了在现实场景中评估已验证代码生成，我们进一步引入Lean4Commit0，一个从真实软件仓库中提取核心API并将其需求（包括跨API的关系规范）转换为Lean任务的、源自仓库的库级基准。使用四个前沿LLM后端，我们在Verina、AlgoVeri以及我们的Lean4Commit0基准上评估P$^3$，它在每个基准-模型组合中均取得了最高求解率。与更强的基线相比，它在每个基准的困难子集上提高了4.6至11.2个百分点的求解率，并将每任务API成本最多降低约40%，墙钟时间最多降低约37%。一项针对性的消融研究进一步显示，相比仅实现规划，联合规划程序与证明带来了3.3至8.3个百分点的增益，从而单独验证了联合规划的好处。

## Abstract
Verified code generation asks a large language model (LLM) to generate both an executable program and a machine-checkable proof that the program meets a formal specification, promising software that is correct by construction. The de facto workflow decouples the two halves of the problem: first synthesize a program, then attempt to prove it correct. We observe that this sequential pipeline can be both ineffective and inefficient in practice. A program generated without anticipating its proof can be subtly incorrect or structurally difficult to verify, forcing the LLM into brittle repair loops that alternate between patching the code and patching the proof. Inspired by Dijkstra's view that a program and its correctness argument should be developed hand in hand, we propose $P^3$, an LLM-based agentic workflow that first derives a unified program-and-proof plan from the specification, then elaborates the implementation and proof scaffold under this shared plan. To evaluate verified code generation in realistic settings, we further introduce Lean4Commit0, a repository-derived, library-level benchmark built by extracting core APIs from real-world software repositories and translating their requirements, including relational specifications across APIs, into Lean tasks. Using four frontier LLM backends, we evaluate $P^3$ on Verina, AlgoVeri, and our Lean4Commit0 benchmark, where it achieves the highest solve rate in every benchmark--model setting. Compared with the stronger baseline, it improves solve rates by 4.6--11.2 percentage points and reduces per-task API cost by up to roughly 40\% and wall-clock time by up to roughly 37\% on the difficult subset of each benchmark. A targeted ablation further shows gains of 3.3--8.3 points over implementation-only planning, isolating the benefit of planning the program and proof jointly.

## 1. 核心问题与研究动机

- **研究背景**：验证代码生成（Verified Code Generation）要求大语言模型（LLM）同时生成**可执行程序**和**机器可检查的证明**，以证明程序满足形式化规范（前置条件 P 与后置条件 Q），从而提供超越测试覆盖的正确性保证。
- **现有方法的缺陷**：当前主流流程是**"先程序、后证明"**（program-then-proof）的串行管线——先合成实现，再进行证明搜索，失败时在修补代码与修补证明之间交替循环。这种做法存在两方面的结构性瓶颈：
  - **有效性瓶颈**：未预先考虑证明就生成的程序，可能缺少证明所需的关键不变量或归纳结构，导致局部修补难以奏效；
  - **效率瓶颈**：大量 token 和时间预算被消耗在注定失败的修复尝试中。
- **核心洞察**：程序结构与证明结构是**相互约束、协同设计**的（Dijkstra 的经典观点），二者应在各自被具体展开之前，先在一个共享的高层计划（shared plan）层面达成结构一致性。

## 2. 方法论：P³ 框架

- **核心思想**：P³ 提出**先联合规划、后指导细化**的两阶段智能体工作流，使程序与证明在构造之初即结构一致，而非事后靠修复弥合。
- **阶段一：联合程序-证明规划（Joint Program-and-Proof Planning）**
  - 规划代理从规范 σ 出发，提出候选计划 ρ，每个计划包含四项结构性承诺：
    1. **形式化契约与算法要求**：规范重述及任何算法/渐进复杂度指令；
    2. **程序分解**：递归变量、分支结构、数据结构、辅助例程与终止度量；
    3. **库函数依赖**：明确要使用的 stdlib/mathlib 函数和既有引理；
    4. **证明义务**：桥接谓词（bridging predicate）、归纳/分情形结构、辅助引理陈述。
  - 候选计划需通过**草稿层面验证**：程序草图满足算法约束；证明草图解释分解如何保持桥接谓词、谓词如何蕴含 Q；必要的断言加强必须显式命名为辅助引理。
  - **示例**：listMax 任务中，结构递归版本（A）直接以规范为桥接谓词；而 foldl 累加器版本（B）需要引入规范中不存在的泛化累加器引理 `foldl_max_gen`。P³ 在计划层面即暴露此权衡，而非等证明失败后才察觉。
- **阶段二：计划指导的细化（Plan-Guided Elaboration）**
  - 在固定计划 ρ 下，代理分别展开程序 π 与证明脚手架 κ，二者遵循同一结构（递归变量、分支、谓词、引理）。
  - 局部证明空缺（以 `sorry` 表示）通过 Lean 4 的 LSP/MCP 反馈（目标与诊断信息）迭代填充。
  - **失败分类**：细化级失败（局部错误，就地进行小范围修复）与计划级失败（桥接谓词过弱、需要未计划的结构性引理）——后者触发**回退重规划**，避免在代码和证明之间无休止地来回打转。

## 6. 主要结论与发现

- **求解率全面领先**：P³ 在全部 12 个（基准 × 模型）单元中取得最高求解率，相对更强基线的绝对增益为 **+4.6 至 +11.2 个百分点**（Verina 上最高 +11.2，AlgoVeri 上 +5.2–7.8，Lean4Commit0 上 +4.6–5.5）；
- **联合规划 vs. 仅实现规划**：P³ 优于 PLAN-SEQ **3.3–8.3 个百分点**；且 PLAN-SEQ 在 Lean4Commit0 上相对 PLAIN 反而下降（13.9 vs. 17.6），说明跨 API 关系规范要求程序与证明必须针对共享证明义务协同规划；
- **效率显著提升**：在困难任务子集上，P³ 成本降低最多约 **40%**、时间降低最多约 **37%**（相对各指标的更优基线）；全求解交集上效率与基线相当，简单任务上有少量规划开销；
- **修复模式改善**：P³ 的全重启修复率在所有 Verina/AlgoVeri 单元中最低（通常较基线降低 2–4 倍），验证了计划作为"统一回退点"的作用；
- **案例佐证**：红黑树删除任务中，SEQ 在结构删除路径上 6,344 行未闭合，或靠冗余重建不变量在 1,176 行才成功；P³ 对比两种草图后以 1,105 行、约 34 分钟解决。

## 7. 优点与亮点

- **方法论层面**：
  - 将 Dijkstra 经典思想（程序与正确性论证协同设计）首次系统性地引入 LLM 驱动验证代码生成，以**共享计划**作为程序与证明的一致性锚点；
  - 明确的**失败分类与回退机制**（细化级 vs. 计划级），避免了程序-证明间的脆弱交替修复循环；
  - 计划将验证器的二元反馈转化为**结构性定位指导**，并支持将细化阶段分派给更便宜的模型（任务划分灵活）。
- **基准贡献**：
  - Lean4Commit0 是首个从真实开源仓库派生、含 **库级多 API 关系规范**的 Lean 验证代码生成基准，填补了教科书任务与现实软件需求之间的空白；
  - 规范质量采用**可自动化的三轮管线**（参考满足性 + 突变拒绝 + LLM 审查），为基准规范强度设立了明确底线。
- **实验设计**：多基准、多模型、多方法的组合提供了较强的泛化证据；消融设计（PLAN-SEQ）能干净地隔离"联合规划"的独特贡献。

## 8. 不足与局限

- **验证环境单一**：仅基于 Lean 4；对 Dafny、Verus、F⋆、Rocq 等其他验证后端（尤其是 SMT 驱动系统）的迁移性只是推测而非实验验证；
- **基准覆盖偏差**：Lean4Commit0 的 API 抽取聚焦核心入口而非完整项目编译，且来源库偏向 Python 生态（65/108），对系统级、数值密集型软件的代表性有限；
- **规范质量问题**：尽管有三轮过滤，规范仍可能在参考测试未覆盖的场景下过弱——求解率反映的是发布的规范而非真实意图的满足程度；
- **统计与可复现性**：每组配置仅运行一次，未估算随机方差、未做显著性检验；成本数据绑定评估时的 API 定价，仅适合相对比较；
- **后端局限**：实验限于四个前沿闭源模型，规划优势能否迁移到开源权重模型、小模型或专用定理证明模型尚未验证；
- **真实性风险**：验证只保证相对于所发布规范的正确性，规范本身若欠约束或有空洞，仍会产生"验证通过但不符合用户意图"的代码。
