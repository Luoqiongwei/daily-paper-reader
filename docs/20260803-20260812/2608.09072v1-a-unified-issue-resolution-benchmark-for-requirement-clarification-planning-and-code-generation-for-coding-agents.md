## 摘要
大型语言模型驱动的编码代理越来越多地用于修改现有代码仓库，例如添加功能或修复错误。然而，现有的仓库级基准通常只评估最终补丁是否通过测试。满足用户请求需要一系列相互依赖的推理和决策：代理必须恢复显式和隐式需求，制定基于仓库的实现计划，并将其转化为正确的代码。通过/失败的结果无法描述不成功的轨迹如何偏离正确补丁所需的需求和实现过程。为了解决这一差距，我们引入了SWE-RPG，一个仓库级基准，结合了可执行补丁评估与经过验证的地面真值参考（GTs），用于（1）需求澄清和（2）实现计划。这些中间GTs支持对完整编码代理轨迹进行回顾性、GT对齐的诊断，涵盖澄清、计划、代码生成和工件提交。SWE-RPG包含来自31个Python和Java仓库的163个任务，包括113个错误修复和50个功能添加。我们评估了3个编码代理，包括Claude Code、Codex和OpenCode，以及6个大型语言模型后端，包括Claude-Sonnet-5和GPT-5.6-Terra。结果表明，所评估的流行编码代理在现有仓库中实现用户请求方面仍然困难，在SWE-RPG上的平均解决率仅为31.5%。中间GT诊断进一步将隐式需求恢复识别为主要瓶颈，占代理运行的24.5%--46.0%。这一结果表明隐式需求恢复是改进编码代理的关键候选方向。基准数据和评估代码可在https://github.com/Xin-Zhou-smu/SWE-RPG-Bench获取。

## Abstract
Large language model-powered coding agents are increasingly used to modify existing code repositories, for example, by adding features or fixing bugs. Yet existing repository-level benchmarks typically evaluate only whether the final patch passes tests. Satisfying a user request requires a long chain of interdependent reasoning and decisions: an agent must recover explicit and implicit requirements, formulate a repository-grounded implementation plan, and translate it into correct code. A pass/fail outcome cannot characterize how an unsuccessful trajectory diverges from the requirements and implementation process needed for a correct patch. To address this gap, we introduce SWE-RPG, a repository-level benchmark that combines executable patch evaluation with validated ground-truth references (GTs) for (1) Requirement Clarification and (2) Implementation Planning. These intermediate GTs support retrospective, GT-aligned diagnosis of complete coding-agent trajectories across clarification, planning, code generation, and artifact submission. SWE-RPG comprises 163 tasks from 31 Python and Java repositories, including 113 bug fixes and 50 feature additions. We evaluate 3 coding agents, including Claude Code, Codex, and OpenCode, with 6 large language model backends, including Claude-Sonnet-5 and GPT-5.6-Terra. Results show that the evaluated popular coding agents still struggle to implement user requests in existing repositories, achieving an average resolved rate of only 31.5% on SWE-RPG. Intermediate-GT diagnosis further identifies implicit requirement recovery as the main bottleneck, accounting for 24.5%--46.0% of agent runs. This result suggests implicit-requirement recovery as a key candidate direction for improving coding agents. The benchmark data and evaluation code are available at https://github.com/Xin-Zhou-smu/SWE-RPG-Bench.

## 方法论：核心思想与关键技术细节

### 1. 基准任务形式化（Task Formulation）
- 输入：（i）指定 base commit 的代码仓库；（ii）自然语言的用户需求。
- 输出：编码代理自主修改仓库后产出的代码补丁。
- 每个实例提供分阶段 GT 工件：**Clarification GT（需求澄清参考）、Plan GT（规划参考）、Gold Patch（开发者补丁）、功能测试、Docker 环境**。

### 2. 需求澄清 GT 构建
- **实践者引导的分类体系（Practitioner-Guided Taxonomy）**：对 10 名来自财富 500 强科技公司的资深软件工程师进行访谈，归纳出六类需求澄清维度：
  - C1: Functional Intent（功能意图/范围）
  - C2: Business Semantics（业务语义）
  - C3: Technical Context（技术上下文）
  - C4: Interface/Protocol Specification（接口/协议规范）
  - C5: Code Structure and Conventions（代码结构与约定）
  - C6: Data-Structure Semantics（数据结构语义）
  - 同时收集 57 个种子 QA 对作为 few-shot 示例。
- **合成（Synthesis）**：由 GPT-5.4 驱动的合成代理，结合 issue、仓库、合并 PR，识别原始请求中未明确说明但实现关键的信息，生成候选 QA 对。
- **验证（Validation）**：验证代理检查每个 QA 对的证据支持性、跨阶段一致性、无实现细节泄漏；最后由两位作者人工独立复核。

### 3. 规划 GT 构建
- **合成阶段**：合成代理分析原始 issue、base 仓库和合并 PR，恢复实现意图，生成有序、模块化的步骤；每步包含目标（goal）、相关文件（relevant files）、预期改动（intended changes）、仓库约束（constraints）。
- **验证阶段（关键创新）**：对齐代理将每个规划步骤与开发者补丁的对应子集（gold subpatch）关联，然后**逐步骤验证可复现性**——编码代理仅凭该步骤生成补丁，评估器判断其是否与 gold subpatch 语义等价；失败则触发 gap-analysis 和修订代理修改计划，通过者保留。这确保了计划的"功能可复现性"（functional reproducibility）。
- 两位作者人工复核所有规划。

### 4. 代码生成 GT
- 无需重建：合并 PR 直接提供开发者补丁，任务相关测试作为可执行正确性 oracle。

### 5. 数据集构建流程（pipeline）
- 从 2000+ 个候选 issue-PR 对出发，依次经过：任务相关性过滤 → 环境构建（基于 SWE-bench-Live 的自动化管道 + 专家引导恢复）→ 测试验证（前后对比、去 flaky）→ 中间 GT 验证 → 最终得到 163 个任务。

## 主要结论与发现

1. **总体解决率低**：18 种配置在 SWE-RPG 上的平均解决率仅 **31.5%**，表明现有流行编码代理在仓库级问题解决上仍有很大提升空间。
2. **最佳配置**：OpenCode-MoonshotAI-Kimi-K3 达 49.7%（最高），Claude Code-Kimi-K3 为 49.1%，Codex-MiniMax-M3 仅 17.8%（最弱）。
3. **代理与模型层面**：OpenCode 平均最高（33.0%），Claude Code 次之（32.8%），Codex 最低（28.5%）；MoonshotAI-Kimi-K3 后端平均最优（46.6%）。
4. **主要瓶颈是隐式需求恢复**：需求阶段失败占各配置运行的 **24.5%–46.0%**，是最大的失败来源；规划失败占 5.5%–17.8%，代码生成失败占 7.4%–37.4%。平均 46.7% 的运行失败发生在需求澄清或规划阶段。
5. **相似解决率可能对应不同瓶颈画像**：如 Codex-DeepSeek-V4-Pro 与 Claude Code-DeepSeek-V4-Pro 解决率相近（40.5% vs 39.3%），但需求失败率分别为 26.4% 和 40.5%，说明端到端指标掩盖了阶段差异。
6. **前代码阶段能力短板**：三类代理在意图/范围维度覆盖最好，但在接口、结构、数据结构语义等实现导向类别上较弱；规划覆盖呈现"目标位置 → 实现方法 → 约束与验证"逐级递减的级联现象（如 Claude Code 从 79.7% 降至 64.5% 再降至 41.6%）。
7. **成本-性能关系复杂**：最佳配置 OpenCode-Kimi-K3 在低于平均成本下达到最高解决率；更长执行时间并不保证更好的补丁。

## 优点（亮点）

- **段级诊断创新**：首次将需求澄清、实现规划和代码生成三个阶段的验证性 GT 统一在一个基准中，突破了"只测最终补丁"的局限。
- **规划 GT 的功能可复现性验证**：不是简单检查规划步骤的语义必要性，而是真正测试"按步骤能否生成等价代码"，保证了规划参考的可执行质量。
- **实践驱动的需求分类体系**：通过访谈 10 名资深工程师构建六类需求澄清分类法，比纯理论分类更贴近真实开发中的澄清需求。
- **严格的质量控制流水线**：从 2000+ 候选对严格筛选到 163 个任务；中间 GT 经历合成-验证-人工复核三层把关；测试经过稳定性验证和 flaky 去除。
- **公平、可解释的评估协议**：失败归因和信息点覆盖均经过人工抽样验证（92%/96% 一致性），并允许替代方案（不要求规划文本或结构相同，只看语义责任是否实现）。
- **公开可用**：基准数据和评估代码开源。

## 不足与局限

- **覆盖范围有限**：仅 163 个任务、31 个仓库、Python 和 Java 两种语言；结论可能无法推广到其他语言或生态系统。
- **评估配置运行次数少**：每种配置每个任务仅运行 2 次，对随机性敏感，可能影响结论稳健性。
- **无人工交互评估**：代理端到端自主运行，无法评估人工反馈或交互式精化的效果。
- **依赖 LLM 辅助构建与评判**：中间 GT 和回顾性归因标签依赖 LLM 辅助构建与评判（GPT-5.4 构建、GPT-5.6-Sol 评判），虽经人工验证，但仍存在模型偏差风险；论文也承认未报告充分的 inter-annotator agreement 审计。
- **领域覆盖偏向**：主要集中在工程类领域（静态分析、编译器、算法/数学等），对 Web 开发、移动开发等常见场景覆盖不足。
- **成本与耗时数据来自特定基础设施**：在 2026 年特定硬件和 API 定价下测得，结果的可迁移性有限。
- **规划 GT 步骤平均仅 2.06 步**，可能偏向相对简单的修复/添加任务，对长程规划的挑战性任务覆盖不足。
