## 摘要
大型语言模型（LLM）能够生成功能上有效但仍存在漏洞的代码，而安全导向的干预措施可能破坏预期行为。我们研究了安全测试在生成之前和迭代修复期间作为可执行规范的作用。我们开发了SecTDD，一个受控的测试反馈脚手架，它分离了三个因素：测试是否预先显示，失败的执行是否触发修订，以及失败如何被选择和表示。评估使用行为划分的可见和隐藏测试，以及字节相同的初始候选用于修复比较。在2,705条轨迹、31个任务实例、三个安全代码基准、16个CWE类别和两个模型家族中，预先显示所有可见测试平均将隐藏的功能与安全联合成功率提高了19.3个百分点，但在九个基准模型条件下仅改善了七个，并损害了两个。在共享候选比较中，结构化反馈修复了80个初始不成功的候选，且没有联合回归；固定的原始反馈修复了83个，但导致三个回归。在其他方面，结构化反馈和原始反馈几乎无法区分（六胜六负，453平局）。通过所有可见测试的候选者在各种常见制度下仍然难以通过隐藏的行为族。这些结果表明，可执行反馈可以修复安全代码生成，但其收益取决于模型、任务、反馈入口点，尤其是测试覆盖范围。

## Abstract
Large language models (LLMs) can generate functionally useful code that remains vulnerable, while security-focused interventions may break intended behavior. We investigate security tests as executable specifications both before generation and during iterative repair. We develop SecTDD, a controlled test-feedback scaffold that separates three factors: whether tests are shown upfront, whether failed executions trigger revision, and how failures are selected and represented. The evaluation uses behavior-partitioned visible and hidden tests and byte-identical initial candidates for repair comparisons. Across 2,705 trajectories, 31 task instances, three secure-code benchmarks, 16 CWE categories, and two model families, showing all visible tests upfront increases hidden functional-and-security joint success by 19.3 percentage points on average, but improves only seven of nine benchmark-model conditions and harms two. In shared-candidate comparisons, structured feedback repairs 80 initially unsuccessful candidates with no joint regressions; fixed raw feedback repairs 83 but causes three regressions. Structured and raw feedback are otherwise nearly indistinguishable head-to-head (six wins, six losses, and 453 ties). Candidates that pass all visible tests still fail hidden behavior families under every common regime. These results show that executable feedback can repair secure-code generation, but its benefits depend on the model, task, feedback entry point, and especially test coverage.

- **核心问题**：在代码生成过程中，**安全测试能否作为一种"可执行规范"**——既在生成前帮助模型理解安全需求，又在生成后通过执行失败反馈驱动模型修复缺陷？其收益、代价与覆盖极限是什么？
- **研究定位**：论文刻意回避"提出一个最优新方法"的路线，而是通过受控实验**分离三个常被混淆的机制因素**：(1) 测试是否提前展示；(2) 执行失败是否触发修订；(3) 失败信息如何被选择与表示。目标是得出机制层面的结论，而非排行榜式的"谁更优"。

## 2. 方法论

### 2.1 核心思想：SecTDD 受控测试反馈脚手架

- SecTDD 将生成流程拆分为两个阶段：
  1. **初始生成**：在提示中只放入需求，或额外附加可见测试（作为可执行规范）。
  2. **反馈修复**：在沙箱中运行候选代码，若可见功能/安全测试失败，由编排器构造受限反馈消息，请求模型重写完整模块；**最多两轮修订**。
- 关键设计：**可见与隐藏测试的行为分区**。可见测试在生成与修复中暴露给模型；隐藏测试仅在最终评估时运行一次，绝不进入提示、反馈或停止决策。

### 2.2 反馈策略

| 策略 | 反馈内容 |
|------|----------|
| 固定原始反馈（B4） | 按稳定顺序返回所有失败日志 |
| 随机原始反馈（B5） | 按重复标识符+轮次确定性选出一个失败日志 |
| 结构化反馈（M） | 优先安全失败 → 未选过的失败 → 稳定标识符；每轮最多 2 个失败，每块含标识符、类型标记、可执行属性描述、失败输出尾部 |

### 2.3 方法族（受控对比矩阵）

| 方法 | 初始上下文 | 反馈 | 重用自 |
|------|-----------|------|--------|
| B0 | 仅需求 | 无 | – |
| B1 | 需求+安全提醒 | 无 | – |
| B2 | 需求+功能测试 | 无 | – |
| B3 | 需求+全部可见测试 | 无 | – |
| B4 | 需求 | 固定原始失败 | B0（字节相同） |
| B5 | 需求 | 单个随机原始失败 | B0（字节相同） |
| M | 需求 | 结构化安全优先 | B0（字节相同） |

### 2.4 关键公式

- **联合成功**：\( J(c) = F(c) \land S(c) \)，候选必须同时通过全部功能测试与安全测试。
- **Hidden Secure-Pass@1 (HSP@1)**：任务×重复网格上隐藏联合成功率的平均值。
- **测试反馈过拟合率（TFOR）**：
  \[
  \text{TFOR} = \frac{\sum_{x,r} \mathbb{1}[J_{vis}(c_{xr}) \land \neg J_{hid}(c_{xr})]}{\sum_{x,r} \mathbb{1}[J_{vis}(c_{xr})]}
  \]
  衡量"可见全过但隐藏失败"的比例，即反馈循环失效的覆盖率瓶颈。

## 6. 主要结论与发现

1. **RQ1（预显测试）**：B3 在 9 个条件中改善 7 个、损害 2 个，宏平均 +19.3 个百分点。预显测试是**依赖模型的规范机制，而非单调的安全干预**——例如 SALLM/Qwen2.5-Coder-7B-Instruct 上安全率从 74.5% 降至 56.4%，CodeGuard+/DeepSeek-V4-Flash 上 B3 反而比 B0 低 7.3 个百分点。
2. **RQ2（可执行反馈）**：结构化反馈（M）在 465 个共享单元格中触发 252 次修订，**修复 80 个隐藏联合失败且零联合回归**；其中 40 个为功能保持的安全修复。固定原始反馈修复 83 个但出现 3 个联合回归。B6 在 330 个共享单元格中修复 18 个且零回归。
3. **RQ3（结构化 vs 原始反馈）**：两者**无显著性差异**——6 胜、6 负、453 平。结构化汇总对工程控制有优势（token 可预测、属性可解释），但**不存在普遍的最优表示**。
4. **RQ4（覆盖极限）**：可见全过但隐藏失败的比例（TFOR）介于 5.6%–18.8%；B3 的池化 TFOR 最高（18.8%）。CodeGuard+/DeepSeek-V4-Flash 的 B6 在全部 55 个单元格中从未触发修订，因为 B3 候选全过可见测试，但其中 5 个隐藏联合失败——**没有可见失败信号，再多的修订轮次也无济于事**。
5. **RQ5（跨族复现）**：反馈的修复机制在 Qwen 与 DeepSeek 家族、三个基准上均复现；但**效应量、预显优化方向、最佳反馈入口点都不稳定**。未经过滤的 CodeGuard+ 广度波中，反馈触发率只有 21/110，修复 4 例，显著小于内部选样 pilot 的效果——说明预选实验会夸大治疗机会。

## 7. 优点

- **因果识别的严谨性**：共享初始候选 + 隐藏测试单次冻结评估，是现有自调试/安全生成研究中少有的受控设计。
- **机制级而非榜单级结论**：将规范效应、反馈效应、表示效应与覆盖瓶颈逐一拆解，回答了"为什么安全干预有时有效、有时有害"。
- **联合评估的纪律性**：始终使用 \(F \land S\) 联合指标，四状态分解（\(F^+S^+ / F^+S^- / F^-S^+ / F^-S^-\)）避免单一分数掩盖功能/安全互相偏移。
- **诚实的不显著结果**：在未达 0.05 显著性的情况下，以效应量、配对事件和分布诊断为主，明确量化统计功效限制。
- **供应链级的可复现性**：发布冻结提示、分块 oracles、沙箱运行器、完整轨迹与分析清单，并对 API 模型的不可复现性做了如实备案。

## 8. 不足与局限

- **任务与语言覆盖面窄**：全部为 Python 函数或小组件级别任务（31 个任务实例、16 个 CWE 类别），不覆盖 Java/C/C++、多文件仓库、并发、依赖漏洞或部署环境。
- **统计功效不足**：任务数少导致置信区间宽、无校正显著的比较；数千条轨迹并不能补偿小任务集。
- **Oracle 本身的有限性**：通过动态测试不能证明"无漏洞"，且安全测试可能拒绝语义不同的安全实现；TFOR 对可见/隐藏分区的强度敏感。
- **构造偏差风险**：SALLM 与 CodeGuard+ 的 overlay 使用了生成式模型辅助构建与初筛（虽经可执行门控 + 三名博士生人工复核，但模型相关错误无法完全排除）。
- **API 模型不可复现**：DeepSeek-V4-Flash 无确定性种子，提供方可能随时更新后端；token 预算使用本地代理分词器近似。
- **未衡量真实开发者价值**：SAFE@1 假设"部分功能的代码仍有价值"，但实际人力投入完成这些代码的代价未被测量；此外，生成代码在审查/修复环节需要的人工验证成本也未纳入。
