## 摘要
大型语言模型越来越多地被用作语义操作符，用于过滤、提取、排序、连接和转换非结构化数据。现有的语义查询处理系统调用的是以请求为中心的LLM服务系统，这些系统不了解查询计划，留下了大量未利用的性能机会。本文引入了关系型LLM服务，这种抽象使得LLM服务能够感知语义查询结构，同时保留查询语义和输出准确性。关键机会在于跨语义操作符的流水线执行：当中间元组直接从操作符流向下一个操作符时，它们的KV缓存状态可以重用，而不是重新计算。我们提出了Kalypso，一个关系型LLM服务系统，它暴露了一个用于语义查询计划的API，并使用自适应、内存感知的调度算法来执行。Kalypso解决了一个新的在线调度问题，其中流水线操作符执行与GPU内存压力管理相结合，以在驱逐之前重用服务引擎中的KV缓存状态。它的调度器持续调整内存分配，以平衡上游并行性、下游进度和GPU利用率。我们的评估表明，与使用以请求为中心的LLM服务的基线相比，Kalypso在各种工作负载下将查询完成时间提高了最高4.57倍，证明了查询感知的LLM服务可以显著提高语义查询执行的效率。

## Abstract
Large language models are increasingly used as semantic operators for filtering, extracting, ranking, joining, and transforming unstructured data. Existing semantic query processing systems invoke request-centric LLM serving systems that are unaware of the query plan, leaving substantial performance opportunities unused. This paper introduces relational LLM serving, an abstraction that makes LLM serving aware of semantic query structure while preserving query semantics and output accuracy. The key opportunity is pipelined execution across semantic operators: when intermediate tuples flow directly from one operator to the next, their KV-cache state can be reused instead of recomputed.   We present Kalypso, a relational LLM serving system that exposes an API for semantic query plans and executes them using an adaptive, memory-aware scheduling algorithm. Kalypso addresses a new online scheduling problem in which pipelined operator execution is coupled with GPU memory pressure management to reuse KV-cache state in the serving engine before eviction. Its scheduler continuously adjusts memory allocations to balance upstream parallelism, downstream progress, and GPU utilization. Our evaluation shows that Kalypso improves query completion time over baselines using request-centric LLM serving, with speedups up to 4.57x across diverse workloads, demonstrating that query-aware LLM serving can substantially improve the efficiency of semantic query execution.

# 论文《Kalypso: Relational LLM Serving》详细中文总结

## 1. 核心问题与整体含义（研究动机和背景）

- **背景**：大语言模型（LLM）被广泛应用于语义过滤、提取、排序、连接等操作，处理非结构化数据。现有语义查询处理系统（SQPS）将LLM请求视为独立的推理请求，调用以请求为中心的LLM服务系统（如vLLM、SGLang），这些系统不了解底层的查询计划。
- **核心问题**：这种“请求中心”的设计导致大量性能浪费。具体表现为：
  - 查询计划中的多个语义操作符（如 filter → map）在处理同一元组时，其提示词（prompt）通常共享前缀。如果KV缓存（KV-cache）被释放，下游操作符必须重新计算前缀，造成昂贵的预填充（prefill）开销。
  - 现有的SQPS采用“操作符-at-a-time”执行策略，将中间结果物化，导致在内存压力下KV缓存被驱逐，无法复用。
- **整体含义**：本文提出“关系型LLM服务”（Relational LLM Serving），使LLM服务层能够感知查询结构，通过流水线执行跨操作符的KV缓存复用，在保证查询语义和输出准确性的前提下显著提升效率。

## 2. 方法论：核心思想、关键技术细节

### 核心思想
- **关系型LLM服务**：在SQPS与底层请求中心推理引擎之间加入一个服务层，该层接收查询计划，决定元组进入哪个操作符、何时发起请求、如何分配KV缓存内存。这属于执行优化，不改变查询语义或输出准确性。
- **流水线（Pipelining）**：当上游操作符处理完元组后，立即将该元组传递给下游操作符，此时KV缓存前缀可被直接复用，无需重新计算。

### 关键技术细节

#### 2.1 Kalypso API
- 操作符以**用户定义函数（UDF）** 形式实现，需声明三个属性：
  1. **是否可流水线（Pipelining）**：如 filter、map 是可流水线的；aggregate、top-k 是阻塞的。
  2. **是否为谓词（Predicate）**：返回布尔值决定是否向下游传递元组（如 filter）。
  3. **是否为笛卡尔积（Cartesian Product）**：如 join 操作符，需通过 Kalypso 过程执行，以控制调度。
- 支持级联（cascade）、向量索引等优化（如 Indexed Cartesian Product, ICP）。

#### 2.2 调度算法（自适应内存感知调度）
- **查询计划解析**：将操作符分组为管道（pipeline），管道内再分为阶段（stage），由阻塞操作符或笛卡尔积分隔。每个阶段处理一个元组称为一个任务（task）。
- **内存感知调度**：调度器根据GPU内存可用性控制任务的启动，确保下游任务能在缓存被驱逐前复用前缀。
- **算法伪代码（Algorithm 1）**：
  - Launch：当阶段有剩余内存预算时，从等待队列中取出任务启动。
  - Complete：任务完成后，若未谓词过滤，则执行笛卡尔积生成子任务入队下一阶段；若过滤或为最后阶段则释放内存。
  - Rebalance：动态检测各阶段队列压力：
    - **饱和（Saturation）**：等待队列大小超过高阈值（high_s），表示下游消费不足，从该阶段转移内存给最后阶段。
    - **饥饿（Starvation）**：等待队列大小低于低阈值（low_s），表示上游产生不足，从下游阶段转移内存给上一阶段。
  - **参数**：α、β 可配置（实验中α=1, β=0.5），minBudget 为每个阶段至少保留一个任务及缓存前缀所需内存。

#### 2.3 内存管理
- **令牌上限估计**：基于历史请求统计输出/输入令牌比率的99百分位作为令牌上限，避免保守或乐观估计。若请求超限则中断并重试（增加上限）。
- **显式钉住（Explicit Pinning）**：要求底层LLM引擎支持钉住KV缓存块，防止驱逐。
- **虚拟钉住（Virtual Pinning）**：仅通过调度控制内存使用，依赖LRU替换策略，避免死锁。实验表明性能接近显式钉住。
- **死锁处理**：通过定期查询引擎状态检测死锁，若发生则解除所有钉住并切换到虚拟钉住。

## 6. 主要结论与发现

1. **显著性能提升**：Kalypso相比Lotus加速1.29×~4.57×，相比Palimpzest加速1.74×~2.23×（可用时）。
2. **流水线 vs. 阻塞**：流水线执行比阻塞执行快1.20×~1.83×，收益随管道长度和元组大小增加而增大。
3. **自适应调度优于静态分配**：固定内存比例无法适应不同工作负载，自适应调度在所有测试中达到或优于最佳固定比例。

5. **令牌上限估计稳健**：Kalypso的自动估计优于保守或激进固定值，在低内存压力下更显著。
6. **低内存压力下仍鲁棒**：当KV缓存容量从190.6GB降至38.6GB，Kalypso延迟增加幅度远小于基线（如MEDEC仅增9% vs. Lotus 44%）。

## 8. 不足与局限

- **实验局限**：
  - 仅使用Llama-3.3-70B一个模型，未验证不同规模或架构的LLM。

- **死锁处理**：仅在压力测试中观察到死锁，实际生产环境可能更频繁，但论文未提供详细机制评估。
