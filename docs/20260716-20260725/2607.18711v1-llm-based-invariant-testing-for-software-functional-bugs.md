## 摘要
手动编写单元测试来发现软件库中的功能缺陷不仅耗时，而且需要对API的预期语义有深刻理解。基于启发式的测试生成方法由于无法像人类一样推理程序语义或解释源代码和文档，因此可用性较低。传统的模糊测试技术（如OSS-Fuzz）通常依赖崩溃来检测缺陷，但功能缺陷并不总是导致崩溃。为了克服这些限制，我们提出了LISA，一种新颖的基于LLM的不变式测试框架，用于检测软件功能缺陷。LISA在API n-gram反馈的指导下迭代生成API序列和程序不变式，与模糊测试和先前基于LLM的测试生成方法相比，实现了更高的缺陷检测率和有竞争力的代码覆盖率，并将每个发现作为高置信度的缺陷候选报告给开发者确认。

## Abstract
Manually writing unit tests to uncover functional bugs in software libraries is not only time-consuming but also requires a deep understanding of the intended semantics of the APIs. Heuristic-based test generation methods suffer from low usability because they cannot reason about program semantics or interpret source code and documentation as humans do. Traditional fuzzing techniques like OSS-Fuzz often rely on crashes to detect bugs, but functional bugs do not always cause crashes. To overcome these limitations, we present LISA, a novel LLM-based invariant testing framework for software functional bugs. LISA iteratively generates API sequences and program invariants guided by API n-gram feedback, achieving higher bug-detection rates and competitive code coverage compared with both fuzzing and prior LLM-based test generation approaches, and reporting each finding as a high-confidence bug candidate for developer confirmation.

### 论文总结：基于LLM的不变式测试用于软件功能缺陷检测

#### 1. 核心问题与整体含义（研究动机和背景）

*   **研究问题**：软件库中的**功能缺陷**（非崩溃型逻辑错误）难以被自动化测试有效检测。传统单元测试需要人工编写，耗时费力；而启发式方法无法理解程序语义；主流模糊测试（如OSS-Fuzz）依赖程序崩溃，无法发现不崩溃但结果错误的“静默”逻辑错误。
*   **整体意义**：本研究旨在开发一种能够自动发现功能缺陷的测试框架，以降低人工成本，提升软件供应链的安全性。它提出了一种新的范式，即**将功能缺陷检测解耦为两个独立子任务**：生成合理的API调用序列（解决“可达性”问题）和生成用于验证结果的程序不变量（解决“预言机问题”）。

#### 2. 方法论：核心思想、关键技术细节与流程

**核心思想**：LISA框架将单元测试生成解耦为两个阶段：**API序列生成**（专注于探索和执行代码路径）和**不变式插入**（专注于验证执行的正确性）。通过此解耦，框架可以更有效地生成多样化且语义丰富的测试用例。

*   **第一阶段：API序列生成 (LISA_API)**
    *   **目标**：生成有效的、可执行的、能覆盖多样代码路径的API调用序列。
    *   **关键技术**：
        *   **API信息提取**: 利用Clang的AST解析库的头文件，提取函数声明、参数类型、结构体定义等元数据。
        *   **自适应的Few-shot生成**: 通过包含库上下文、项目规则、成功的API组合示例等提示词，引导LLM生成长串的、直通执行的（straight-line）API序列。
        *   **错误检测与修复**: 对生成的序列进行编译和执行测试，失败的序列通过LLM进行单次自动修复，修复不成功则丢弃。
        *   **API N-Gram反馈机制**: 为了引导LLM探索新的API组合，提出了一种基于API三元组（N=3）的覆盖反馈。当生成一个成功执行的序列时，其包含的新API三元组会获得奖励能量。
        *   **自适应压缩归一化（ACNE）**: 为了避免高能量API过早主导选择，ACNE动态调整API采样的概率。它通过对能量进行归一化，并应用一个参数可调的幂压缩函数（`C(a) = Ê(a)^α`）来平衡探索（低能量API）和利用（高能量API）。参数`α`会根据能量分布的变异系数自适应调整。
    *   **流程**：API信息提取 → 提示词构建 → LLM生成序列 → 编译/执行 → 错误修复 → 计算API三元组覆盖 → 更新采样概率 → 迭代优化。

*   **第二阶段：不变式生成 (LISA_inv)**
    *   **目标**：在第一阶段生成的API序列中插入具有语义意义的程序不变量（断言），以检测功能正确性。
    *   **关键技术**：
        *   **API知识库构建**: 混合方法。通过动态分析工具Daikon挖掘“似是而非”的不变量；通过专家手动从API官方文档中提取“预期”不变量。两者经过筛选、整合，形成知识库。
        *   **分块级不变量生成**: 将长API序列按逻辑分成多个块（Chunks）。对每个块，LLM结合当前块的代码、前序已验证的代码/断言、以及知识库中的API文档，生成候选不变量。
        *   **验证与修复循环**: 在每个分块插入候选不变量后，立即编译并执行。如果断言失败，进入最多5次的重试循环，LLM据此修正或弱化断言。如果失败持续，则将此测试标记为“高置信度缺陷候选”。
    *   **不变量类型**：包括结构型（句柄有效性）、值域型（字段范围）、关系/守恒型（输入输出关系）、文档衍生语义合约型（如只读保证）。
