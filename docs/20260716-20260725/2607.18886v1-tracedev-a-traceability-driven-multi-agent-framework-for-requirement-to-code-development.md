## 摘要
在现代软件开发中，大型语言模型（LLM）的快速发展使得将自然语言需求（NLR）端到端转换为可执行的仓库级代码变得越来越可行。然而，现有方法通常依赖简化的指令（例如单句描述），未能反映复杂的软件开发场景。此外，它们缺乏明确的需求可追溯性机制，难以精确对齐和验证生成的代码是否符合原始需求。为应对这些局限性，我们提出TraceDev，一种基于用例（包含多个功能点和复杂语义）的自动化软件开发多智能体框架。TraceDev采用五个角色特定的智能体，包括需求精炼者、设计者、开发者、测试者和验证者。值得注意的是，验证者智能体构建并维护一个异构的可追溯性图，该图链接需求、设计模型和代码制品，以与前述四个智能体交互。可追溯性图保持了各种制品之间的一致性，并作为结构化上下文用于高效的内存管理，支持可靠的仓库级代码生成。我们在两个广泛使用的数据集（包含125个用例）上评估TraceDev，并与两种最先进的方法进行比较。在ETOUR数据集上，TraceDev实现了53.63%的成功率，比基线方法高出多达186.63%。在SMOS数据集上也观察到类似趋势，TraceDev达到了56.82%的成功率，比基线方法高出多达340.80%。这些结果证明了TraceDev在从需求生成仓库级代码方面的有效性。

## Abstract
In modern software development, the rapid advancement of Large Language Models (LLMs) has made the end-to-end transformation of Natural Language Requirements (NLRs) into executable repository-level code increasingly feasible. However, existing approaches typically rely on simplified instructions (e.g., single-sentence descriptions), failing to reflect complex software development scenarios. Moreover, they lack explicit requirement traceability mechanisms, making it difficult to precisely align and validate generated code against original requirements. To address these limitations, we propose TraceDev, a multi-agent framework for automated software development grounded in use cases that contain multiple functional points and complex semantics. TraceDev employs five role-specific agents, including a Requirement Refiner, Designer, Developer, Tester, and Validator. Notably, the Validator Agent constructs and maintains a heterogeneous traceability graph that links requirements, design models, and code artifacts for interacting with the preceding four agents. The traceability graph maintains consistency across various artifacts and serves as a structured context for efficient memory management, supporting reliable repository-level code generation. We evaluate TraceDev on two widely used datasets (including 125 use cases) compared with two state-of-the-art approaches. On the ETOUR dataset, TraceDev achieves a success rate of 53.63\%, outperforming baseline approaches by up to 186.63\%. A similar trend is observed on the SMOS dataset, where TraceDev attains a success rate of 56.82\%, exceeding baseline approaches by up to 340.80\%. These results demonstrate the effectiveness of TraceDev in repository-level code generation from requirements.

## 1. 核心问题与整体含义（研究动机和背景）

- **现有问题**：
  - 大多数端到端代码生成方法（如 ChatDev、MetaGPT）依赖**简化的需求输入**（单句描述或函数级任务），无法反映真实世界中包含**多个功能点和复杂语义**的用例（Use Case）。
  - 缺乏**需求可追溯性机制**：跨阶段转换（需求→设计→代码）时易产生语义偏差、功能遗漏，且难以检测缺失或错误实现。
- **研究动机**：在真实软件开发中，需求通常以结构化用例形式呈现（如 ETOUR 和 SMOS 数据集），且维护阶段（占软件生命周期约 80%）高度依赖需求到实现的可追溯性。因此，需要一个既能处理复杂场景又能保持**需求-设计-代码一致性**的自动化框架。
- **核心含义**：提出 TraceDev，通过构建和维护**异构可追溯性图**来显式链接制品，实现更可靠、更完整的仓库级代码生成。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：基于多智能体协作模拟完整软件开发生命周期（SDLC），以可追溯性图为**结构化上下文**和**内存管理机制**，驱动迭代精炼。
- **五个专用智能体**：
  1. **Requirement Refiner（需求精炼者）**：
     - 解决术语不一致（如“Entry Conditions” vs “Preconditions”）和语义歧义（如缺主语）。
     - 使用 **形式化语法约束** 引导 LLM 进行模式对齐和主语推断。
     - 通过**形式化检查器**迭代验证，确保输出符合标准化 schema。
  2. **Designer（设计者）**：
     - 基于精炼用例，生成 PlantUML 格式的**类图**（静态结构）和**序列图**（动态交互）。
     - 将架构骨架与实现解耦，提升模块化和可维护性。
  3. **Developer（开发者）**：
     - 以类图和序列图为输入，生成仓库级代码（多文件协作）。
  4. **Tester（测试者）**：
     - 自动生成并执行**单元测试**（覆盖主路径和异常路径）。
     - 收集执行反馈（错误日志），驱动开发者自我修正（最多 5 轮重试）。
  5. **Validator（验证者）**：
     - 构建**异构有向图 G=(V,E)**，节点来自需求（正则提取）、设计（结构解析）、代码（AST 解析）。
     - **需求→设计**：LLM 语义匹配；**设计→代码**：AST 句法匹配。
     - 自动检测**缺失链接**，生成质量报告反馈给 Designer/Developer，进行最多 3 轮精炼。
- **内存管理**：可追溯性图将大规模制品压缩为紧凑的节点-边表示，保留核心依赖关系，降低上下文大小。
- **总体流程**：输入用例 → Refiner（精炼） → Designer（设计） → Developer（编码）+ Tester（测试+修正） → Validator（追溯验证+迭代）。

## 7. 优点

- **创新性**：**首次将可追溯性图引入代码生成**，实现需求-设计-代码的显式链接，支持自动检测缺失和错误实现。
- **贴近实际**：采用**结构化用例**作为输入，包含多个功能点和复杂约束，比现有简化指令更符合真实场景。
- **系统性**：多智能体覆盖完整 SDLC（精炼→设计→编码→测试→验证），并形成闭环迭代。
- **全面评估**：自动、人工、统计三方面评估，消融实验分析各组件贡献，结果可信度高。
- **可复现性**：代码、数据、提示模板全部开源。
- **跨 LLM 泛化**：在 Gemini、DeepSeek、GPT-5-mini 上均表现稳定，不依赖特定模型。

## 8. 不足与局限

- **可追溯性图可能引入错误**：错误链接可能导致不必要修改，但通过有限修复机制（最多 3 轮追溯修复、5 轮测试修复）将影响控制在可接受范围。
- **输入格式局限**：当前仅支持用例格式（结构化字段），对于用户故事、软件需求规格说明书（SRS）等其他需求形式需要重新设计模式和解析规则。
- **缺少代码与测试之间的追溯**：可追溯性图仅覆盖“需求→设计→代码”，未包含测试用例，测试与需求/代码的对应关系未在图层面建模。
- **实验通用性有限**：
  - 仅两个数据集（ETOUR、SMOS），均为学术数据集，是否适用于工业级大型项目未验证。
  - 仅 Java 语言（基于数据集），其他语言未测试。
- **LLM 评分不确定性**：自动评估使用 LLM-as-a-Judge，虽采用多数投票缓解，但仍有偏差风险。
- **计算成本**：验证者迭代多次会增加时间和 token 消耗，在资源受限场景下可能不适用。
