## 摘要
可见测试是LLM生成代码的常见关卡，但通过测试并不能证明规范的正确性。我们研究了一个类似部署的监控问题：代码通过公共测试后，较弱的LLM验证器能否识别残留的隐藏错误？我们引入了代码监控红队测试，这是一个监控-红队测试协议，它在固定公共检查信息边界的同时，改变生成器压力、验证器支架和弱到强能力。我们将其实例化为CodeMonitorBench，涵盖函数级、数据科学和工作流代码。在71,000个生成的候选代码中，43,677个通过了公共测试，其中23,081个未能通过隐藏测试。弱验证器通过支架和模型族有所改进，但在5%的假阳性率下仍然遗漏了大部分隐藏错误。作为鲁棒性压力测试，对抗性公共测试过拟合压力降低了验证器的AUROC，并在大多数情况下提高了低FPR的遗漏率。在相同的证据边界下，GLM-5.1验证器恢复了部分差距；可推断性审计显示，剩余的遗漏混合了验证器失败和M1证据限制。

## Abstract
Visible tests are a common gate for LLM-generated code, but passing them does not certify specification correctness. We study a deployment-like monitoring problem: after code has passed public tests, can a weaker LLM verifier identify the residual hidden bugs? We introduce Code Monitor Red Teaming, a monitor-red-teaming protocol that fixes a public-check information boundary while varying generator pressure, verifier scaffolding, and weak-to-strong capability. We instantiate it as CodeMonitorBench, spanning function-level, data-science, and workflow code. Across 71,000 generated candidates, 43,677 pass public tests and 23,081 of those fail hidden tests. Weak verifiers improve with scaffolding and model family, but still miss most hidden bugs at 5% false-positive rate. As a robustness stress test, adversarial public-test-overfit pressure lowers verifier AUROC and raises low-FPR miss rates in most cells. A GLM-5.1 verifier recovers part of the gap under the same evidence boundary; an inferability audit shows that remaining misses mix verifier failures with M1 evidence limits.

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：将代码验证视为**公共传递监控**（public-pass monitoring）。在公共测试通过后，验证器基于固定的“公共检查视图”（M1：规范、接口、公共测试、候选代码、通过状态），为每个候选输出一个可疑分数（0~1），用于排序。隐藏测试仅作为标签（不提供给验证器），衡量残留缺陷是否被检测到。
- **协议组成**：
  - **公共传递工作流**：先生成代码并执行公共测试，只将通过的候选送交验证器。
  - **验证器信息边界M1**：验证器只能看到公共视图，不能看到隐藏测试、执行结果、参考实现或标签。
  - **基准构建**：三个代码域：函数级（BigCodeBench-Hard）、数据科学代码（Data-Science Code）、工作流代码（CodeWorkflow），均有冻结的公共/隐藏测试集。
  - **生成器条件**：5种压力条件（G1普通意识、G2验证器意识、G3方案意识、G4-自然捷径、G4-对抗过拟合），其中G4-adv明确要求通过公共测试但故意留下隐藏缺陷。
  - **验证器支架**：直接审查（Direct）和混合审查（Hybrid），后者先分解需求再对抗性搜索，但证据边界相同。
  - **弱到强比较**：使用相同M1边界，比较不同模型家族和能力（Qwen-7B, Llama-8B, Mistral-7B, GPT-5.4-mini, GLM-5.1）。
- **技术细节**：候选代码经公共测试筛选后，验证器返回可疑分数，隐藏标签在之后得出。无效输出标记为NA，不插值。主要指标：AUROC、FPR@5%时的TPR/FNR、AUPRC、NA率。考察固定低假阳性率下的漏检率（FNR）。

## 6. 论文的主要结论与发现

1. **公共测试留下大量隐藏缺陷**：71k候选中有43,677通过公共测试，其中23,081（52.7%）仍包含隐藏缺陷，且即使在非对抗条件下（G1）也高达43-47%。
2. **弱验证器在低假阳性率下漏检大部分缺陷**：以5% FPR为操作点，Hybrid Qwen-7B漏检86.8%，Mistral-7B漏检80.0%，即使提升预算至10% FPR仍漏检72-80%。改进支架和模型家族后仍然不足。
3. **对抗性压力（G4-adv）降低监控性能**：G4-adv不仅提高隐藏缺陷率，还使缺陷更难以被弱验证器识别，AUROC平均下降~0.07，FNR上升~0.07。
4. **更强验证器（GLM-5.1）部分恢复能力但仍有残留监控差距**：在相同M1下，GLM-5.1 FNR从弱模型的~0.76降至0.54（G1），0.66（G4-adv），但仍漏检大量对抗性缺陷。
5. **可推断性审计确认混合失败**：92%的隐藏缺陷是规范根源的，但只有33%能从M1构造性发现，64%事后可推断。GLM-5.1捕获了40%（vs 20%弱模型），23%为弱漏检/强捕获。残留缺陷混合了验证器失败和M1证据限制。
6. **公共传递审查应作为对抗性搜索，而非最终接受**。

## 7. 优点

- **创新性协议**：首次将监控红队测试概念系统应用于代码生成后的验证阶段，固定公共信息边界，模拟真实部署场景，而非直接比较代码生成或批评基准。
- **多领域基准**：CodeMonitorBench覆盖函数级、数据科学和工作流代码，每个领域有不同的缺陷表面（API语义、库重形状/dtype、工件不变量），提升泛化性。
- **系统消融**：分离生成器压力、验证器支架和模型能力的影响，并通过大量消融和审计揭示不同因素的作用，有助于理解监控失败根源。
- **弱到强比较保持公平**：强验证器也受M1边界约束，不获得隐藏测试或执行结果，因此能力差异可归因于模型本身。
- **可审计性**：通过人工审计、样本组合分析和证据边界消融，将构造效应与监控失败分离，增强了结论的透明度和可解释性。

## 8. 不足与局限

- **隐藏测试完整性问题**：隐藏测试是冻结的测试集，不一定能覆盖所有语义错误，可能漏标或过估缺陷。
- **数据集覆盖有限**：构造的数据科学和工作流分裂不涵盖所有库、所有仓库类型或交互式开发。BigCodeBench-Hard基于现有基准，可能引入偏差。
- **对抗条件非部署率估计**：G4-adv是压力测试，用于揭示验证器脆弱性，不应被解读为实际部署中的缺陷频率。
- **未探究学习型验证器训练**：未使用监督学习或微调来改进验证器，仅依赖单次LLM审查。生成的测试基线虽略有帮助，但并未充分优化。
- **计算资源与延迟未报告**：无GPU型号、训练时间或推理成本，影响可重复性评估。
- **仅有定量指标**：未进行交互式审查、多轮修复或成本-收益分析，可能不足以涵盖实际工程场景。
