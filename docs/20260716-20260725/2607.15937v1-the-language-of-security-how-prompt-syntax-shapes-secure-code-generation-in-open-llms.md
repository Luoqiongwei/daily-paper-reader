## 摘要
大型语言模型（LLMs）越来越多地被用于源代码生成，尽管其输出经常存在安全漏洞。先前的研究表明，提示工程可以减轻此类风险，但（1）他们关注的是高层次的提示策略，忽略了近期证据表明细粒度的句法变化可以显著改变模型行为；（2）主要评估专有LLMs，限制了其发现在工业环境中的适用性，而在工业环境中，出于隐私、合规性和部署控制等原因，更倾向于使用自托管的开放模型。在本文中，我们研究提示的细粒度句法成分如何影响开放LLM生成代码的安全性。通过使用解析器驱动的方法，我们系统地生成了与安全相关的代码生成提示的句法变体，并评估它们对多个开放LLMs和编程语言中代码安全性的影响。我们的结果表明，特定的句法元素，如约束、防护、条件和概念绑定，以及它们在提示中的位置，始终影响生成不安全代码的可能性。这些发现将提示语法确定为一个具体的安全控制面，并为减少LLM辅助开发中的漏洞风险提供了可操作的指导。

## Abstract
Large Language Models (LLMs) are increasingly used for source code generation despite their outputs often exhibiting security vulnerabilities. Prior work shows that prompt engineering can mitigate such risks, yet (1) they focused on high-level prompting strategies, neglecting recent evidence that fine-grained syntactic variations can substantially alter model behavior; and (2) predominantly evaluate proprietary LLMs, limiting the applicability of their findings in industrial settings where self-hosted, open models are preferred for privacy, compliance, and deployment control. In this paper, we study how fine-grained syntactic constituents of prompts influence the security of open LLM-generated code. Using a parser-driven approach, we systematically generate syntactic variants of security-relevant code generation prompts and evaluate their impact on code security across multiple open LLMs and programming languages. Our results show that specific syntactic elements, such as constraints, guards, conditions, and concept bindings, and their position within the prompt consistently affect the likelihood of generating insecure code. These findings identify prompt syntax as a concrete security control surface and provide actionable guidance for reducing vulnerability risk in LLM-assisted development.

### 1. 核心问题与整体含义（研究动机和背景）

- **问题**：大语言模型（LLMs）生成的代码经常存在安全漏洞，尽管提示工程（prompt engineering）能在高层策略上缓解风险，但现有研究忽略了**细粒度句法变化**（如词序、从句移除等）对代码安全性的影响；同时，已有工作主要评估**专有模型**（如GPT-4），而工业界出于隐私、合规和部署控制，更倾向使用**开放模型**（Open LLMs），但开放模型的安全性研究不足。
- **背景**：NLP和推理领域的证据表明，小句法变动（如添加无关从句、移除词法成分）能显著改变LLM行为（准确率下降65%）。因此，本文假设**提示的句法成分本身构成安全控制面**，需要系统探究。
- **目标**：揭示开放LLM中，提示的**语法成分（句法类型、位置、粒度）**如何影响生成代码的安全性，为安全提示工程提供可操作指导。

### 2. 方法论

- **核心思想**：将提示视为结构化语言制品，通过**成分句法分析树**（constituency parse tree）识别并系统性**移除单个句法成分**，生成一组最小变体（prompt permutations），然后比较变体与原始提示生成的代码漏洞率，从而推断因果影响。
- **关键技术细节**：
  - 使用**crf-en-constituency parser**（基于Penn Treebank II标注规范）解析英文提示，得到短语结构树。
  - 对每个提示，分别移除树中每个非终端节点对应的连续token跨度，每次仅移除一个成分，生成变体。每个变体由三个特征描述：
    - **成分类型**（Constituent Type）：如S（陈述句）、SBAR（从属连词从句）、NP（名词短语）、VP（动词短语）、WHADVP（疑问副词短语）、ADJP（形容词短语）等（共18种）。
    - **粒度**（Granularity）：Minimal（最小短语）、Chunk（中间短语）、Clause（从句/谓词结构）。
    - **句子索引**（Sentence Index）：0-based，表示该成分在提示文本中的句子顺序位置。
  - 通过移除成分，产生**仅一个成分被改变**的变体，从而隔离效果。
- **流程**：原始提示 → 解析树 → 遍历非终端节点 → 生成所有可能的变体（每个变体只移除一个成分） → 加载LLMs生成代码 → CodeQL静态分析 → 统计比较漏洞率。

- **数量**：共生成**12,960个提示变体**（3种语言 × 4,320个/语言），每个变体对应一个LLM生成代码，最终**40,230个代码片段**（包含基线）。

### 6. 主要结论与发现

- **句法特征显著影响代码安全**，效果在Python中最强，Java次之，C最弱但方向一致。
- **位置（句子索引）是最强单因子**：
  - Python：后期位置（索引1-7）移除成分导致漏洞率单调上升（RR最高达2.24），晚期信息（边界条件、操作守卫）关键。
  - Java：**早期位置（索引0）**移除核心任务描述导致漏洞率上升（RR≈1.6~2.3）。
- **成分类型**是第二重要单因子：
  - **WHNP/WHADVP**（疑问/相对代词短语，如“which input”“how”）最敏感，移除后漏洞率上升最大（Python RR≈1.73-1.88）。
  - **VP**（动词短语，移除动作语义）和 **SBAR**（从属从句，移除条件/守卫）次之。
  - **ADJP**（形容词短语，移除规范性限定）在Python和Java中也有影响。
- **粒度影响**：最弱单因子，仅**Clause级别**在Python显著，起调制作用而非主导。
- **组合特征放大风险**：早期位置+WHNP/WHADVP、晚期位置+NP/PP、SBAR/VP+Minimal等组合产生超额风险，且跨模型方向一致。
- **跨模型一致性**：Qwen、Athene、Phi-4在风险模式和方向上一模一样，仅幅度差异，表明句法敏感性可能是自回归模型的固有属性。

### 7. 优点

- **首创性**：首次从**细粒度句法成分**角度系统分析对LLM安全代码生成的影响，填补了高层提示策略与低层语言结构之间的空白。
- **严格因果推断**：采用**单一成分移除**的受控实验，使得观测到的漏洞率变化可以归因于特定句法变化，而非混杂语义。
- **多语言多模型验证**：覆盖三种代表性语言和三种不同规模的开源模型，结果稳健且可泛化。
- **统计严谨**：使用两阶段检验（omnibus + pairwise）、FDR校正、效应量和风险比，避免假阳性。
- **可复制性强**：提供了完整复制包（含数据、脚本、解析器配置），并进行了确认性重运行。
- **实践指导价值**：直接建议“必须明确指定‘which’‘how’‘under what conditions’”等，对工业界安全使用LLM有直接帮助。
