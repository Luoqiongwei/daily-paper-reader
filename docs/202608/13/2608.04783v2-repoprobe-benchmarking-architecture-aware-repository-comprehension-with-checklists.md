## 摘要
大型语言模型（LLM）与软件工程的集成已将焦点从函数级生成转移到仓库级辅助。然而，现有基准测试主要依赖GitHub Issues中的错误报告，这往往使模型能够通过错误日志的模式匹配绕过真正的理解。这种偏差低估了编辑偏差（Edit Bias），即模型过早地提出代码修改建议，而非理解现有仓库架构。此外，当前基于LLM作为评判者的标量评分存在高方差和低可解释性的问题。本工作引入了RepoProbe，一种通过GitHub Discussions进行开放式问答来评估仓库级代码理解的新型基准测试，其重点是开放式架构探究而非缺陷报告。为确保严格评估，我们提出了一种基于检查清单的验证协议，将答案分解为原子的、可验证的事实，从而用客观验证取代主观评分。我们对最先进（SOTA）LLM的评估揭示了高清晰度与基于证据的技术正确性之间的持续差距。同时，该评估定量证实了编辑偏差的普遍性，即模型优先进行代码生成而非架构分析。最后，我们证明了相较于传统标量评分评估，我们的验证协议显著提高了评估可靠性。

## Abstract
The integration of Large Language Models (LLMs) into software engineering has shifted the focus from function-level generation to repository-scale assistance. However, existing benchmarks largely rely on bug reports from GitHub Issues, which often allow models to bypass genuine understanding via pattern matching on error logs. This misalignment under-measures Edit Bias, which refers to premature generation, where models prematurely propose code modifications instead of understanding the existing repository architecture. Furthermore, current LLM-as-a-Judge scalar scoring suffers from high variance and low interpretability. This work introduces RepoProbe, a novel benchmark for evaluating repository-level code understanding through open-ended Q&A using GitHub Discussions, which focuses on open-ended architectural inquiries rather than defect reporting. To ensure rigorous evaluation, we propose a Checklist-Based Verification Protocol that decomposes answers into atomic, verifiable facts, thereby replacing subjective ratings with objective verification. Our evaluation of state-of-the-art (SOTA) LLMs reveals a persistent gap between high clarity and evidencegrounded technical correctness. It also quantitatively confirms the prevalence of edit bias, in which models prioritize code generation instead of architectural analysis. Finally, we demonstrate that our verification protocol significantly improves evaluation reliability compared to traditional evaluations with scalar scoring.

## 6. 论文的主要结论与发现

### 主要发现一：SOTA 模型表现呈现清晰但非单调的能力层级

- 闭源前沿模型占据大部分顶级位置，开源模型具有竞争力但普遍落后。
- 跨代际进步**并非单调**：Claude Opus 4.6、Gemini 3.1 Pro、GLM-5、Kimi-K2.5 等有所改进，但 GPT-5.4 和 MiniMax-M2.5 出现倒退。通用模型进步不能自动转化为更好的仓库级理解。
- 最佳系统仅在 **60% 出头的水平**（GPT-5.2 总体性能 62.7%），留有大量改进空间。

### 主要发现二：清晰度持续高于技术正确性

- 所有模型表现出共同特征：**清晰度得分明显高于知识得分**。模型常生成结构良好的解释，但遗漏必要的检查清单项目。
- 完美解决率即使对前沿系统也保持中等水平（最高仅 27.5%），表明仓库级 Q&A 的主要瓶颈是证据基础和跨文件依赖追踪，而非流畅叙述。

### 主要发现三：清单验证协议显著提升评估可靠性

- 清单验证的**标准差约为标量评分的一半**（例如 Claude Opus 4.5：SD 从 3.5% 降至 1.5%，范围从 8.3% 降至 3.2%）。
- 标量评分存在两种失败模式：**解释漂移**（高方差）和**方向不一致**（不可解释性）。即使分数相同，评价者可能给出方向相反的反馈。

### 主要发现四：编辑偏差是普遍失败模式

- 在低分失败案例中，编辑偏差平均占 **15.8%**（GPT-5.2 为 10.4%，Gemini 3 Pro 高达 24.0%）。
- 模型面对开放式仓库询问时，往往默认优先生成代码而非进行必要的结构分析。

### 主要发现五：分层性能差异

- **编程语言**：QML（38.4%）显著低于 TypeScript（57.6%），长尾语言表现弱。
- **代码理解类别**：业务逻辑的完美解决率最低，因为需要因果和跨组件推理。
- **仓库主题**：安全（56.0%）和云 DevOps（55.4%）较易，桌面应用（47.3%）和数据处理（47.6%）较难。

## 7. 优点

1. **数据来源创新**：使用 GitHub Discussions 而非 GitHub Issues，避免了缺陷报告中文件路径、堆栈跟踪等显式定位线索对“真实理解”的信号污染，迫使模型执行真正的语义映射和跨文件探索。
2. **检查清单验证协议**：将开放式答案分解为原子、可验证的技术项目，用离散分数和细则代替模糊的标量评分，显著提高了评估稳定性和可解释性。
3. **约束式评估**：先理由后评分+细则遵守的双重约束，以及统一的 JSON 输出格式，有效减少了幻觉评估和事后合理化。
4. **多维度分层实验设计**：系统地分析了编程语言、代码理解类别和仓库主题三个轴上的性能差异，提供了细粒度的诊断视野。
5. **代理环境评估**：使用 Claude Code 作为固定代理脚手架，模拟真实开发者环境，比静态提示更贴近实际使用场景。
6. **模型选择多元化**：涵盖 10 个提供商、20 个模型、两个 SOTA 时间点，能够分析跨代际进步并识别非单调现象。
7. **有效暴露编辑偏差**：通过精心设计的案例分析（如 adk-python 案例），展示了传统基准可能奖励“错误但字面上正确”的方案，而清单验证能捕捉真正的架构理解。

## 8. 不足与局限

### 实验覆盖方面

- **模型覆盖仍有偏移**：被评估模型多为 2025-2026 年的前沿模型，但仅评估了一个固定代理脚手架（Claude Code），未比较不同脚手架对性能的影响，可能限制了结论的泛化性。
- **RQ3 失败模式分析不完整**：仅对 3 个顶尖模型报告了失败模式分解，未覆盖全部 20 个模型；同时，编辑偏差的粗略占比缺乏更细粒度的回归分析来量化其对整体分数的具体贡献。
- **数据集规模相对有限**：500 个 Q&A 对虽经严格筛选，但相比 SWE-bench 等基准的规模仍然较小，且来自 2024 年后创建的仓库，可能过度代表新一代项目。

### 偏差风险方面

- **LLM 生成检查清单的偏差**：检查清单由 Claude 生成，虽然有人工验证，但其质量依赖于生成模型的能力；清单可能在知识覆盖上存在盲点，或偏向参考答案的表达方式。评估器（Claude Sonnet 4.5）与清单生成器为同一模型家族，存在系统性偏差风险。
- **外部链接上下文整合的语义损失**：在上下文增强阶段，将外部链接摘要整合进问题时可能丢失原始上下文中的细微信息，影响问题的真实完备性。
- **人工审查的规模有限**：论文未报告人工审查的具体标注者数量、标注时长或标注者间一致性指标，虽然声称“专家标注者”完成了审查并达成一致。

### 应用限制方面

- **仅评估文本答案**：基准排除了依赖图片的讨论，限制了在多模态仓库场景（如 UI 代码、架构图）中的适用性。
- **静态问答与真实开发的差距**：虽然采用代理环境，但任务仍是“回答问题”而非“修改代码”，与实际的仓库级软件工程项目（端到端功能实现）仍有距离。
- **离线评估限制**：外部链接被整合进文本，模型仅需访问仓库代码和问题文本即可回答，这虽然保证了离线可复现性，但与真实开发者可浏览在线资源的场景存在差异。
- **编辑偏差定义边界**：论文将其定义为失败模式，但在某些开发场景中，生成代码修改本身可能是合理的响应方式。基准的评分并未区分“有用的代码生成”和“过早的代码生成”之间的灰色地带。
