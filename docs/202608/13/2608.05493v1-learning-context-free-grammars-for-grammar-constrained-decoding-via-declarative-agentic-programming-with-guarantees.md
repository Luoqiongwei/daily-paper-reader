## 摘要
语言模型（LM）越来越广泛地用于通过以领域特定语言（DSL）编写的程序与外部服务交互。然而，由于DSL通常是低资源和冷门的，LM经常在这些语言中产生语法无效的程序。文法约束解码可以消除此类失败，但需要语法约束。这些约束通常以目标语言的上下文无关文法形式存在，而这一产物对于第三方DSL来说是难以获得的。在这项工作中，我们定义了一个名为Autogrammar的智能体，它从文档和执行数据中自动学习上下文无关文法。Autogrammar被形式化为一个Kripke结构，其非确定性选择由语言模型解决，从而通过线性时序逻辑约束实现对智能体行为的声明式控制。我们在三种DSL（即Amazon CloudWatch Logs Insights、Dynatrace Query Language和Datadog Search Syntax）上评估了四个版本的Autogrammar，发现它生成的文法在未见数据上实现了接近完美的精确率；时序限制将执行时间减少了3.8倍，且没有导致统计上显著的精确率损失；执行数据至关重要，而文档则是可有可无的；使用Autogrammar生成的文法进行文法约束解码，在十个真实任务中的八个上显著提升了端到端语言模型性能，达到或超过了专业维护文法的表现。相比之下，现有LM基线和最先进的形式化技术生成的上下文无关文法在相同评估中表现显著较差。

## Abstract
Language models (LMs) are increasingly used to interact with external services via programs written in domain-specific languages (DSLs). Unfortunately, since DSLs are often low-resource and esoteric, LMs frequently produce syntactically invalid programs in these languages. Grammar-constrained decoding can eliminate such failures, but requires syntactic constraints. These are usually in the form of a context-free grammar for the target language, an artifact that is hard to come by for third-party DSLs. In this work, we define an agent, called Autogrammar, that automatically learns context-free grammars from documentation and execution data. Autogrammar is formalized as a Kripke structure whose nondeterministic choices are resolved by a language model, enabling declarative control of agent behavior via linear temporal logic constraints. We evaluate four versions of Autogrammar on three DSLs (i.e., Amazon CloudWatch Logs Insights, Dynatrace Query Language, and Datadog Search Syntax) and find that it generates grammars that achieve near perfect precision on unseen data; that temporal restrictions reduce execution time by 3.8x without incurring statistically-significant loss in precision; that execution data is crucial while documentation is dispensable; and that grammar-constrained decoding using Autogrammar-generated grammars significantly improves end-to-end LM performance on eight out of ten real tasks, matching or exceeding the performance of a professionally-maintained grammar. In comparison, the context-free grammars generated by existing LM baselines and a state-of-the-art formal technique perform significantly worse over the same evaluation.

## 1. 论文的核心问题与整体含义（研究动机与背景）

- **背景：** 语言模型（LM）越来越多地被用于生成领域特定语言（DSL）程序，以交互外部服务（如云监控查询、日志分析等）。
- **问题：** DSL 通常是低资源、冷门语言，LM 在生成时频繁产生**语法无效**的程序。文法约束解码（Grammar-Constrained Decoding, GCD）可以解决此问题，但其前提是具备目标语言的**上下文无关文法（CFG）**——而对于第三方或专有 DSL，这一文法往往不存在且手工编写成本高昂、易出错。
- **现实数据支撑：** 作者通过 Claude Sonnet 4.6 对 AWS Boto3 中 416 个服务的字符串参数进行分类，发现 **23% 的服务暴露至少一个需符合 DSL 的字符串参数**，共发现 **59 种独特 DSL**；这些 DSL 均属于低资源语言，LM 在其上的生成质量预期不理想。
- **核心目标：** 提出一种能够**自动从文档和执行数据中学习 CFG** 的智能体 Autogrammar，使 GCD 能够在缺乏现成文法的第三方 DSL 上落地应用。

## 2. 论文提出的方法论

### 2.1 核心思想

- 将 LM 智能体形式化为 **Kripke 结构**，其中的**非确定性选择由 LM 决定**，并通过**线性时序逻辑（LTL）约束**对智能体行为进行**声明式控制**。
- 该方法借鉴了经典文法推断理论（如 Gold 1967 的极限辨识）和形式化方法（模型检验），但利用现代 LM 的先验知识来弥补传统被动学习算法在泛化上的不足。

### 2.2 Autogrammar 的关键定义

- **状态变量：** 训练数据（正/负字符串示例）、文档、候选 CFG 集合、元数据（如时间戳、最小正确拒绝次数等）。
- **动作集合（工具）：**
  - `add_g`：提出候选文法
  - `eval`：在全部训练样例上评估文法
  - `add_s` / `del_s`：向训练集添加/删除样例
  - `gen_ts`：基于文档为目标文法缺陷生成测试字符串并加入训练集
  - `return`：返回最终文法
- **LTL 约束示例：**
  - 安全约束：如公式 (2)，确保 `eval(x)` 只能作用于候选文法集合 `C` 中的文法。
  - 性能约束：如公式 (1)，禁止在数据未变化时重复评估同一文法；公式 (3) 设定时间上限 `b`（如 120 分钟），超时后强制返回；公式 (4) 禁止对同一文法重复调用 `gen_ts`。
- **四个版本的 Autogrammar：**
  1. **Unlimited**：约束最少，仅含必要的安全限制。
  2. **Performance**：增加效率约束，如不重复评估、时间上限等。
  3. **No Documentation**：在 Performance 基础上禁用文档读取动作。
  4. **No Execution Data**：在 Performance 基础上禁用执行数据读取动作。

### 2.3 形式化保证

- **安全性：** LM 无法接触测试数据（工具层面保证）。
- **进展性：** LTL 约束防止 LM 陷入低效循环（如重复评估、重复生成测试样例），这是对实际开发中观察到的问题模式的形式化预防。

## 3. 实验设计

### 3.1 数据集 / 场景（三个 DSL）

### 3.2 Benchmark 与对比方法

- **RQ1（精度）：** 5 折交叉验证，每折用 4/5 数据训练文法、1/5 数据测试，评估精度与召回率。
- **RQ2（基线对比）：**
  - **Arvada**：最先进的文法归纳算法，使用 oracle 主动学习（仅在 CWIL 上评估，因需 oracle 且仅 CWIL 有 ground-truth 文法；oracle 为 CloudWatch 团队专业维护的文法）。
  - **LM-0**：直接用 LM 基于文档生成文法。
  - **LM-40**：在 LM-0 基础上附加 20 正例 + 20 负例。
- **RQ3（性能约束）：** 对比 Unlimited 与 Performance（120 分钟时间上限）的精度和召回率。
- **RQ4（消融）：** 对比 No Documentation 与 No Execution Data 配置。
- **RQ5（端到端）：** 10 个真实 CWIL 任务，6 个 LM（claude-opus-4-6-v1、claude-sonnet-4-6、claude-haiku-4-5-20251001-v1:0、nova-pro-v1:0、qwen3-32b-v1:0、deepseek.v3.2），每个 LM 每个任务调用 100 次，共 6,000 次 boto3 API 调用，对比三种模式：无后置条件、Autogrammar 文法后置条件、专业维护文法后置条件。

## 4. 资源与算力

- **硬件：** Amazon EC2 **c7a.4xlarge** 实例（16 个 vCPU、32 GiB 内存、最高 12,500 Megabit 网络性能）。
- **模型：** Claude Opus 4.6（语法学习阶段）、Claude Sonnet 4.6（DSL 参数分类）、以及端到端实验中 6 种不同模型。
- **时间：** Unlimited 版 Autogrammar 学习 CWIL 文法平均耗时 **461 分钟**；Performance 版受 120 分钟时间上限约束。
- **明确说明：** 论文**未提及使用了任何 GPU**，也未说明 GPU 型号、数量及训练时长；实验在 CPU 实例上运行，LM 通过 API 调用（Strands SDK）。

## 5. 实验数量与充分性

- **多 DSL 覆盖：** 在 3 个不同 DSL 上验证（CWIL 规模大、DQL 中等、DSS 规模小且负例极少），覆盖了不同数据规模和难度。
- **5 折交叉验证：** 每个 DSL 进行 5 折交叉验证，每折独立生成文法并测试。
- **四版本对比：** Unlimited vs. Performance vs. No Documentation vs. No Execution Data，构成较完整的消融实验。
- **两种基线：** 形式化方法（Arvada）和 LM 基线（LM-0、LM-40）均有对比。
- **端到端实验：** 10 个真实任务 × 6 个 LM × 100 次调用 × 3 种模式，规模相当充分。

- **评估客观性：** 端到端实验通过真实 boto3 API 调用成功与否作为最终指标，客观可靠。

  - DSS 数据集仅有 17 个负例，导致其精度波动较大（±0.124~±0.215）。

## 6. 论文的主要结论与发现

- **RQ1：** Autogrammar 生成文法在未见数据上精度**接近完美**（CWIL：0.999±0.003，DQL：1.000±0.000，DSS：0.910±0.124）；数据量越大精度越高。
- **RQ2：** Autogrammar 的精度**显著优于** Arvada（CWIL 精度仅 0.025±0.001，平均 63k 次 oracle 调用、14.6 小时/次）、LM-0（最高 0.228）和 LM-40（最高 0.510）；所有对比均通过统计检验。
- **RQ3：** Performance 版在**精度无统计显著下降**的前提下（CWIL 0.989，DQL 1.000，DSS 0.883），执行时间从 461 分钟降至 120 分钟以内（**3.8× 加速**），但 CWIL 召回率出现统计显著下降（0.555→0.176）。
- **RQ4：** **执行数据至关重要**，移除后 CWIL 精度骤降至 0.113（−89%）；**文档基本可有可无**，移除后 CWIL 和 DSS 精度无统计显著变化，DQL 仅轻微下降（1.000→0.975，p=0.027）。
- **RQ5：** Autogrammar 文法在 **8/10 任务**上显著提升端到端成功率；在 **1/10 任务上显著超越**专业维护文法，其余任务与专业文法持平。

## 7. 优点

- **新颖的形式化框架：** 将 LM 智能体形式化为 Kripke 结构 + LTL 约束，提供了声明式、可验证的智能体编程范式；与现有 agent 开发实践（工具集定义）自然契合，具有良好的可推广性。
- **被动学习、无需 oracle：** 相比 Arvada 等主动学习方法，Autogrammar 仅需已有执行日志，不依赖可查询的 oracle，适合真实场景中 DSL 只能通过受限 API 访问的情况。
- **理论保证：** 安全约束（不接触测试数据）和进展约束（防止低效循环）均由形式化框架直接支撑，而非口头承诺。
- **简明的版本控制：** 仅通过修改 LTL 约束即可获得不同行为特征的 agent 版本，体现了声明式编程的灵活性和表达力。
- **全面的评估体系：** 从文法精度、基线对比、性能消融、输入消融到端到端应用，形成完整闭环。
- **实际意义：** 能生成匹配甚至超越专业维护文法的 CFG，对 GCD 的实际部署有直接价值。

## 8. 不足与局限

- **召回率不理想：** 即使是 Unlimited 版，CWIL 召回率仅 0.555、DQL 仅 0.514，意味着文法会拒绝相当一部分合法 DSL 程序（高精度以牺牲覆盖率为代价）。
- **性能约束的副作用：** Performance 版在 CWIL 上召回率从 0.555 降至 0.176（降幅 68%），统计显著，说明时间限制会损害文法完整性。
- **DSS 数据量过小：** 仅 17 个负例，导致精度方差大（±0.124），LM 生成不稳定；DSS 结果可信度相对弱。
- **文档利用效率低：** 消融实验表明文档对最终文法质量贡献有限（甚至无贡献），说明 LM 可能未充分理解和利用文档信息，存在改进空间。
- **DSL 覆盖有限：** 仅 3 个 DSL，且均为查询语言/搜索语法；未覆盖策略语言（如 IAM）、调度语言（如 cron）等其他类型 DSL。
- **LM 依赖：** 方法高度依赖底层 LM 的先验知识（编程语言理解能力）；LM-40 基线仅达到远低于 Autogrammar 的精度，说明 LM 本身不足以单独完成任务，但若 LM 质量不足，Autogrammar 的效果仍可能下降。
- **实验偏差风险：** 端到端任务取自 Autogrammar 自身执行日志，可能存在选择偏差；任务多样性有限（均为日志分析类）。
- **形式化范围局限：** 当前 LTL 约束主要用于安全和效率控制，尚未涉及更复杂的行为验证（如组合 agent 的交互约束）。
