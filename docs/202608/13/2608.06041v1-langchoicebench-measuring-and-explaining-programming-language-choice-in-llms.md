## 摘要
大型语言模型（LLM）已被证明在生成项目级代码时表现出强烈的Python偏好，但目前尚无系统方法在新模型上衡量这一行为。为弥补这一空白，我们提出了LangChoiceBench，一个用于测量Python偏好、推荐-实现一致性以及语言多样性的项目级代码生成基准。LangChoiceBench涵盖28个跨七个软件领域的项目，在这些领域中Python通常不是好的默认选择。我们评估了25个多样的LLM，发现Python仍然被过度选择，推荐-实现一致性较低，且较小的开源权重模型通常表现出更强的Python偏好和较低的语言多样性。我们进一步分析了9,826条推理轨迹，发现大多数Python选择是自动的或主要由便利性驱动，而非对项目需求的明确考虑。在较小但重要的一组案例中，模型编造了选择Python的上下文支持——我们称之为“幻影证据”的失败模式——或者生成的代码与模型自身推理中所选语言相矛盾。

## Abstract
Large language models (LLMs) have been shown to exhibit strong Python preferences when generating project-level code, but there is currently no systematic way to measure this behaviour across new models. To bridge this gap, we introduce LangChoiceBench, a project-level code-generation benchmark for measuring Python preference, recommendation-implementation consistency, and language diversity. LangChoiceBench covers 28 projects across seven software areas where Python is often a poor default. We evaluate 25 diverse LLMs and find that Python remains heavily over-selected, recommendation-implementation consistency is low, and smaller open-weight models generally show stronger Python preference and lower language diversity. We further analyse 9,826 reasoning traces and find that most Python choices are automatic or driven primarily by ease, rather than explicit consideration of project requirements. In a smaller but important set of cases, models fabricate contextual support for choosing Python - a failure mode we call phantom evidence - or produce code that contradicts the language selected in their own reasoning.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- 大型语言模型（LLM）在项目级代码生成中的角色日益重要，从单函数生成转向更自主的软件开发流程。在此过程中，用户往往将编程语言、库生态等高层设计决策隐式地留给模型决定。
- 已有研究表明，LLM 在代码生成中表现出强烈的 Python 偏好，甚至在 Python 并非最优选择的项目级任务中依然如此；模型还可能出现“推荐一种语言、实现时使用另一种语言”的矛盾行为。
- 然而，现有研究缺乏系统性、可复现的基准来度量这一行为，尤其缺少对现代推理模型（reasoning models）的考察。
- 本文提出 **LangChoiceBench**，一个专门用于测量和解释 LLM 项目级编程语言选择的基准，填补了这一空白。其核心意义在于：将编程语言选择视为一个独立的评估目标，并揭示模型在该决策上的系统性偏差与推理缺陷。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **基准构建思路**
  - 选择七个 Python 通常不是好默认选择的软件领域：嵌入式、企业应用、前端、游戏、低延迟系统、移动应用、系统级软件。
  - 每个领域设计四个真实、简洁、语言无关的项目任务，共 28 个任务；每个任务提供三种实现提示和三种推荐提示变体。
  - 通过独立专家标注验证任务合理性：两位至少具有七年专业经验的开发者对 Python 在每个任务中的适合性进行评分，关于“weak”标签的特定一致性达到 87.8%。

- **评估协议**
  - 默认解码设置下，每个实现提示生成 20 个样本，每个推荐提示生成 5 个样本，合计每模型 2,100 个响应。
  - 实现响应通过正则表达式解析代码块，以代码量最大者为“主要语言”；推荐响应通过 `<language>...</language>` 标签解析。

- **五个核心指标**
  - **Python 实现率（PyIR）**：实现响应中主要语言为 Python 的比例。
  - **Python 推荐率（PyRR）**：推荐响应中 Python 出现在前三名建议语言中的比例。
  - **推荐-实现率（RIR）**：实现的主要语言属于模型自身该任务前三推荐语言的比例，衡量个体一致性。
  - **推荐-实现对齐（RIA）**：同一任务上推荐语言排序与实际实现语言排序的 Spearman 秩相关，衡量整体分布对齐程度。
  - **有效语言多样性（ELD）**：基于 Vendi Score 的类别特例，计算每个领域内实现语言分布的指数熵，表示“有效语言数量”。

- **推理轨迹分析**
  - 对 15 个暴露原始推理轨迹的模型，共 9,826 条 Python 实现响应进行人工标注+LLM 自动分类。
  - 建立五类互斥标签，按优先级判断：幻影证据（phantom evidence）、语言不匹配（language mismatch）、为便利选 Python（Python for ease）、自动选 Python（automatic Python）、不清楚/其他。
  - 使用 GPT-5.4 Mini 作为自动分类器，在保留测试集上达到 96.0% 准确率、Cohen's κ = 0.93。

## 6. 论文的主要结论与发现

- **Python 过度选择**：平均 Python 实现率（PyIR）为 35.3%，而推荐率（PyRR）仅 10.7%；所有模型实现时都比推荐时更常使用 Python，小型模型尤其严重。
- **推荐-实现一致性低**：平均 RIR 为 48.8%，即超过一半的实现未使用模型自己推荐的前三语言；RIA 平均仅 0.17，许多模型推荐的与实现的语言排序几乎无关。
- **语言多样性不足**：平均有效语言多样性 ELD 为 3.05；部分小型模型（如 Nemotron 7B、Code Nemotron 7B）ELD 仅约 1.7，几乎只会用一两种语言。
- **推理轨迹揭示深层原因**：
  - 69.8% 的 Python 实现是“自动选择”（忽略语言决策）；
  - 20.5% 因“便利性”而选择 Python；
  - 7.8% 出现“幻影证据”（编造提示或上下文要求 Python）；
  - 1.9% 存在“语言不匹配”（推理中选了其他语言，但输出仍是 Python）。
- **代码专用模型并未改善语言选择**：Codestral、Code Nemotron 等代码特化模型 Python 偏好反而更强；Kimi K2.7 Code 比 K2.6 的 PyIR 还高。
- **推理模型不一定更可靠**：即使有大量推理痕迹，大多数模型仍未真正评估语言选择，推理链“开始得太晚”，直接跳到实现细节。

## 8. 不足与局限

- **任务覆盖有限**：28 个任务、7 个领域远不能涵盖所有需要语言选择的场景，且刻意聚焦于“Python 不优”的领域，不适用于评估其他语言偏好的情况。
- **语境简化**：提示为单轮、语言无关的初始实现请求，未考虑真实工作流中用户会提供技术栈约束或进行讨论的情况，因此可能高估模型的自由选择效应。
- **不评估代码质量**：只分析语言选择，不衡量生成代码的正确性、可维护性或长期项目质量，语言选择与实际产出质量之间的关系未明确。
- **潜在偏差风险**：
  - 默认解码配置与重复采样虽反映常见用法，但不同温度设置可能会影响语言偏好测量。
  - 推理轨迹可能并不完美反映模型潜在推理，分类只覆盖 Python 实现，忽略其他语言选择的推理模式。
  - 人工标注和自动分类由单一方完成，尽管经过验证，仍存在主观性。
- **缺乏干预实验**：论文只描述和测量了“分布性错位”，并未测试通过提示工程、few-shot 或微调是否能够修正这些行为。
