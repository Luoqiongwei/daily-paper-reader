## 摘要
开发者通常需要将从LLM生成的代码或在线论坛中的代码片段适配到自己的项目中。然而，将其集成到现有代码库中仍然是一个具有挑战性的手动过程。成功的集成通常不仅仅是复制代码，因为用户必须在目标代码库的指定位置生成正确的适配更改。我们将此形式化为代码适配问题：给定一个代码片段、功能意图、目标代码库和适配位置，生成一个将代码片段适配到代码库中的补丁。我们提出了AdaptAgent，一种用于代码适配的多智能体、领域引导推理框架。AdaptAgent不依赖单次提示，而是将适配分解为通过类型化工件通信的专门智能体：意图摘要器从问答文本中提取适配目标；策略代理从六种适配类别中推导领域策略；领域规划器生成自排序计划；上下文挖掘器从目标代码库中提取兄弟方法的语义；代码适配器将计划实现为最小统一差异，并基于编译器的验证器进行迭代优化。这种分工实现了稳健、策略对齐的适配，并支持将代码片段适配到项目中。在真实世界数据集上，AdaptAgent在语义正确性方面优于强基线，并生成了反映开发者实际适配模式的补丁。我们的消融研究显示了每个智能体的必要性，特别是针对代码加固和异常处理的规划，以及针对逻辑定制的意图。

## Abstract
Developers often need to adapt into their projects the code generated from LLMs or code snippets from online forums. However, integrating them into an existing repository remains challenging in a manual process. A successful integration typically requires more than copying code as a user must produce correct adapting changes at a designated location in the target repository. We formalize this as the code adaptation problem: given a snippet, functional intent, a target repository, and an adaptation location, generate a patch that adapts the snippet into the repository. We present AdaptAgent, a multi-agent, domain-guided reasoning framework for code adaptation. Rather than relying on single-shot prompting, AdaptAgent decomposes adaptation into specialized agents that communicate via typed artifacts: an Intent Summarizer extracts adaptation goals from Q&A text; a Policy Agent derives domain policies from six adaptation categories; a Domain Planner generates a self-ordered plan; a Context Miner distills sibling-method semantics from the target codebase; and a Code Adapter realizes the plan as a minimal unified diff, iteratively refined using a compiler-based Verifier. This division of labor enables robust, policy-aligned adaptations and supports adapting code snippets into a project. On a real-world dataset, AdaptAgent outperforms strong baselines in semantic correctness and produces patches that mirror developers' actual adaptation patterns. Our ablation study shows each agent's necessity, especially planning for code-hardening and exception-handling, and intent for logic customization.

## 1. 核心问题与研究动机

- **背景**：开发者经常需要将从 LLM 生成的代码或 Stack Overflow 等在线论坛的代码片段集成到自己的项目中。当前这一过程完全依赖手工分析、重构和集成，既费时又容易出错，需要同时理解外来代码片段与目标代码库。
- **核心问题（形式化定义）**：论文将上述场景定义为"**代码适配问题（Code Adaptation Problem）**"——给定一个代码片段、功能适配意图、目标仓库以及适配位置，生成一个将片段适配进仓库的补丁。
- **直接 LLM 方案的不足**：初步实验表明，直接用 GPT-4 进行单次提示无法完成任务。主要两个缺陷：
  1. SO 帖子包含大量无关信息（多余的说明、替代方案、无关讨论），GPT-4 难以提取核心适配意图，导致错误和不完整的修改；
  2. 适配时经常遗漏代码加固（如缺少条件判断、final 修饰符、资源清理）和异常处理（try-catch、异常声明等），生成的代码脆弱甚至错误。

## 2. 方法论：AdaptAgent 框架

### 2.1 总体架构
- 采用**多智能体架构**，通过**类型化工件（typed artifacts）**在线性管道中协作，将适配任务分解为六个专门化组件：
  1. **Intent Summarizer（意图摘要器）**：从 Stack Overflow 问题与回答文本中提取/总结适配目标，过滤噪声。
  2. **Policy Agent（策略代理）**：依据 Zhang et al. 的 6 类适配分类学（代码硬化、解决编译错误、异常处理、逻辑定制、重构、其他），结合项目特定规范，生成适配检查清单。
  3. **Domain Planner（领域规划器）**：借助 Chain-of-Thought（CoT）推理生成"自排序"适配计划，计划由行动-理由对（𝒜ᵢ, ℛᵢ）组成，无需预设原子修改顺序。
  4. **Context Miner（上下文挖掘器）**：从目标代码库的适配位置提取兄弟方法中的 API 调用作为语义上下文。
  5. **Code Adapter（代码适配器）**：基于计划、意图、上下文生成**最小 unified diff 补丁**，而非重写整个文件，以避免幻觉性改动。
  6. **Verifier（验证器）**：外部编译器反馈循环，将语法错误回传给 Adapter 迭代修正，直至通过或达到上限。
- **四个核心思想**：
  - *Key Idea 1（适配意图）*：适配意图可通过问题与回答的摘要有效传达；
  - *Key Idea 2（领域引导）*：基于实际实践的领域知识可引导 LLM；
  - *Key Idea 3（语义上下文）*：目标类内兄弟方法提供关键语义信息；
  - *Key Idea 4（多智能体 + LLM 规划）*：多智能体与 LLM 规划合理分解任务，推导原子修改间的依赖顺序，保证补丁正确完整。

### 2.2 关键公式
- **规划生成**：以 CoT 自回归方式生成计划本身：
  p(𝒴 | ℐ, 𝒟, 𝒫𝒞, 𝒫𝒯) = ∏ᵢ₌₁ⁿ p((𝒜ᵢ, ℛᵢ) | (𝒜₁, ℛ₁), …, (𝒜ᵢ₋₁, ℛᵢ₋₁), ℐ, 𝒟, 𝒫𝒞, 𝒫𝒯)
- **补丁生成**：以计划等为条件，逐 hunk 生成统一差异补丁：
  p(ℋ | ℐ, 𝒴, 𝒞, 𝒫𝒯) = ∏ᵢ₌₁ⁿ p(ℋᵢ | ℋ₁, …, ℋᵢ₋₁, ℐ, 𝒴, 𝒞ℒ, 𝒞𝒢, 𝒞𝒜, 𝒫𝒯)

## 3. 实验设计

### 3.1 数据集与基准
- **数据集**：基于 Zhang et al. 的 629 个 Java 样本（SO 代码片段 → GitHub 对应适配代码）。过滤后得 **542 个样本 / 952 对**；其中可构建运行的仓库 201 个，对应的 **Dₜ 子集含 259 对（有测试用例）**，**Dₘ 子集含 693 对（无测试用例，人工评估）**。
- **评估指标**：
  - 正确率：Dₜ 以"通过全部目标用例"为准；Dₘ 以双人人工判断 + 第三方仲裁为准（Cohen's Kappa = 0.72）；
  - 代码相似度：PDG 依赖相似度（F1）、AST 句法相似度（F1）、CodeBLEU、编辑相似度；
  - 有效性检验：McNemar 配对显著性检验。
- **基线对比**（均基于 GPT-4o）：
  1. **CoT-only**：仅给代码片段 + 思维链提示；
  2. **Naive**（单智能体）：在 CoT 基础上一并给予意图摘要、领域引导、上下文；
  3. **Copy+APR**：直接复制代码 + 自动程序修复工具（Agentless 与 GPT-4o 修复）；
  4. **Agentless**：LLM 修复基准，有/无测试两种模式。

### 3.2 研究问题与实验组数
- **RQ1 正确性分析**：Dₜ（259 实例、测试通过）与 Dₘ（693 实例、人工检查）两条评估线，对比 4 类基线；
- **RQ2 与人类适配对比**：用 Zhang et al. 工具对 24 种适配细类进行类别分布对比，Spearman/Pearson 相关性检验；另对额外新增的 Code Hardening（188 实例）与 Exception Handling（106 实例）做运行时错误触发实验；
- **RQ3 消融研究**：分别移除 Planner、Summarizer、Context Miner，形成 3 个变体，并做 McNemar 检验；
- **RQ4 复杂度分层**：按补丁行数（8 个区间）与 hunk 数（5 个区间）分层统计正确率；
- **RQ5 规划正确性**：随机抽取 274 个实例，由独立评估者人工核查规划是否正确匹配 6 大适配类别。

## 6. 主要结论与发现

- **整体正确率**：AdaptAgent 在 Dₜ 上正确率 65.2%，在 Dₘ 上 62.3%；整体语义正确率为 **63.1%**，比基线高 5.5%–53.6%。
- **与基线对比**：统计显著优于所有基线（p < 0.01）。正确实例在 PDG/AST/CodeBLEU 等静态相似度上也全面高于基线，说明补丁在结构与语义上都更接近开发者真实适配。
- **与人类适配模式对齐**：在 5 大主类上 Spearman ρ=0.913（p=5.1×10⁻⁸）；加上 Misc 后仍有中等相关，表明工具适配模式与人类行为高度一致。AdaptAgent 在 Code Hardening（743 vs 315）与 Exception Handling（353 vs 167）上的新增修改量超过人类；运行时实验显示其中 40.3%（CH）和 44.8%（EH）的额外逻辑确实能避免人类版本会触发的运行时错误/异常。
- **消融发现**：
  - 移除 Planner：正确率降至 52.4%/51.0%，特别损害 Code Hardening 和 Exception Handling；
  - 移除 Summarizer：正确率降至 46.7%/47.6%，Logic Customization 受损最重；
  - 移除 Context Miner：正确率降至 49.8%/56.8%，Method Call 修改、目标指定、访问修饰符等适配类型明显下降。
- **复杂度影响**：正确率随改动行数与 hunk 数增加而下降——<10 行时为 79.9%，>71 行降至 46.7%；单 hunk 为 73.3%，≥5 hunks 骤降至 33.3%。
- **规划质量**：Planner 对 Logic Customization 的规划最准（246/274），对 Exception Handling 最弱（147/274）；Adapter 在 Logic Customization 上缺失率最高。

## 7. 方法的优点与亮点

- **任务分解合理**：多智能体通过类型化工件通信，将"意图理解—策略制定—规划—上下文—实现—验证"分离，避免单次提示遗漏关键修改。
- **领域知识可操作化**：将代码适配经验（6 大类分类学）转化为检查清单引导 LLM，落地性强。
- **生成最小补丁**：直接输出 unified diff，降低大规模重写导致的幻觉与无关修改风险。
- **上下文挖掘机制**：通过兄弟方法 API 调用提取语义上下文，有效提高调用本地 API 的准确性，导向项目风格的适配代码。
- **评估设计严谨**：双线评估（自动化测试 + 人工核验）、多维度相似度比较、完整消融、配对统计检验、与人类改编模式的相关性分析，以及额外鲁棒性逻辑的运行时验证，形成证据链。
- **成本可控**：约 0.05 美元/实例，在现实使用中具备可行性。

## 8. 不足与局限

- **实验覆盖有限**：仅针对 Java 与 GPT-4o，未扩展到 Python 等语言或其他模型，泛化性未验证（作者因此没有使用 AdaptEval 数据集）；框架虽可扩展更丰富的结构信号（类型、调用图、PDG），但当前统一上下文只用了 API 调用。
- **对数据质量的依赖**：适配效果受 Stack Overflow 帖子质量制约。若帖子未明确说明 API 替换或环境细节，LLM 无法推断意图。
- **复杂适配性能不足**：多 hunk / 大改动场景正确率显著下降，且模型倾向于修改方法中不相关段落。
- **提示工程敏感性**：结果高度依赖 prompt 措辞和细节程度，存在提示设计偏差风险。
- **参考偏差与人工判断风险**：尽管设计上减少了参考偏差，但 Dₘ 人工评估仍有主观因素；非确定性执行虽然取 5 次均值，但没有报告方差与单次稳定性。
- **额外改动可能过度**：AdaptAgent 引入的大量额外加固/异常处理代码即便有些被证明有用，仍可能偏离人类实际做法、引入不必要的"假阳性"差异，在实际工程审阅中可能造成噪声。
- **数据泄漏风险**：作者仅通过 GPT-4o 性能不佳来论证泄漏风险低，但未做严格的反泄漏检测。

## 总结

AdaptAgent 将代码适配这一现实工程问题转化为结构化多智能体协作的自动推理任务，通过意图摘要、领域策略、规划、上下文挖掘与编译器验证的整合，在真实数据集上显著优于单次提示与 APR 类基线，且适配模式在统计学上与人类开发者高度一致。实验设计较充分、评测方式多样、成本可控，为代码适配乃至更广泛的软件维护自动化提供了具有参考价值的框架与实证基础。
