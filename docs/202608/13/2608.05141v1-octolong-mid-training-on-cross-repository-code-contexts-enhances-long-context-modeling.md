## 摘要
语言模型（LM）的上下文长度因上下文学习、自我改进和长周期智能体工作流的需求而急剧增加。然而，现有的长上下文语料库主要由书籍、学术文章和代码仓库构成，这些资源有限，且往往缺乏长距离依赖。在这项工作中，我们引入了OctoLong，一个上下文工程流水线，利用AST解析器、语言服务器后端和包管理器来促进代码引用的递归检索，从而能够整理出长度达数百万token的依赖丰富的代码上下文。随后，我们训练了OctoLong-Instruct，这是一套能力强大的长上下文开放语言模型，源自参数量从6亿到140亿不等的基础模型，通过在约500亿token的混合语料（包含约62亿token的OctoLong代码上下文）上进行上下文扩展中期训练，再经过约100亿token的指令微调。我们的训练消融实验和针对18个最先进的开放权重长上下文语言模型的评估表明，仅用OctoLong数据替代传统上下文扩展语料库的12%，就能在长距离检索、长期状态跟踪、仓库级代码理解和下游智能体任务上取得显著提升，同时还能增强短上下文编程场景中的API使用能力。

## Abstract
Context lengths of language models (LMs) have dramatically increased, driven by the demands for in-context learning, self-improvement, and long-horizon agentic workflows. Existing long-context corpora, however, are dominated by books, academic articles, and code repositories, which are finite resources and often scarce in long-distance dependencies. In this work, we introduce OctoLong, a context engineering pipeline that instruments an AST parser, a language server backend, and a package manager to facilitate the recursive retrieval of code references, enabling the curation of dependency-rich code contexts of millions of tokens in length. We then train OctoLong-Instruct, a suite of capable long-context open LMs, derived from base models ranging in size from 600M to 14B parameters, via context-extension mid-training on a ~50B-token mixture containing ~6.2B tokens of OctoLong code contexts, followed by ~10B tokens of instruction tuning. Our training ablations and experimental evaluations against 18 state-of-the-art open-weight long-context LMs show that supplanting just 12% of traditional context-extension corpora with OctoLong data yields substantial gains in long-range retrieval, long-term state tracking, repository-level code understanding, and downstream agentic tasks, while also enhancing API usage in short-context coding scenarios.

  - 更关键的是，这些语料中**长距离依赖（long-distance dependencies）稀疏**，即上下文中真正需要跨长距离关联的"引用"密度低，导致模型在长上下文中难以学到真正有价值的关联能力。
- **论文含义**：论文提出跨仓库代码依赖挖掘（cross-repository code dependency mining）这一新范式，利用开源代码数据构建"依赖密集、多跳引用、跨仓库边界"的长上下文语料，从根本上改善长上下文模型训练的数据质量，从而显著提升模型在长距离检索、状态跟踪、仓库级理解和智能体任务上的表现。

## 方法论

### 核心思想
利用代码世界中天然存在的**跨文件、跨仓库依赖关系**（如函数调用、类实例化、模块导入），递归检索被引用代码的实现，构建依赖密集的长上下文。相比传统数据源（书籍、论文等），代码依赖具有**结构显式、可自动验证、来源近乎无限**的独特优势。

### OctoLong 数据获取流水线（五个核心阶段）
1. **种子选择（Seed Selection）**：从 SEART Hub 筛选高质量 Python 仓库（≥15 GitHub stars、≥5 贡献者），要求声明依赖且可安装，最终得到 12K 仓库、92K 种子文件；种子通过 OpenCoder 质量过滤流水线。
2. **容器化环境（Containerized Environment）**：每个种子在容器化沙箱中运行，预装其仓库依赖（site-packages），确保语言服务器查询时能解析到正确版本的依赖代码。
3. **调用点索引（Call-Site Indexing）**：使用 tree-sitter 查询提取函数调用、方法调用和类实例化的调用点（call sites），构建按种子索引的调用点列表。
4. **依赖遍历（Dependency Traversal）**：对每个调用点发起 LSP 的 GoToDeclaration 请求，通过 **jedi 语言服务器**定位被引用实现，再用 tree-sitter 提取函数/类边界代码，递归深入，最大深度 10 步。
5. **BFS 序列化（BFS Serialization）**：按广度优先顺序将获取的代码片段组装为上下文，目标长度 128K token，去重确保不重复引用同一函数/类；丢弃深度低于 5 层或跳转成功率低于 60% 的上下文。

### 训练配方（两阶段）
- **阶段一：长上下文微调（LCFT）**——基于 Qwen3 稠密基础模型（600M/1.7B/4B/8B/14B），采用 ABF RoPE 缩放，将 RoPE base frequency 从 1M 升至 10M，上下文从 32K 扩展到 128K token。在 ≈50B token 的 OctoLong-LCFT 混合语料上训练（其中 OctoLong 数据占 12.05%，约 6.2B token）。训练后与预 LCFT 检查点进行 1:9 线性模型合并以缓解短上下文性能回退。
- **阶段二：监督微调（SFT）**——在 ≈10B token 的 OctoLong-SFT 混合指令/智能体数据上微调，得到 **OctoLong-Instruct** 系列模型。

### 关键统计分析指标
论文引入两个诊断指标来量化数据质量：
- **依赖均值（Dep. Mean）**：基于改进的 LongAttn 分数，测量最后 2K 查询 token 对前缀各分段的注意力分布，反映数据是否存在"lost-in-the-middle"模式；数值越高表示依赖分布越均匀。
- **关键 token 比例（% Key Tokens）**：基于改进的 LongPPL，测量上下文敏感 token 的比例——即那些在有完整上下文时困惑度显著降低的 token，反映数据中真正依赖长距离信息的比例。

## 主要结论与发现

1. **跨仓库代码上下文是高质量长上下文训练数据**：OctoLong 流水线生成的上下文比其他数据源长 1–2 个数量级，依赖密度（Dep. Mean 0.61–0.63 vs 0.44–0.57）和关键 token 比例（6.0% vs 0.26–2.12%）显著更高。
2. **仅 12% 的 OctoLong 数据即可带来显著增益**：将传统长上下文语料中的 12% 替换为 OctoLong 数据，在 RQ1–RQ4 全部场景均有提升，尤其对高分散度状态跟踪（Call Graph）和智能体工具调用提升最大。
3. **跨领域迁移有效**：尽管数据采集仅限 Python，但在多语言代码任务（RepoQA 覆盖 5 种语言）和通用领域长上下文基准上均表现优异，说明代码依赖的推理模式具有通用性。
4. **短上下文能力不受损**：上下文扩展后短代码生成能力保持稳定（-Context Extension 消融显示几乎无回退），且 API 使用能力（BigCodeBench）反而增强。
5. **模型合并有效**：LCFT 后与预训练检查点合并可缓解短上下文性能回退，在短上下文编码和通用长上下文任务中均有正向贡献。
6. **规模趋势良好**：从 0.6B 到 14B，各尺寸均显著超越同尺寸基线，且越大提升越明显；14B 模型在多数基准上超越或追平 1024K 上下文模型（如 Qwen2.5-14B-1M）。

## 优点

- **新颖的数据来源**：首次系统性地利用跨仓库代码依赖构建长上下文语料，突破了传统数据源在长距离依赖密度上的瓶颈。
- **工程实现扎实**：AST 解析 + LSP（jedi 服务器）+ 包管理器三者的组合方案，比纯语法解析（如 ctags）更精确；容器化环境确保依赖版本正确；树状遍历 + BFS 序列化确保引用完整。
- **严格的量化验证**：不止于训练后效果，还通过注意力分析、困惑度分析从机制层面验证了数据质量优势（Table 1），建立"数据质量→模型能力"的因果链。
- **消融设计清晰**：三组消融分别隔离数据贡献、合并策略贡献和扩展必要性，逻辑严密。
- **评估全面**：覆盖长/短上下文、代码/通用、检索/推理/生成/工具调用、单轮/多轮，且对比了 18 个强基线，结论的泛化性强。

## 不足与局限

- **语言覆盖局限**：数据采集仅限 Python，虽在 RepoQA 多语言任务上有迁移效果，但未验证对其他语言（如 C++/Java/Go）代码依赖挖掘的适用性和效果。
- **上下文长度局限**：训练上限 128K，虽然流水线理论上可生成百万级 token 上下文（Table 1 显示最大可达 9.7M），但未训练和评测更长上下文模型。
- **规模局限**：最大模型 14B，无法验证方法在更大规模（如 70B+）下是否依然有效；计算资源信息不完整（未报告 GPU 型号、训练时长、总计算量等关键信息），影响可复现性和成本评估。
- **多语言缺失**：所有训练数据经英文过滤，未涉及多语言长上下文场景。
- **评估的潜在偏差**：
  - RepoQA 使用 BLEU 0.8 作为接受阈值，可能受代码格式影响；
  - AA-LCR 使用 Qwen3-235B 作为 judge 模型，存在模型偏见风险；
  - 跳过了平均超过 128K 的基准子集，可能掩盖模型在超长上下文上的弱点。
- **未解决的技术局限**：递归依赖检索仅限同语言内调用，未处理跨语言 ABI/FFI 调用；对复杂代码库中的多语言静态分析和控制流追踪无能为力。
- **应用范围局限**：OctoLong 数据在 LCFT 混合中仅占 12%，未探讨更高比例的影响（可能存在数据重复或过拟合风险）。
