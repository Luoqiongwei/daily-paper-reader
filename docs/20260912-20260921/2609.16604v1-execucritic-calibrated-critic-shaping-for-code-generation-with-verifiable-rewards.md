## 摘要
执行反馈对代码模型是一种有用的监督信号，因为单元测试是客观的，并直接衡量程序的正确性。其弱点在于，整个程序常常被简化为一个通过或失败的比特，使 RLVR 需要解决困难的信用分配问题。与此同时，编码系统通常包含独立的评审者或测试者角色，但这些评论家通常是提示出来的，而非训练得到的，并且未针对执行进行校准。我们提出 ExecuCritic，一个联合训练框架，其中代码生成器和评论家在同一执行 rollout 上更新。评论家预测通过或失败结果，并给出简短的诊断反馈；仅当评论家与执行器在当前 rollout 组上一致时，代码生成器才使用该信号。在八个代码基准和两个近期开源骨干模型上，ExecuCritic 优于无评论家的 GRPO、提示式评审者系统和标量奖励模型基线，同时需要更少的策略梯度步骤和更少的沙箱执行。消融实验和可靠性分析表明，收益来自更好的信用分配，而非更大的采样预算。

## Abstract
Execution feedback is a useful supervision signal for code models because unit tests are objective and directly measure program correctness. Its weakness is that an entire program is often reduced to one pass or fail bit, leaving RLVR to solve a difficult credit assignment problem. At the same time, coding systems often include separate reviewer or tester roles, but these critics are usually prompted rather than trained and are not calibrated against execution. We propose ExecuCritic, a joint training framework in which a coder and a critic are updated on the same execution rollouts. The critic predicts pass or fail outcomes and gives short diagnostic feedback; the coder uses this signal only when the critic agrees with the executor on the current rollout group. Across eight code benchmarks and two recent open backbones, ExecuCritic improves over GRPO without a critic, prompted reviewer systems and scalar reward model baselines, while requiring fewer policy gradient steps and fewer sandbox executions. Ablations and reliability analyses suggest that the gains come from better credit assignment rather than larger sampling budgets.

### 1. 核心问题与整体含义

- **研究动机**：代码生成中，单元测试/沙箱执行是客观且直接的可验证奖励信号，适合 RLVR（Reinforcement Learning with Verifiable Rewards）。但其核心弱点是：整个程序常被压缩为一个通过/失败比特，导致信用分配困难——长程序、长补丁中的具体错误难以归因。
- **现有路线不足**：
  - 纯 RLVR/GRPO 虽有可信 verifier，但奖励稀疏、噪声大，常需大量 rollout 与沙箱执行。
  - 多智能体/角色分解系统（如 reviewer、tester、debugger）虽提供语言反馈，但 critic 通常是提示出来的、冻结的，未与执行结果校准；coder 也不知道何时该相信 critic。
- **论文核心问题**：能否把执行奖励与学习到的 critique 结合，使 critic 让 RLVR 信号更稠密，同时避免其变成不可信的 reward model？
- **整体含义**：ExecuCritic 将 coder 与 execution-grounded critic 放在同一执行 rollout 上联合训练，通过“校准门控”只在 critic 与 executor 一致时使用 critic 信号，从而改善信用分配，并减少策略梯度步数与沙箱执行。

### 2. 方法论

- **核心思想**：联合训练 coder \(\pi_c\) 与 critic \(\pi_v\)。二者共享冻结骨干，使用独立 LoRA adapter；critic 既预测 pass/fail，又输出简短诊断 critique；coder 仅在 critic 与 executor 在当前 rollout group 上一致时采纳 critic 信号。
- **架构细节**：
  - coder 是标准自回归策略 \(\pi_c(y|x)\)。
  - critic 输入 prompt 与候选程序，先输出自然语言 critique，再输出 `<verdict>` token；该 token 在 pass/fail 上的概率质量作为校准分数 \(\hat{s}\in[0,1]\)。
  - 先 critique 后 verdict，有助于校准与可解释性。
- **校准优势**：
  - 标准 GRPO 组内标准化执行优势：\(A_i=(R_i-\mu_R)/(\sigma_R+\epsilon)\)。
  - critic 标准化分数：\(S_i=(\hat{s}_i-\mu_{\hat{s}})/(\sigma_{\hat{s}}+\epsilon)\)。
  - 最终优势：\(\tilde{A}_i=A_i+\alpha\rho_K(R,\hat{s})S_i\)，其中 \(\rho_K\) 是当前 rollout group 内 executor reward 与 critic score 的秩相关。
  - 关键：当 critic 校准好时 \(\rho_K\to1\)，critic 提供稠密信号；当 critic 不可靠或对抗时 \(\rho_K\le0\)，该项坍缩或反向，更新退回普通 RLVR。
- **critic 目标**：三项损失联合训练：
  - verdict 似然：让 critic 预测 executor 的 pass/fail。
  - pass/fail margin hinge：在同时含通过和失败样本的组内，要求通过程序分数至少比失败程序高 \(m\)。
  - critique consistency：对失败 rollout，让 critique 匹配 executor trace 提取的失败类型（syntax、import/API、type、assertion、timeout、runtime exception、unknown）。
- **coder 目标**：使用带校准优势 \(\tilde{A}_i\) 的 clipped PPO/GRPO surrogate，并加 KL 正则约束到 SFT 参考模型，防止风格漂移。
- **三阶段训练流程**：
  - **Stage 1 SFT 初始化**：coder 用 OSS-Instruct 与 Evol-Code 等数据微调；critic 用 \((x,y,v,z)\) 三元组/四元组 warm start，\(v\) 为 executor verdict，\(z\) 为教师 critique 或规范化失败描述。
  - **Stage 2 联合 RLVR**：每 prompt 采样 \(K=8\) 个 coder rollout，执行沙箱得到 reward 与失败描述，critic 预测分数与 critique，计算 \(\rho_K\) 与 \(\tilde{A}_i\)，先更新 critic，再更新 coder。
  - **Stage 3 推理时 refinement**：coder 生成 \(N=8\) 候选，critic 排序，只执行 top \(k=3\)；若全失败，反馈最高分失败 critique 给 coder，再采样新一轮，最多 \(T=3\) 轮。
