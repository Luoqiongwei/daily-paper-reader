## 摘要
大型语言模型（LLMs）在自动代码生成任务中表现出卓越性能，从而推动了该领域的新研究。尽管已有大量研究探索了基于LLM的代码生成，但输入提示中自然语言的影响仍未得到充分探索（语言偏差）。本研究旨在（1）量化输入提示的自然语言如何影响基于LLM的代码生成性能，并（2）评估一种缓解策略以减少代码生成中的语言偏差。我们在AtCoder、LeetCode和BigCodeBench上评估代码生成的准确率。为了量化代码生成中的语言偏差，每个问题均以英语、日语和中文呈现。我们使用七种LLM（GPT-4o、o3-mini、DeepSeek-V3.2、Llama-3、Qwen2.5-Coder-14B、Qwen2.5-Coder-0.5B和GitHub Copilot），并以准确率（生成的代码通过所有测试用例的问题数量）评估其性能。我们比较翻译前后的准确率，以评估翻译作为缓解策略的有效性。我们观察到，问题陈述的自然语言会影响基于LLM的代码生成性能。具体而言，各数据集官方支持的语言取得了最高的中位准确率。此外，翻译提高了准确率，但其有效性在不同数据集和模型类型之间并不一致。我们发现，AtCoder包含特别高比例的叙事风格问题陈述以及更长的问题陈述。自然语言显著影响LLM代码生成准确率。翻译可以在某些设置下缓解语言偏差，但其有效性取决于数据集和模型类型。此外，输入提示的叙事方面和上下文长度是与语言偏差以及翻译作为缓解策略的有效性相关的重要因素。

## Abstract
Large Language Models (LLMs) have demonstrated remarkable performance in automatic code generation tasks, thereby encouraging new research in this area. Although numerous studies have explored LLM-based code generation, the impact of the natural language in input prompts remains unexplored (language bias). This study aims to (1) quantify how the natural language of input prompts influences LLM-based code generation performance and (2) evaluate a mitigation strategy to reduce language bias in code generation. We assess code generation Accuracy on AtCoder, LeetCode, and BigCodeBench. To quantify the language bias on code generation, each problem is presented in English, Japanese, and Chinese. We use seven LLMs (GPT-4o, o3-mini, DeepSeek-V3.2, Llama-3, Qwen2.5-Coder-14B, Qwen2.5-Coder-0.5B, and GitHub Copilot) and assess their performance in terms of Accuracy (the number of problems for which generated code passes all test cases). We compare Accuracy before and after translation to evaluate the effectiveness of translation as a mitigation strategy. We observed that the natural language of problem statements affects LLM-based code generation performance. Specifically, the languages officially supported by each dataset achieved the highest median Accuracy. Also, translation improved Accuracy, but its effectiveness was not consistent across datasets and model types. We found that AtCoder contained a particularly high proportion of narrative-style problem statements and longer problem statements. Natural language significantly affects LLM code generation accuracy. Translation can mitigate language bias in some settings, but its effectiveness depends on the dataset and model type. Furthermore, the narrative aspects and context length of input prompts are important factors related to language bias and the effectiveness of translation as a mitigation strategy.

## 1. 核心问题与整体含义

- **研究动机**：LLM 在自动代码生成任务上表现优异（如 GitHub Copilot 在 Java 任务上达 57% 准确率；约 29% 的 Python 函数由 AI 生成），但输入提示所用**自然语言**是否会引入性能偏差（language bias）此前缺乏系统研究。
- **背景缺口**：
  - 已有研究揭示了 LLM 在通用 NLP 任务中的自然语言偏差（如英语表现最好，低资源语言较差）。
  - 作者前期工作（Koyanagi et al., MSR 2024）仅用 GitHub Copilot + AtCoder 单一数据集，发现代码生成中存在语言偏差，但**范围受限**，且**未提出缓解策略**。
- **研究目标**：
  1. 量化问题陈述的自然语言对 LLM 代码生成性能的影响（概念性复现 + 扩展）。
  2. 评估**翻译**作为缓解语言偏差策略的有效性。
- **整体含义**：这是首个系统性地跨多数据集、多模型量化代码生成语言偏差，并首次引入**叙事性（narrative）与上下文长度**视角解释偏差来源的研究，对开发者选择提示语言与工具链具有实践指导意义。

## 2. 方法论

- **核心思想**：将同一编程问题的**语义等价**问题陈述分别以英语、日语、中文呈现，喂给多个 LLM 生成代码，用测试用例通过率（Accuracy）衡量性能差异；再通过机器翻译把低性能语言翻译为高性能语言，检验能否提升准确率。
- **关键技术与流程**：
  - **语言选择三准则**：高资源语言；作者母语或学术界通用（保证提示质量）；与前期工作一致。最终选定英/日/中。
  - **数据构建翻译流程**：
    - Step 1 自动翻译：用 DeepL 将英文问题译成中文（AtCoder）/日文（LeetCode）/中+日（BigCodeBench）。
    - Step 2 人工校验：由日语、中文母语作者逐条审校修正；用开放式编码 + **饱和准则**（连续 50 个样本无新编码则停止）建立“编码手册”以系统化纠错。
    - 该流程生成的翻译文本不在 LLM 训练数据中，可**部分缓解数据泄漏**问题。
  - **实验工作流（4 步）**：
    - Step 1 生成代码：构造系统+用户提示模板（占位符 `[[PROBLEM HERE]]` 替换为具体问题），统一要求 Python 代码（后扩展 C++），以 `def` 开头并加 `if __name__ == "__main__":`。Copilot 无 API，采用 VSCode 内嵌注释方式输入，只取**第一个**建议代码。
    - Step 2 判定正误：运行官方/自备测试用例，全部通过记 "Pass"，计算 Accuracy = Pass 数 / 问题总数 ×100%。
    - Step 3 重复 5 次：因 LLM 有随机性，重复 5 次取 **中位数** Accuracy 作为结果。
    - Step 4 翻译提示：把最低性能语言译成最高性能语言（用 DeepL、Google Translate、GPT-4o 三种工具），重新生成并评估。
  - **辅助度量**：Pylint 每行告警数（代码规范）、圈复杂度、代码行数（LOC），用于检验语言是否影响代码质量而非仅功能正确性。
  - **叙事性定义（补充分析）**：满足以下任一即判为叙事风格——(1) 存在具体主语（人名/地点/组织）；(2) 目标被情境化表述（如 "Snake 的最小悲伤值"）；(3) 含解题无关的冗余句（flavor text）。两位作者独立标注，Cohen's kappa = 0.941。

## 3. 实验设计

- **数据集 / Benchmark**：
  - **AtCoder**（ABC 竞赛，题号 99–287）：756 题，难度 A/B/C/D 各 189 题；官方支持日/英。
  - **LeetCode**：100 题（16 easy、52 medium、32 hard）；官方支持英/中；测试用例由 ChatGPT 辅助生成 15 条/题并逐条人工在官网验证。
  - **BigCodeBench**（规范式代码生成，1140 题）：按 95% 置信度、5% 误差界抽样 **288 题**；官方主要提供英文。
- **对比维度**：
  - 3 种自然语言（英/日/中）× 3 数据集 × 难度等级。
  - 7 个 LLM：闭源 GPT-4o、o3-mini、DeepSeek-V3.2、GitHub Copilot；开源 Llama-3.1-8B-Instruct、Qwen2.5-Coder-0.5B/14B。
  - 翻译策略对比：翻译前后 Accuracy 差异；三种翻译工具（Google / DeepL / GPT-4o）横向比较（含 BLEU 分数）。
  - 补充实验：C++ 代码生成（仅 AtCoder）；5 种低资源语言（泰、斯洛伐克、芬兰、保加利亚、挪威语）；叙事 vs 说明性问题的 Accuracy 对比；50 例失败案例定性分析。

  - **局限**：Copilot 因无 API、版本不可控被排除后续分析；LeetCode 测试用例非官方隐藏用例，可能覆盖不全；翻译质量受人工判断影响。

## 6. 主要结论与发现

- **RQ1（语言偏差是否存在）**：
  - 存在显著语言偏差。**数据集官方支持的语言往往取得最高中位 Accuracy**（AtCoder：英/日；LeetCode：英/中；BigCodeBench：英）。
  - **语言差距（最高与最低中位 Accuracy 之差）**：开源模型为 3.6%–6.6%，闭源模型为 2.7%–15.6%，依数据集与模型类型而异。
  - DeepSeek-V3.2 整体最强（24 个组合中 17 个最优）；o3-mini 搭配**日语**表现突出，DeepSeek-V3.2 搭配**英/中**表现突出。
  - 开源模型在**英语**下相对最好，但绝对性能低于闭源模型。
  - 代码规范（Pylint 每行告警数）与圈复杂度**跨语言基本一致**，语言主要影响功能正确性而非代码风格。
- **RQ2（翻译能否缓解偏差）**：
  - 效果**高度依赖数据集与模型类型**：
    - LeetCode：翻译普遍提升（译英中位 +6.2%/+6.3%，译中 +1.9%/+6.9%）。
    - BigCodeBench：提升幅度较小（闭源 +2.4%，开源 +0.2%），但提升率较高（72.2%）。
    - AtCoder：**译英时开源模型 +3.2%、闭源模型 −5.3%**；**译日则普遍下降**（闭源 −10.3%、开源 −4.3%）。
  - 翻译工具（Google/DeepL/GPT-4o）影响不显著，BLEU 分数接近（均值 0.501–0.564）。
- **补充分析**：
  - AtCoder 叙事性问题占比 **74.0%**，LeetCode 约 50%；AtCoder 中位句数 12，LeetCode 仅 5。
  - **叙事性 + 长上下文**降低代码生成准确率（AtCoder 叙事题中位差 −6.9%）；**叙事性 + 短上下文**反而有利（LeetCode 中位差 +3.4%）。
  - 50 例失败案例中 20 例归因于叙事相关因素（理解错误/抽象不当），而非纯逻辑错误。
  - C++ 结果与 Python 一致（DeepSeek-V3.2 最优、官方语言占优）。
  - **低资源语言同样存在偏差**（如保加利亚语显著差于斯洛伐克语/芬兰语），且模型能力提升并不能消除偏差，难度越高偏差越大。

## 7. 优点

- **首个聚焦“代码生成语言偏差”的系统性研究**，同时覆盖竞赛式（AtCoder、LeetCode）与规范式（BigCodeBench）两类任务，提升外部效度。
- **概念性复现 + 扩展**的设计思路清晰：明确交代相对于前期工作（MSR 2024）的两大局限（单模型、单数据集）并逐一补齐。
- **方法严谨**：翻译经 DeepL + 母语者人工校验，并用饱和准则建立编码手册；重复 5 次取中位数控制随机性；用 Cohen's kappa 量化标注一致性（0.941 / 0.623）。
- **多维度评估**：不仅看功能正确性，还引入 Pylint、圈复杂度、LOC 检验代码质量，并验证 LOC 差异可忽略。
- **引入新解释视角**：首次在代码生成语境下定义并量化**叙事性**与**上下文长度**，揭示翻译效果差异的潜在机制。
- **实用性强**：提出可操作建议（选高资源/官方支持语言；翻译前先在小规模目标数据上验证），并指出压缩（compression）与结构化组织（organization）两个未来方向。
- **可复现性**：提供复现包（Zenodo 链接）。

## 8. 不足与局限

- **算力信息缺失**：未报告硬件、推理成本与耗时，难以评估实验的可复现成本与规模。
- **构造效度**：
  - 低资源语言翻译**无母语者验证**（作者团队无对应母语者），翻译质量存疑。
  - 主实验仅生成 Python，C++ 实验仅限 AtCoder，编程语言覆盖有限。
- **内部效度**：
  - 闭源模型内部结构不透明，且可能随版本更新变化；Copilot 无法固定版本被排除。
  - **数据污染风险**：AtCoder/LeetCode 上大量多语言题解（博客、仓库）可能进入训练数据，观测到的差异可能部分源于训练数据分布而非模型内在语言理解能力。
  - LeetCode 测试用例非官方隐藏用例，边界覆盖可能不足。
  - 5 次重复是经验性参数，可能不足以完全消除随机性。
- **外部效度**：
  - 3 个数据集不能代表全部代码生成场景；7 个模型也未覆盖全部主流 LLM。
  - 未纳入日本本土 LLM（作者称当时无满足条件的模型）。
- **分析层面局限**：
  - 翻译策略在**数据集层面**选择目标语言，而非按模型/难度细分，可能掩盖更细粒度的语言偏好。
  - 叙事性分析仅覆盖 AtCoder D 级与 LeetCode Hard 级，样本量较小（50 + 32）。
  - 论文摘要与正文存在数据不一致（摘要称 LeetCode 叙事性占比 21.2%，正文表 20 为 50.0%），提示结果表述需谨慎。
  - 低资源语言偏差归因（如分词器效率差异）仅为**假设**，未经验证。
