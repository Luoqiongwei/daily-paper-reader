## 摘要
大语言模型编程智能体近来已可用于软件任务，但能力较弱或开放权重的智能体仍难以可靠地理解用户意图并执行复杂的多步工作流。这一差距在长时程场景中尤为明显：智能体必须反复检查先前结果、诊断失败，并在交互约束下选择下一次代码编辑。这引出一个自然的问题：我们可以做些什么来改进弱编程智能体的思考过程？我们在 CodeClash 中研究这一问题；CodeClash 是一个代码竞技场基准，原工作通过多轮锦标赛在 6 个竞技场中评估了 8 个商业编程智能体。由于 Qwen3 Coder Plus 在其中排名最后，我们以开放权重的 Qwen3-Coder-30B 为案例，研究如何利用来自更强智能体的蒸馏知识来改进它。我们的分析表明，Qwen3-Coder-30B 并未针对竞技场式交互得到良好优化：它经常产生语法错误和破坏协议的错误，并且在多轮之间表现出较弱的策略适应性。这些失败仅靠普通指令微调难以纠正，因为离线 SFT 无法直接验证生成的动作是否有效或有益。为解决这一问题，我们提出 ReAct SFT，其将教师轨迹重写为显式的 [obs][thought][act] 链，以及轨迹质量加权 SFT，其通过重新加权样本来鼓励编辑后检查。ReAct SFT 显著改善了策略行为，并且我们微调后的模型在锦标赛评估中优于原始 Qwen3 Coder Plus。

## Abstract
Large language model coding agents have recently become useful for software tasks, but weaker or open-weight agents still struggle to reliably interpret user intent and execute complex multi-step workflows. This gap is especially visible in long-horizon settings, where an agent must repeatedly inspect prior outcomes, diagnose failure, and choose the next code edit under interaction constraints. It motivates a natural question: what can we do to improve the thinking process of a weak code agent? We study this question in CodeClash, a code-arena benchmark where the original work evaluates 8 commercial coding agents across 6 arenas through multi-round tournaments. Since Qwen3 Coder Plus ranks last among them, we take the open-weight Qwen3-Coder-30B as a case study and investigate how to improve it with distilled knowledge from stronger agents. Our analysis shows that Qwen3-Coder-30B is not well optimized for arena-style interaction: it frequently produces syntax and protocol-breaking errors and exhibits weak strategic adaptation across rounds. These failures are difficult to correct with vanilla instruction tuning alone, since offline SFT cannot directly verify whether a generated action is valid or beneficial. To address this, we propose ReAct SFT, which rewrites teacher trajectories into explicit [obs][thought][act] chains, and trajectoryquality weighted SFT, which reweights samples to encourage post-edit checking. ReAct SFT substantially improves strategic behavior, and our fine-tuned model outperforms the original Qwen3 Coder Plus in tournament evaluation.

## 2. 方法论
### 2.1 共享 SFT 设置
- 将每个 CodeClash 轮次轨迹视为多轮对话微调实例，只对 assistant 输出计算损失，mask 掉 system/user token。
- 形式化：对第 k 个 assistant 响应，历史上下文为  
  \(X_k=(s,u_1,a_1,\dots,u_{k-1},a_{k-1},u_k)\)。
- 损失函数：  
  \[
  L_{SFT}=-\sum_{j=1}^{L}\log p_\theta(t_j|t_{<j})\cdot \mathbf{1}[j\in Y]
  \]
  其中 \(Y\) 为 assistant token 位置。
- 参数高效微调：使用 **QLoRA/LoRA**，4-bit 量化加载 30B 模型，前向/反向用 bfloat16；LoRA rank \(r=16\)，插入所有 Transformer block 的注意力投影层（q/k/v/o_proj），主干冻结。
- 支持全轨迹训练和固定窗口训练，因锦标赛轨迹较长且近期交互更相关。

### 2.2 ReAct SFT
- **核心思想**：将教师轨迹重写为显式的 **[Obs][Thought][Act]** 链，使竞技决策过程更明确。
- 使用 **Claude Sonnet 4.5 API** 逐步标注强智能体轨迹；每个 assistant turn 的标注输入包括前一步执行输出、当前上下文、原 THOUGHT 和原 bash 命令。
- 重写只针对 reasoning 部分：
  - **[Obs]**：总结最相关的先前反馈；
  - **[Thought]**：说明当前步骤的策略目的；
  - **[Act]**：命名具体执行操作；
  - **原 bash 命令保留**，保证轨迹仍忠实于教师动作。

### 2.3 Trajectory Quality Weighted SFT (TQ-SFT)
- **目标**：针对无效或未验证编辑问题，鼓励“先修改、再检查”的安全行为。
- 从 top 5 教师轨迹构造规则标注，将 bash 命令映射为行为类别，如 `MODIFY_MAIN`、`CODE_CHECK`、`SUBMIT`、`STRATEGY_READ`、`STRATEGY_ANALYSIS`。
- 根据动作时序计算轨迹级统计量，例如修改后是否检查、是否未验证就提交，并合成启发式质量分 \(q_i\in[0,1]\)。
- 训练时将质量分转为样本权重 \(w_i\)，损失为：
  \[
  L_{TQ-SFT}=\frac{\sum_i w_i \ell_i}{\sum_i w_i}
  \]
  其中 \(\ell_i\) 为样本 i 的 assistant-only 交叉熵损失。更安全的“edit-validate-submit”轨迹权重更高。

## 3. 实验设计
- **场景/benchmark**：CodeClash 的 **BattleSnake arena**。智能体在固定预算下通过终端脚手架迭代修改私有仓库，再在竞技场中执行并多轮竞争；每步必须输出一个 bash 命令和 THOUGHT。
- **训练数据**：

## 6. 主要结论与发现
- **ReAct SFT 最有效**：显式 [Obs][Thought][Act] 监督显著改善策略行为，使模型更常检查轮次结果、日志和失败模式，并选择与观察相关的编辑。
- **最终模型**：ReAct 6-turn 在锦标赛中：
  - 对 Qwen3 Coder 30B base：9 胜 3 负 1 平；
  - 对 Qwen3 Coder Plus：12 胜 0 负 0 平；
  - 对 Claude 4.5：0 胜 15 负 0 平。
  - 即显著超过原始 Qwen3 Coder Plus，但仍远低于 Claude 4.5。
- **TQ-SFT 的作用**：主要提升可靠性，减少无效提交和协议破坏，但未直接教策略，锦标赛提升有限；自对弈变体将无效提交从约 40% 降至 25%，但实际比赛失败更多，说明模仿式微调可能带来行为漂移。
- **普通 SFT 不稳定**：Vanilla self-play SFT 可小幅提升胜率，但教师数据 SFT 常导致全平局或无效执行，说明朴素模仿可能放大行为漂移。
- **行为差异**：ReAct SFT 更接近 Claude 4.5 的轮次诊断和测试行为；TQ-SFT 主要增加检查和脚本分析，偏可靠性而非策略适应。
