## 摘要
确保 LLM 生成代码的正确性是现代软件工程的一项核心挑战。面向智能体代码生成的基准测试使用留出测试套件检查正确性，而这类测试套件本质上不完整，且越来越容易受到记忆化的影响。形式化验证可以避免这两个问题，但现有工作仅覆盖以规范作为输入的独立任务，而非真实问题；真实问题涉及大型代码仓库，并以模糊的自然语言陈述意图。我们提出 Benchproofer，一个将带有已知正确补丁的编码任务转化为经形式化验证任务的流水线：它为新增代码编写规范，用公理概括该代码调用的现有函数，并且只有在机械门控与对抗门控均通过后才接纳一个实例。将其应用于 SWE-bench Verified 得到 SWE-Proof，包含 500 个真实问题，其正确性经由形式化验证而非测试来确认，并且该方法还可扩展到 SWE-bench Pro。在两个前沿模型上，验证能捕捉到测试遗漏的问题：四分之一到二分之一的通过测试补丁存在反例，这是结构化自然语言规范所不能修复的，而正确的形式化规范则将 Opus 4.8 的解决率从 85% 提升到 95%。编写该规范才是难点：必须自行编写规范的模型相较于无辅助基线没有任何提升，而且它们的规范只有 62% 通过了我们的审计。常见的失败模式是忠实性：规范只约束了部分所需行为，而让其余部分自由。规范质量仍然与结果相关：在未解决实例中有 89% 失败，而在已解决实例中为 47%，这使得忠实规范合成成为一个具体的开放问题。

## Abstract
Ensuring the correctness of LLM-generated code is a core challenge for modern software engineering. Benchmarks for agentic code generation check correctness with held-out test suites, which are inherently incomplete and increasingly susceptible to memorization. Formal verification avoids both problems, but existing work covers only standalone tasks whose specifications are given as input, not real issues, which touch large repositories and state intent in vague natural language. We present Benchproofer, a pipeline that turns a coding task with a known correct patch into a formally verified one: it writes a specification for the new code, summarizes the existing functions that code calls with axioms, and admits an instance only after mechanical and adversarial gates agree. Applying it to SWE-bench Verified yields SWE-Proof, 500 real issues whose correctness is formally verified rather than tested, and it extends to SWE-bench Pro. Across two frontier models, verification catches what tests miss: a quarter to a half of test-passing patches admit counterexamples, which a structured natural-language specification does not fix, while a correct formal one lifts resolution from 85% to 95% for Opus 4.8. Writing that specification is the hard part: models that must write their own gain nothing over an unaided baseline, and only 62% of their specifications pass our audit. The usual failure is faithfulness, a specification that constrains part of the required behavior and leaves the rest free. Specification quality still tracks the outcome, failing on 89% of unresolved instances against 47% of resolved ones, making faithful specification synthesis a concrete open problem.

## 1. 核心问题与整体含义（研究动机与背景）

- **问题根源**：当前评估 LLM 代码生成智能体的主流范式是**执行留出测试套件**。测试虽然廉价、易实现、可复用现有代码库中的测试，但作为正确性判据存在两个根本缺陷：
  - **本质不完整**：有限输入集无法证明未覆盖输入上的行为；审计发现 SWE-BENCH 中许多被判正确的补丁仅因测试太弱而通过。
  - **易被奖励黑客**：智能体可利用测试的不完整性，产出通过测试但不通用的代码；已有研究发现大量通过测试但实际错误的解。
- **形式化验证的优势与缺口**：形式化验证可避免上述两问题，对规格定义的整个输入域进行证明。但现有工作仅覆盖：
  - 小型精选习题；
  - 独立的 HumanEval 式任务；
  - 竞赛数学；
  - 且**大多数技术把形式化规格作为输入**。
- **真实任务的挑战**：真实编程任务需要新代码融入大型代码库（多文件、多依赖），并以**模糊的自然语言**陈述意图。现有方法与其基准都无法对这类任务施加可靠的验证预言机。
- **论文目标**：填补这一空白——提出 **BENCHPROOFER** 构建流水线与 **SWE-PROOF** 基准，为 SWE-BENCH VERIFIED 的全部 500 个真实问题附加形式化验证预言机，并扩展到 SWE-BENCH PRO。

## 2. 方法论：核心思想、关键技术细节与流程

### 2.1 核心思想

- **核心主张（Claim 1，Verify ⇒ Resolve）**：给定规格 $S$ 与公理 $A$，若实现 $I$ 在 $A$ 下对 $S$ 验证通过，且 $P$ 是与 $I$ 等价的 Python 补丁，则 $P$ 通过 SWE-BENCH 隐藏测试、解决该实例。
- **两大支柱**：
  1. **环境公理化**：只建模新增/修改的代码，用**公理**概括被调用的未改动函数（超近似摘要），使验证可行。
  2. **多重门控准入**：机械验证 + 对抗式 LLM 审计共同把关，只有全部门控一致通过才接纳实例。

### 2.2 构建流程（BENCHPROOFER）

- **规格合成**：智能体将自然语言描述转为形式化规格，并在反馈循环中精化。构建期可看到金标准补丁、缺陷代码、测试补丁、F2P/P2P 列表，通过"是否存在实现能满足规格却仍失败 F2P 测试"来校准规格强度。
- **环境公理化**：
  - 收集新实现调用的未改动被调函数 $f_1, f_2, \dots$；
  - 为每个 $f_i$ 构建模糊测试器（随机输入 + 智能体编写用例）；
  - 智能体起草候选公理 $A_i$，由两个对立循环精化：
    - **正确性循环**：模糊测试器执行 $f_i$，任何违反 $A_i$ 的输入将公理打回修订；
    - **有用性循环**：验证器尝试用 $A_i$ 作为引理闭合证明，失败则打回。
  - 公理**无需精确**，可超近似，只要证明能闭合。
- **三后端**：
  - **NAGINI**：静态类型 Python 的契约验证器（SMT 求解）；
  - **VELVET**：嵌入 LEAN 的命令式验证 DSL（SMT 支撑的 tactic）；
  - **纯 LEAN**：以 Lean 4 + Mathlib 陈述规格，由证明智能体写出证明项，内核校验。
- **实现与补丁**：每个实例携带参考实现（必须验证通过）、前置缺陷实现（必须验证失败）、以及等价的 Python 补丁。
- **证明**：LEAN 下证明由智能体编写、编译器检查；NAGINI/VELVET 由 SMT 求解。

### 2.3 正确性门控（13 项）

- **机械门控**：验证、判别（前置缺陷必须失败）、变异（一阶变异体必须被拒）、卫生（导入白名单、无 `sorry` 等）、解析（官方 Docker 跑通金标准补丁）。
- **对抗门控**：
  - **公理可靠性**：独立审计员重新模糊测试，在实例 Docker 镜像内执行真实被调函数，单次违反即拒绝；
  - **一致性**：参考实现与真实补丁仓库函数在大量生成输入上比对（至少 105 个输入）；
  - **可靠性与完备性**：审计员从两个方向攻击规格——过强（真实代码不满足）或过弱（错误实现也能验证）；
  - **属性测试证伪**：为每个建模函数编写带标签的属性测试套件，由验证器裁决；
  - **等价性**：逐操作审计参考实现与金标准补丁的对应关系（类型精化 / 公理化被调 / 相同操作）；
  - **防泄漏**：规格视图不得泄露修复答案，机械筛查 + 对抗重建。

### 2.4 保证的边界

- **意图–规格边界**：无法保证规格匹配非形式化自然语言意图，由属性测试证伪门控守护。
- **公理–被调函数边界**：由公理可靠性门控 + 模糊测试守护。
- **参考实现–补丁边界**：由一致性门控与等价性门控直接处理。

## 6. 主要结论与发现

- **发现 1：测试不完整，只有形式化规格能弥合差距。**
  - 在通过所有隐藏测试的补丁中，**26.8% 被对抗审计推翻**（即存在与金标准补丁可区分的输入）。
  - 形式化后端从 Row 6 到 Row 7 仅损失 0.9 / 0.3 个百分点；EARS 则损失 17.8 / 46.0 个百分点。
  - 结构化自然语言规格**不能**替代形式化验证。

- **发现 2：自构建规格无帮助。**
  - 端到端设置（Row 2）相对无辅助基线（Row 0）无提升，最佳单元仅 +0.6 个百分点，其余持平或负。
  - Row 3 与 Row 2 差 ≤1.6 个百分点，瓶颈不在实现或证明，而在规格本身。

- **发现 3：正确的规格帮助显著。**
  - 提供金标准规格将解析率从 85.0% 提升到 96.2%（Opus 4.8）、81.2% 到 94.4%（GPT-5.5）。
  - 扣除局部化收益后仍 +6.9 / +7.7 个百分点。
  - Row 7 对 Row 3：给定正确规格比自写规格多 **+11.0 / +14.2 个百分点**（NAGINI）。

- **发现 4：规格合成是瓶颈，忠实性是主因。**
  - 五属性审计通过率：NAGINI 46.0% / 64.2%，VELVET 60.0% / 72.0%，LEAN 61.4% / 69.2%。
  - 失败高度偏斜：公理可靠性、可采纳性、完备性几乎不失败；**忠实性失败 42.5%（Opus）/ 30.0%（GPT）**，在每个单元中都是最高。
  - 模型写出"对所建模函数正确但覆盖太少"的规格。

- **发现 5：规格正确性跟踪补丁正确性。**
  - 未解决实例的规格审计失败率 **89.4%**，已解决实例 **47.3%**。
  - 忠实性差距最大（平均 44.3 个百分点），可靠性次之（26.7 个百分点）。
  - 盲审再审计与解析结果的 Mantel–Haenszel 优势比约 **13.5 / 14.0**。

- **SWE-BENCH PRO 迁移**：两项发现完整迁移（验证几乎免费、规格合成仍是瓶颈）；隐藏测试不完整性更严重，基线解析的实例经反例审计后仅剩 17.4% / 3.7%。

## 7. 优点

- **对抗式生成 + 机械裁决**：所有攻击由指令为"打破 bundle"的智能体产生，再由验证器/仓库/测试套件机械裁决，避免主观判断。
- **多后端设计**：同一任务在 4 种规格语言下独立构建，既能比较表达能力，又能交叉验证建模位置（84.4% 实例三后端建模相同文件集，中位 Jaccard = 1.0）。
- **全面的门控体系**：13 项准入检查覆盖验证、判别、变异、公理可靠性、一致性、等价性、防泄漏等，且"不适用"与"通过"严格区分。
- **可复现证据链**：每个 bundle 附带公理探测、属性测试套件、逐操作对应图、来源图、准入记录，使语料可**再审计**而非仅可重跑。
- **诚实的边界声明**：明确列出三大信任边界（意图–规格、公理–被调、实现–补丁）和三类窄限制。
- **反作弊与防泄漏**：版本历史清洗、隐藏测试不可见、验证工具无仓库访问、机械 + 对抗防泄漏筛查。
- **丰富的分层分析**：揭示规格收益在非局部任务上最大（多文件 +23.4、多函数 +22.3、3–5 个 F2P 测试 +30.4）。
- **模型行为洞察**：Opus 4.8 通常先打补丁（约 3/4 episode），GPT-5.5 通常先形式化（约 2/3），但结果相近；后端难度可通过验证器接受率量化（EARS 0.99–1.00 > LEAN 0.60–0.66 > NAGINI 0.30–0.53 > VELVET 0.17–0.29）。

## 8. 不足与局限

- **Verify ⇒ Resolve 不是证明**：依赖两个经审计的信任点（公理可靠性、实现到补丁的精化保真度），通过执行、模糊测试和对抗审计建立，而非形式化证明。
- **三大边界限制**：
  - **意图–规格边界**：无法保证规格匹配非形式化自然语言
